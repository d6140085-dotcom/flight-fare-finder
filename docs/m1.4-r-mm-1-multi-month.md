# M1.4 R-MM-1 — Several departure months per route

- **Status:** approved by the owner 2026-11-12; **implemented as code only** (this PR). Nothing
  deployed; no production table, Lambda, API Gateway, IAM, SSM or EventBridge change; no email.
- **Decision record:** [ADR 0001](adr/0001-m1-4-dynamic-routes.md) D1 as amended 2026-11-12.
- **Background audit:** [m1.4-same-route-multi-month.md](m1.4-same-route-multi-month.md).

## 1. Rules

1. A user can hold several **fixed-month** subscriptions of the same route:
   `KHH → TYO` for 2027-01, 2027-02 and 2027-03 are three independent subscriptions.
2. At most **one subscription per user, route and fixed month**.
3. **Legacy rolling** subscriptions (M1 rows, no month, always "next month") stay as they are:
   at most one per user and route, and they **can coexist** with fixed months of that route.
4. **10 records per user**, every row counted: each month is one record, paused and expired
   rows included. Only a delete frees a slot.
5. Changing a subscription's route **or month** moves it (one transaction, quota untouched).
   Moving onto an existing route/month is `409 duplicate_subscription`, never a merge.

## 2. Identity

| | Legacy rolling | Fixed month |
|---|---|---|
| DynamoDB partition key `email` | session email | session email |
| DynamoDB sort key `route` | `KHH-TYO` | `KHH-TYO#2027-01` |
| Public subscription ID (API paths, front end) | `KHH-TYO` | `KHH-TYO_2027-01` |
| `origin` / `destination` attributes | `KHH` / `TYO` (M1 rows: derived from the key) | `KHH` / `TYO` |
| `departure_month` attribute | absent | `2027-01` (always equal to the key's month) |
| API field `route` | `KHH-TYO` (the pair) | `KHH-TYO` (the pair) |
| API field `id` | `KHH-TYO` | `KHH-TYO_2027-01` |

- **Mapping:**
  - sort key ↔ ID is a pure character swap (`#` ↔ `_`);
  - both are pure functions of (origin, destination, month), via `subkeys.py` (three identical
    copies, kept identical by a test) and `src/lib/m14/subscription-id.ts`;
  - the shared vectors are in `aws/tests/vectors/subscription-ids.json`.
- **Why `_`:**
  - It is an unreserved URL character, so the ID never needs percent-encoding.
  - `#` would be read as a fragment and never reach the server.
  - It can't occur in a code or a month.
  - The regex `^[A-Z]{3}-[A-Z]{3}(_\d{4}-(0[1-9]|1[0-2]))?$` accepts nothing else; `KHH-TYO#…`,
    `%23` and `..` are all `400 invalid_route`.
- **Stability:** the ID changes only when the subscription's route or month changes (the API
  returns the new `id`; the front end uses it). Legacy IDs (`TPE-TYO`) are unchanged, so the old
  `{route}` paths keep working.
- **Authorisation:** every read and write uses the session's email as the partition key. An ID
  is only a sort key *inside the caller's partition*: knowing someone else's ID gives `404`.
  Tested.
- **Invariant I6:** the key's pair equals `origin`/`destination`, and a fixed key's month
  equals `departure_month`.
  - The fare check treats a row that breaks it as INVALID; it never guesses.
  - The B4 scenarios check it after every storm.
- **Rejected:** opaque UUIDs. They would need a lookup per request and a stored attribute, with
  no gain over a deterministic key that DynamoDB already enforces as unique.

## 4. Rolling/fixed overlap policy

**Overlap:** a user's rolling row and a fixed row of the same route resolve to the **same
effective month** (e.g. today, rolling `TPE-TYO` → 2026-12 and fixed `TPE-TYO#2026-12`).

**Unit of deduplication.** The notification stream is (user, route pair, effective month), as in
Phase 2B-1. Every subscription resolving to that stream shares it. Within a stream the M1 rule
applies: at most one alert per 24 h, unless the fare drops ≥ 20 % or ≥ NT$2,000. So two
overlapping subscriptions **never produce two emails for the same fare**. That is the
intentional policy, not a silent suppression: the email is about a route and month, and the
user gets it.

| Case | Behaviour | Tested in |
|---|---|---|
| a. Both eligible (active, target ≥ fare) | **One** message listing both keys; **one** email. The email shows the **lowest matched target** (the fare is at or below both, so this is the most informative true statement) | `test_a_both_eligible_one_message_listing_both`, `test_both_eligible_one_email` |
| b. Targets differ, the fare meets only one | The alert is for the one whose target is met, with its own target. **No suppression** by the other | `test_b_targets_differ_the_met_one_alerts` |
| c. Month end (Asia/Taipei midnight on the 1st) | The rolling row moves to the next month: it leaves the old stream (where the fixed row stays) and joins the next month's stream. All month rules use the scheduler's single `as_of`, so a run never mixes months. A fare event checked before midnight is still judged by its `as_of` month | `test_c_month_end_moves_only_the_rolling_row`, `test_month_end_rolling_row_starts_a_new_stream` |
| d. One of them paused or expired | Ignored: it neither alerts nor blocks the other. If the strictest one is paused **between the fare check and the send**, the email still goes out for the other, showing the other's target | `test_d_paused_or_expired_never_suppress_the_other`, `test_strictest_one_paused_since_the_check_still_sends_with_the_other_target` |
| e. Both paused/expired, or both targets no longer met at send time | Nothing sent, **nothing recorded** as sent | `test_all_listed_rows_ineligible_skips_and_records_nothing` |
| f. Two messages for one stream (e.g. an older fare check) | The second is deduplicated by the stream's M1 rule: one email, or a re-alert only on a real price drop | `test_second_message_for_the_same_stream_is_deduped` |
| g. Different months of one route | Independent streams: each month alerts on its own | `test_other_months_of_the_route_are_independent_streams` |

**Send-time behaviour, end to end** (`OverlapFlowTests` in `aws/tests/test_m14_multi_month.py`:
real fare-check runner → v2 message → notification service on a moto table, with a fake Resend):

| Situation between fare check and send | Result |
|---|---|
| Different targets, only one met | one email, that subscription's target |
| Both met | one email, lowest target, one history row for the stream |
| One paused / one deleted | one email, the other's target |
| Both paused/deleted | nothing sent, nothing recorded (`skipped:paused+subscription_gone`) |
| Shown target lowered / raised | lowered below the fare → the other's target; raised → the lowest target that is still met (never a target the fare doesn't meet) |
| Same fare event delivered again | `skipped:duplicate_event`, no second send |
| Next scheduled run, same fare / small drop / ≥ 20 % drop | deduplicated / deduplicated / re-alert (M1 rule unchanged) |
| Resend outcome uncertain (timeout or lost response), then retry | **same Idempotency-Key and same body** → Resend deduplicates; exactly one delivery |

**Fix made in this review — stable retry payload.** The email shows the lowest *still-eligible*
target, re-read at send time. Before this fix, a retry after an uncertain Resend outcome
re-read the rows again: if the user had paused one subscription or changed a target in between,
the retry carried a **different body under the same Idempotency-Key**. Resend rejects that
(`409 invalid_idempotent_request`), and the message would end in the DLQ — no duplicate email,
but an alert could be lost. Also, the search links were dated from the send time rather than the
fare event. Now:
- the presented target is **pinned to the claim** on the first attempt
  (`history.pin_target`: `SET claim_target = :t, claim_target_event = :e` only while
  `claim_event = :e` and this event has not pinned yet; otherwise its earlier pin is read back), and every retry of
  that claim reuses it. A pin left by another event whose claim expired and was taken over is
  never reused (`test_a_taken_over_claim_never_reuses_another_events_pinned_target`). Both
  attributes are removed when the claim is committed or released;
- links are built from the message's `as_of`, not from "now".

So the key (`flight-fare/{event id}`) and the rendered body are functions of the fare event
alone. A test proves the retry is refused without the pin (`test_without_the_pin_the_retry_would_be_refused`).

**At most one email — argument.** (1) The fare check emits one message per user per work item,
listing all overlapping keys (no second message for the overlap). (2) Every message for the
stream (user, pair, month) takes the stream's single claim; a second message is deduplicated by
the M1 rule or by the event id. (3) Each send uses `flight-fare/{event id}` with a body fixed by
the claim, so Resend delivers it at most once whatever the retries. (4) Pausing, deleting or
editing can only *remove* eligibility; nothing re-opens a committed stream except the M1 price-
drop rule. `test_at_most_one_email_for_every_state_combination` checks all 225 combinations of
{active, paused, deleted, target lowered, target raised} × the same for the second row × three
fares: never more than one delivery, and a delivery exactly when at least one row is still
eligible. M1 safeguards (24 h floor, 20 % / NT$2,000 re-alert, `{email}#{route}` dual-write,
EventBridge DISABLED, Resend testing mode) are unchanged.

The page states it in plain words: 「同一航線可以分別追蹤不同的出發月份，每個月份各算 1 筆訂閱。
舊版「每月滾動」的訂閱若與某個月份的訂閱查詢同一個月，同一天最多寄出一封通知。」

## 6. Rollback risks

Two different questions for every rollback: **data integrity** (can a row, quota or history
record become wrong?) and **availability of price tracking** (does every subscription the user
sees on the page still get alerts?). A rollback is only **service-safe** when both hold.

| | Rollback | Data integrity | Price-tracking availability | Verdict |
|---|---|---|---|---|
| A | **Subscriptions API only** (back to the pre-R-MM-1 M1.4 API) | Safe: no row is rewritten. But the old API's `route_param` rejects `ORIG-DEST_YYYY-MM` IDs, so existing fixed-month rows **cannot be edited, paused or deleted** while they keep counting toward the quota (a user with 10 such rows is stuck at the limit). The old create path writes plain `ORIG-DEST` keys with a month — a second representation of the same route/month beside an existing `#YYYY-MM` row, which the new code then sees as two rows (I7 violation) | Fare check (still new) keeps alerting all rows | **Not service-safe** — integrity risk from new writes, users lose control of their rows. Only acceptable with writes blocked (read-only page) until roll-forward |
| B | **Fare-check Lambda only** (back to the M1 parser) | Safe: the fare check writes nothing to subscriptions | **Every fixed-month subscription stops getting alerts** (the M1 parser reads only `route = "ORIG-DEST"`); rolling rows keep working. Silent from the user's point of view | **Not service-safe.** Integrity-safe only. Must be announced or kept short; roll forward to restore |
| C | **Notification Lambda only** (v2 → M1 notification) | Safe: v2 dual-writes the M1 history key `{email}#{route}`, so M1 dedups correctly against what v2 sent; nothing in subscriptions is written | Alerts continue for rolling and fixed rows, but with M1's rules: **no send-time re-check at all** (a row paused or deleted after the fare check can still trigger that one email — as in M1 today), no pinned target, and dedup **per route, not per month**: an alert for one month suppresses alerts for the route's other months for 24 h unless the price drops ≥ 20 % / NT$2,000 | **Degraded, not service-safe**: no data damage and no duplicate within 24 h, but some month alerts are suppressed and the pause/delete guarantee is lost. Short-term only |
| D | **Complete M1.4 stack** (API + fare check + notification + page back to M1) | Safe for the stored data (no migration to undo; PITR is the backstop per D11, but it is DISABLED today and must be enabled before B3, see the cutover blocker below). `subscription_quota` is left orphaned (harmless, unread by M1) | **All fixed-month subscriptions lose alerts and disappear from the page** (the M1 list Lambda only knows rolling rows); M1 rolling rows work exactly as before | **Not service-safe** for users with fixed-month rows. Integrity-safe. Before rolling back: count fixed-month rows; if > 0, notify those users or keep alerts running |

Front end only (Phase 3A mock) is preview-only and harmless. No rollback can make a key change
half-done: every key change is one transaction (s18, s22–s24).

### B3 production-cutover BLOCKER — legacy M1 writers and row versions (recorded 2026-11-13, revised 2026-11-19)

Since PR #22, every M1.4 mutation is a version-aware conditional write (`version_token`, API
contract §4.5). PATCH and DELETE need `if_version`: `428` when missing, `409` when stale. Rows
written by the deployed M1 save Lambda (`flight-save-subscription`) are **legacy**: the API
protects them with an all-attribute guard and a `legacy-` version, with one documented gap (an M1
row re-created byte-identically). **B3 must not go to production until everything below is done
and verified.** This document authorises no production change.

**Production facts this plan relies on (read-only checks, 2026-11-17).**
- The only M1 code that writes `subscriptions` is `flight-save-subscription`, behind
  `POST /subscribe` on the HTTP API `flight-api`. The M1 parser and list Lambdas only read it, and
  the M1 notification Lambda writes only `notification_history`.
- All five M1 Lambdas share **one** role, `flight-lambda-role`. Its policy `flight-data` grants
  `PutItem`/`UpdateItem` on both `subscriptions` and `notification_history`. **Do not change
  that role:** removing write access would also break the notification Lambda's history writes.
  The M1 writer is retired by disabling the function itself (below). The new API has its own
  role, `flight-subscriptions-api-role` (contract §1).
- PITR on `subscriptions` is **DISABLED**, although ADR D11 requires it before any new write path.

#### Why the backfill must also change `updated_at`

The API treats a row as current only when **both** hold (`store.py` `token_current`):
`version_token` is set **and** `updated_at` matches `^\d{4}-\d\d-\d\dT\d\d:\d\d:\d\d\.\d{3}Z$`
(the M1.4 millisecond UTC stamp, `service.py` `_iso`). M1 rows carry second-precision `+00:00`
stamps, and some have no `updated_at`. A backfill that added only the token would leave every
row legacy, and `version_of` would still return `legacy-…`. The identical-content gap would stay
open, and refusing `legacy-` versions afterwards would make every M1 subscription impossible to
edit, pause or delete (`409`).

#### Conditional backfill (one `UpdateItem` per row)

1. **Rows:** every row where `token_current(row)` is false, read with a consistent read.
2. **Update:** `SET version_token = :tok, updated_at = :now`. `:tok` is
   `secrets.token_urlsafe(16)` (22 URL-safe characters, OS CSPRNG, matches the API's
   `VERSION_RE`), new for every row. `:now` is the current UTC time formatted by `_iso`. These
   are the **only** attributes that may change; `updated_at` is added where missing.
3. **Condition:** the API's own legacy guard (`store.guard(row)`): the row exists; every stored
   attribute equals the value read; and `attribute_not_exists(version_token)` for a row without
   a token, or the old token unchanged for a token row last written by M1. A concurrent write
   therefore makes the update fail (`ConditionalCheckFailed`) instead of being overwritten. The
   update is never unconditional.
4. **Idempotent:** a rerun selects only rows that are still not current.
5. **Recovering the originals:** the backfill overwrites only the old `updated_at` (and adds a
   token). The original values stay in the cutover backup (step 6 below) and in PITR. Read them
   from a restore into a separate table; a restore never overwrites `subscriptions`. No export
   containing user emails is committed to the repository.
6. **Code:** the backfill is B3 code. It needs review, tests on moto and DynamoDB Local, and its
   own approval to run.

#### Mandatory verification after the backfill

Reads for every check here and in steps 5 and 10:
- every read is a **full, paginated `Scan` with `ConsistentRead=true`**, continued until no
  `LastEvaluatedKey` remains;
- the comparison covers keys, every attribute, row counts per user and the expected version of
  each row.

A `Scan` is **not** a snapshot: it reads pages at different moments, so a write during a scan can
be partly seen or missed. Matching scans are therefore only supporting evidence. They never prove
on their own that nothing else wrote. That proof is the write-freeze verification (step 5):
write sources isolated and in-flight executions drained.


1. Every row has a `version_token` matching `^[A-Za-z0-9_-]{22}$`, and no two rows share a token.
2. Every row's `updated_at` matches the M1.4 stamp format above.
3. The API's `version_of(row)` for every row is the row's token: **no `legacy-` version remains**.
   This is checked with the deployed code against the scan, and through `GET /subscriptions` in
   step 10.
4. The set of keys (`email`, `route`) and the row count per user equal the cutover backup. Every
   attribute other than `version_token` and `updated_at` is byte-identical to the backup, read
   from a scratch restore.
5. No partial state: no row has a token without an M1.4 stamp, or the reverse, so every row
   satisfies `token_current`.

#### Prerequisites (B3 execution only; not done by this document)

1. PITR **enabled** on `subscriptions` and `notification_history` (D11), and checked:
   `DescribeContinuousBackups` reports ENABLED with an earliest restorable time.
2. An on-demand backup of `subscriptions`: status **AVAILABLE**, ARN recorded in the cutover log.
3. That backup **restored into an isolated scratch table**. The backfill is run there, every
   verification above passes there (including `version_of`), and then the scratch table is
   deleted.
4. Prepared and reviewed beforehand, without enabling them:
   - the `subscription_quota` table;
   - the `flight-subscriptions-api` function and its own role;
   - the route change sets for steps 9, 11 and 12;
   - the rollback commands.
5. Notification v2 and the fare check deployed first (release order below). They write nothing
   to `subscriptions`.
6. Throughout: EventBridge `flight-price-check` **DISABLED** and Resend in **testing mode** until
   separately authorised. No automatic production deployment, no step run without the owner's
   approval, and at no time two writers that can both accept subscription writes.

#### Cutover sequence (write-freeze boundary from step 3 to step 11)

1. **Backup and restore readiness:** prerequisites 1–3 done and recorded.
2. **Prepare and test the procedures:** prerequisite 4. Dry-run every command on the scratch
   copy, or in the B4-style isolated stack.
3. **Server-side write freeze:** set **reserved concurrency 0** on `flight-save-subscription`
   and record the exact time (T0).
   - This blocks **new** invocations only. It does **not** stop or cut short an execution that
     was already running at T0; those run to completion and may still write.
   - From T0, `POST /subscribe` returns an error (the Lambda throttle), and the `/app` page shows
     its generic error message.
   - **Subscription writes are unavailable during the freeze, by design.** They must not be
     redirected to, or silently accepted by, any other writer.
   - `GET /subscriptions` keeps working.
   - Announce the maintenance window to users beforehand.
4. **M1 writer retired:** with this architecture, the freeze in step 3 *is* the retirement. The
   function stays deployed but cannot run, so the freeze can be undone without a redeploy. The
   shared role is not touched.
5. **Write-freeze verification, all required before step 6:**
   - **Concurrency is exactly 0:** `GetFunctionConcurrency` returns
     `ReservedConcurrentExecutions = 0`.
   - **In-flight executions drained:**
     - read the function's configured `Timeout` and wait **at least that long after T0, plus a
       margin for metric delay** (CloudWatch Lambda metrics can arrive minutes late; use at
       least 5 minutes);
     - every log stream with a `START` before T0 shows its `END`/`REPORT`;
     - there is no `START` after T0;
     - no execution is still running.
   - **Metrics, once the delay has passed:**
     - `Invocations` for the function is 0 for every period after T0;
     - any attempts appear only as `Throttles`;
     - `ConcurrentExecutions` has fallen to 0.
   - **No other writer can modify `subscriptions`:**
     - the four other Lambdas on `flight-lambda-role` (list, parser, parser-wrapper,
       notification) run code with no write call to `subscriptions`, and their deployed
       `CodeSha256` equals the reviewed baseline;
     - EventBridge `flight-price-check` is DISABLED;
     - `flight-subscriptions-api` is not routed and not invoked;
     - no other role, user, tool, script or job (B5 tools included) writes to the table during the
       freeze;
     - the IAM principals allowed to write the table are listed, and each is accounted for.
   - **Supporting check only:** two full consistent scans after the drain, at least several
     minutes apart, are identical (keys, every attribute, counts). A difference stops the
     cutover; identical scans alone prove nothing (see the scan note above).
6. **Cutover backup:** only after step 5 passes, a new on-demand backup, status AVAILABLE, ARN
   recorded. This is the reference for the backfill comparison and for recovery. A scan just
   before the backfill must equal this backup (keys, attributes, counts, expected `legacy-`
   versions).
7. **Conditional backfill** as above.
8. **Verify** every check above. Anything failing → STOP (below); the freeze stays in place.
9. **API cutover, read-only first:** point **only** `GET /subscriptions` at
   `flight-subscriptions-api`. Its response is a superset of M1's, so `/app` keeps working.
   `POST /subscribe` stays on the frozen M1 function, and the four new routes stay unattached.
   No write path exists in this step.
10. **Verify the new API while writes stay frozen:** through real HTTP, `GET /subscriptions` for
    a canary user returns every row with a token `version`, never `legacy-…`. Logs show no
    errors, and the table scan is unchanged.
11. **Re-enable writes, rolling-only:** in one change set, point `POST /subscribe` at
    `flight-subscriptions-api` (the legacy path: quota-checked, rolling rows, writes tokens;
    contract §8.2). Then verify with the canary user: create, update, `limit_reached`, the quota
    record equal to the row count, and a token on every written row. The old function stays at
    concurrency 0, so only one writer ever exists. No fixed-month row can be created yet: the
    legacy path writes rolling rows only, and the routes that set a month are not attached.
12. **Fixed-month functionality:** only after step 11 is verified and separately approved,
    attach `POST /subscriptions`, `PATCH` and `DELETE /subscriptions/{id}`, then release the
    page (Phase 3B). This is the point of no clean return (B3 strategy item 3 below).

**Gate for refusing `legacy-` versions** (contract §4.5 step 4; its own reviewed code change and
approval, never part of steps 1–12). It may be enabled only when all of these hold:
1. Steps 1–12 are complete and verified, and writes have run on `flight-subscriptions-api` alone
   since step 11.
2. The M1 writer can never run again: still at concurrency 0 with no route, or deleted.
3. A fresh full consistent scan, taken immediately before enabling, shows **zero rows that are
   not token-current**. If any appears, the cause is found, the row is backfilled again with the
   same conditional update, and the scan is repeated.
4. A canary check on a migrated M1 row succeeds: list, then `PATCH` and `DELETE` with the
   returned (token) version.
5. No rollback or backup restore is in progress or planned: restored rows are legacy, and would
   need the legacy path back first.

No client can hold a pre-backfill `legacy-` version at that point. The API only became readable
at step 9, after the backfill, so no migrated user is locked out. Afterwards, delete the M1 save
Lambda in its own reviewed change.

**Difference from contract §8.3 as written before 2026-11-19 (explained, not silent):** §8.3
switched all routes in one change set. Doing that would accept writes, including fixed-month
writes, before steps 10–11 could be verified, and the API has no write-freeze or fixed-month
switch today. The staged route attachment above gives the same guarantee: the new write routes
are never reachable while the old writer can still run. It also keeps writes closed until the
backfill is verified. §8.3 is updated to match.

#### STOP conditions (stop, keep the freeze, report; no retry until the cause is understood)

- Reserved concurrency not exactly 0, an execution of `flight-save-subscription` still running or
  without `END`, or any `START` or `Invocations` after T0.
- Any sign of another writer (an unexpected principal, function, tool or job), or any write
  source that cannot be accounted for.
- Any unexplained difference between scans, between a scan and the cutover backup, or after step
  6 apart from the backfill's own changes. Stop immediately; do not re-scan until the scans happen
  to match.
- A backup that is not AVAILABLE, has no recorded ARN, or whose restore fails.
- Any `ConditionalCheckFailed` during the backfill. Under the freeze nothing else may write, so
  even one means an unexpected writer.
- Any backfill update that fails or keeps conflicting.
- Any row with a missing or malformed token, a duplicate token, or a non-M1.4 `updated_at`.
- Any `legacy-` version from `version_of` or from `GET /subscriptions`.
- Any difference in keys, row counts per user, or attributes other than the two migrated ones.
- Any failure of the step 10 or 11 verification, or any API error rate above zero for the canary.
- EventBridge not DISABLED, or Resend not in testing mode, at any step.

#### Rollback and its limits

- **Steps 3–6 (frozen, nothing migrated):** set the M1 function's concurrency back. This
  returns exactly to M1 and is safe.
- **After step 7, before step 11:**
  - Re-enabling the old writer is **not automatically safe**. M1 writes keep the old token but
    set a `+00:00` `updated_at`, so those rows turn legacy again. That stays data-safe only while
    the API still accepts `legacy-` versions, and the backfill must be redone before any later
    cutover.
  - Moving `GET /subscriptions` back to the M1 list Lambda is safe: it ignores the extra
    attribute and the stamp format. `updated_at` is display-only and unused by `/app`.
- **After step 11:**
  - Never re-enable the quota-unaware M1 writer next to the API: it bypasses the limit (§8.3)
    and makes quota records disagree with the rows.
  - Default: roll forward (fix and redeploy).
  - A real rollback first restores the freeze (API write routes detached), and checks
    consistency before writes are allowed again.
- **After `legacy-` versions are refused:** re-enabling the M1 writer would make every row it
  writes impossible to edit. Re-enable the legacy path first.
- **After step 12:** the §6 table applies. Only the whole set (D) can be rolled back, with users
  informed.
- **Restoring a backup** creates a new table and discards every write made after the backup.
  It needs every function repointed to that table, so it is acceptable only while the freeze is
  still in place (before step 11).
- **Every rollback** keeps or restores a write freeze until a consistency scan passes. Never
  roll back to a configuration where an M1 writer and the M1.4 API can both write.

### B3 — coordinated release and rollback strategy (recommendation; not implemented)

1. **Release order (forward):** notification v2 (accepts v1 and v2 messages) → fare check
   (emits v2) → subscriptions API, staged as in the cutover sequence above (writes frozen until
   the backfill is verified; rolling-only first; fixed-month routes last) → page. Each step is
   backward compatible with the previous one, and **no fixed-month row exists until the last
   two steps**, so steps 1–2 can be rolled back with no availability loss.
2. **Gate before the API step:** B4 Stage C re-run PASS (24 scenarios, 2 runs; met 2026-11-17, 48/48, B4 plan §7.11), the cutover blocker above done; EventBridge still
   DISABLED; Resend testing mode; one canary user.
3. **Point of no clean return:** the first fixed-month row. From then on, B and D lose alerts for
   those rows and A risks integrity. So after the API step, **rollback = roll forward** (fix and
   redeploy) by default; a real rollback must be the **whole set together** (D) with the
   fixed-month users informed, never the fare check or API alone.
4. **Kill switch instead of rollback:** keep `RECHECK_SUBSCRIPTION` on and add a
   create-fixed-month feature flag in the API (refuse new fixed-month creates with a clear
   message) — this stops the growth of the at-risk set without touching existing rows.
5. **Before any rollback:** snapshot counts (fixed-month rows, users affected), record Lambda
   `CodeSha256` and alias versions so each function is rolled back by alias, not by redeploy.
6. **Production deployment is not part of this PR.**
