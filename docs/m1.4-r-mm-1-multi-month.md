# M1.4 R-MM-1 — Several departure months per route

- **Status:** approved by the owner 2026-11-12; **implemented as code only** (this PR). Nothing
  deployed; no production table, Lambda, API Gateway, IAM, SSM or EventBridge change; no email.
- **Decision record:** [ADR 0001](adr/0001-m1-4-dynamic-routes.md) D1 as amended 2026-11-12.
- **Background audit:** [m1.4-same-route-multi-month.md](m1.4-same-route-multi-month.md).

## 1. Rules

1. A user can hold several **fixed-month** subscriptions of the same route:
   `KHH → TYO` for 2027-01, 2027-02 and 2027-03 are three independent subscriptions.
2. At most **one subscription per user, route and fixed month**.
3. **Legacy rolling** subscriptions (M1 rows, no month, always "next month") stay as they are:
   at most one per user and route, and they **can coexist** with fixed months of that route.
4. **10 records per user**, every row counted: each month is one record, paused and expired
   rows included. Only a delete frees a slot.
5. Changing a subscription's route **or month** moves it (one transaction, quota untouched).
   Moving onto an existing route/month is `409 duplicate_subscription`, never a merge.

## 2. Identity

| | Legacy rolling | Fixed month |
|---|---|---|
| DynamoDB partition key `email` | session email | session email |
| DynamoDB sort key `route` | `KHH-TYO` | `KHH-TYO#2027-01` |
| Public subscription ID (API paths, front end) | `KHH-TYO` | `KHH-TYO_2027-01` |
| `origin` / `destination` attributes | `KHH` / `TYO` (M1 rows: derived from the key) | `KHH` / `TYO` |
| `departure_month` attribute | absent | `2027-01` (always equal to the key's month) |
| API field `route` | `KHH-TYO` (the pair) | `KHH-TYO` (the pair) |
| API field `id` | `KHH-TYO` | `KHH-TYO_2027-01` |

- **Mapping:**
  - sort key ↔ ID is a pure character swap (`#` ↔ `_`);
  - both are pure functions of (origin, destination, month), via `subkeys.py` (three identical
    copies, kept identical by a test) and `src/lib/m14/subscription-id.ts`;
  - the shared vectors are in `aws/tests/vectors/subscription-ids.json`.
- **Why `_`:**
  - It is an unreserved URL character, so the ID never needs percent-encoding.
  - `#` would be read as a fragment and never reach the server.
  - It can't occur in a code or a month.
  - The regex `^[A-Z]{3}-[A-Z]{3}(_\d{4}-(0[1-9]|1[0-2]))?$` accepts nothing else; `KHH-TYO#…`,
    `%23` and `..` are all `400 invalid_route`.
- **Stability:** the ID changes only when the subscription's route or month changes (the API
  returns the new `id`; the front end uses it). Legacy IDs (`TPE-TYO`) are unchanged, so the old
  `{route}` paths keep working.
- **Authorisation:** every read and write uses the session's email as the partition key. An ID
  is only a sort key *inside the caller's partition*: knowing someone else's ID gives `404`.
  Tested.
- **Invariant I6:** the key's pair equals `origin`/`destination`, and a fixed key's month
  equals `departure_month`.
  - The fare check treats a row that breaks it as INVALID; it never guesses.
  - The B4 scenarios check it after every storm.
- **Rejected:** opaque UUIDs. They would need a lookup per request and a stored attribute, with
  no gain over a deterministic key that DynamoDB already enforces as unique.

## 4. Rolling/fixed overlap policy

**Overlap:** a user's rolling row and a fixed row of the same route resolve to the **same
effective month** (e.g. today, rolling `TPE-TYO` → 2026-12 and fixed `TPE-TYO#2026-12`).

**Unit of deduplication.** The notification stream is (user, route pair, effective month), as in
Phase 2B-1. Every subscription resolving to that stream shares it. Within a stream the M1 rule
applies: at most one alert per 24 h, unless the fare drops ≥ 20 % or ≥ NT$2,000. So two
overlapping subscriptions **never produce two emails for the same fare**. That is the
intentional policy, not a silent suppression: the email is about a route and month, and the
user gets it.

| Case | Behaviour | Tested in |
|---|---|---|
| a. Both eligible (active, target ≥ fare) | **One** message listing both keys; **one** email. The email shows the **lowest matched target** (the fare is at or below both, so this is the most informative true statement) | `test_a_both_eligible_one_message_listing_both`, `test_both_eligible_one_email` |
| b. Targets differ, the fare meets only one | The alert is for the one whose target is met, with its own target. **No suppression** by the other | `test_b_targets_differ_the_met_one_alerts` |
| c. Month end (Asia/Taipei midnight on the 1st) | The rolling row moves to the next month: it leaves the old stream (where the fixed row stays) and joins the next month's stream. All month rules use the scheduler's single `as_of`, so a run never mixes months. A fare event checked before midnight is still judged by its `as_of` month | `test_c_month_end_moves_only_the_rolling_row`, `test_month_end_rolling_row_starts_a_new_stream` |
| d. One of them paused or expired | Ignored: it neither alerts nor blocks the other. If the strictest one is paused **between the fare check and the send**, the email still goes out for the other, showing the other's target | `test_d_paused_or_expired_never_suppress_the_other`, `test_strictest_one_paused_since_the_check_still_sends_with_the_other_target` |
| e. Both paused/expired, or both targets no longer met at send time | Nothing sent, **nothing recorded** as sent | `test_all_listed_rows_ineligible_skips_and_records_nothing` |
| f. Two messages for one stream (e.g. an older fare check) | The second is deduplicated by the stream's M1 rule: one email, or a re-alert only on a real price drop | `test_second_message_for_the_same_stream_is_deduped` |
| g. Different months of one route | Independent streams: each month alerts on its own | `test_other_months_of_the_route_are_independent_streams` |

**Send-time behaviour, end to end** (`OverlapFlowTests` in `aws/tests/test_m14_multi_month.py`:
real fare-check runner → v2 message → notification service on a moto table, with a fake Resend):

| Situation between fare check and send | Result |
|---|---|
| Different targets, only one met | one email, that subscription's target |
| Both met | one email, lowest target, one history row for the stream |
| One paused / one deleted | one email, the other's target |
| Both paused/deleted | nothing sent, nothing recorded (`skipped:paused+subscription_gone`) |
| Shown target lowered / raised | lowered below the fare → the other's target; raised → the lowest target that is still met (never a target the fare doesn't meet) |
| Same fare event delivered again | `skipped:duplicate_event`, no second send |
| Next scheduled run, same fare / small drop / ≥ 20 % drop | deduplicated / deduplicated / re-alert (M1 rule unchanged) |
| Resend outcome uncertain (timeout or lost response), then retry | **same Idempotency-Key and same body** → Resend deduplicates; exactly one delivery |

**Fix made in this review — stable retry payload.** The email shows the lowest *still-eligible*
target, re-read at send time. Before this fix, a retry after an uncertain Resend outcome
re-read the rows again: if the user had paused one subscription or changed a target in between,
the retry carried a **different body under the same Idempotency-Key**. Resend rejects that
(`409 invalid_idempotent_request`), and the message would end in the DLQ — no duplicate email,
but an alert could be lost. Also, the search links were dated from the send time rather than the
fare event. Now:
- the presented target is **pinned to the claim** on the first attempt
  (`history.pin_target`: `SET claim_target = :t, claim_target_event = :e` only while
  `claim_event = :e` and this event has not pinned yet; otherwise its earlier pin is read back), and every retry of
  that claim reuses it. A pin left by another event whose claim expired and was taken over is
  never reused (`test_a_taken_over_claim_never_reuses_another_events_pinned_target`). Both
  attributes are removed when the claim is committed or released;
- links are built from the message's `as_of`, not from "now".

So the key (`flight-fare/{event id}`) and the rendered body are functions of the fare event
alone. A test proves the retry is refused without the pin (`test_without_the_pin_the_retry_would_be_refused`).

**At most one email — argument.** (1) The fare check emits one message per user per work item,
listing all overlapping keys (no second message for the overlap). (2) Every message for the
stream (user, pair, month) takes the stream's single claim; a second message is deduplicated by
the M1 rule or by the event id. (3) Each send uses `flight-fare/{event id}` with a body fixed by
the claim, so Resend delivers it at most once whatever the retries. (4) Pausing, deleting or
editing can only *remove* eligibility; nothing re-opens a committed stream except the M1 price-
drop rule. `test_at_most_one_email_for_every_state_combination` checks all 225 combinations of
{active, paused, deleted, target lowered, target raised} × the same for the second row × three
fares: never more than one delivery, and a delivery exactly when at least one row is still
eligible. M1 safeguards (24 h floor, 20 % / NT$2,000 re-alert, `{email}#{route}` dual-write,
EventBridge DISABLED, Resend testing mode) are unchanged.

The page states it in plain words: 「同一航線可以分別追蹤不同的出發月份，每個月份各算 1 筆訂閱。
舊版「每月滾動」的訂閱若與某個月份的訂閱查詢同一個月，同一天最多寄出一封通知。」

| What | Effect |
|---|---|
| Existing M1 rows (`TPE-TYO`, `TPE-SEL`, no month) | **Untouched.** Same key, same ID, still rolling. No data migration. Choosing a month moves the row to `TPE-TYO#YYYY-MM` only when the user does it |
| Phase 1B rows | None exist (never deployed). A hypothetical row with a plain key *and* a month still reads correctly and is moved to the composite key on its next month or route edit |
| `notification_history` (M1 rows `{email}#{route}`, v2 streams) | Unchanged. Stream keys use the pair and month as before |
| Deployed M1 parser / notification / list / save Lambdas | Unchanged and **unaware of fixed-month keys** (they look for `route = "ORIG-DEST"`). Fixed-month rows only ever exist after the M1.4 API is deployed (B3), at which point the fare check replaces the M1 parser |
| v1 fare-check messages (M1 notification Lambda) | Same M1 shape key for key; now one per user and item (the M1 notification dedups by `{email}#{route}` anyway) |
| API clients using `{route}` paths for M1 rows | Still work (same value); the `{route}` path parameter name is still accepted |
| M1 production front end (`/app`) | Unchanged (it uses the deployed M1 list Lambda) |

## 6. Rollback risks

Two different questions for every rollback: **data integrity** (can a row, quota or history
record become wrong?) and **availability of price tracking** (does every subscription the user
sees on the page still get alerts?). A rollback is only **service-safe** when both hold.

| | Rollback | Data integrity | Price-tracking availability | Verdict |
|---|---|---|---|---|
| A | **Subscriptions API only** (back to the pre-R-MM-1 M1.4 API) | Safe: no row is rewritten. But the old API's `route_param` rejects `ORIG-DEST_YYYY-MM` IDs, so existing fixed-month rows **cannot be edited, paused or deleted** while they keep counting toward the quota (a user with 10 such rows is stuck at the limit). The old create path writes plain `ORIG-DEST` keys with a month — a second representation of the same route/month beside an existing `#YYYY-MM` row, which the new code then sees as two rows (I7 violation) | Fare check (still new) keeps alerting all rows | **Not service-safe** — integrity risk from new writes, users lose control of their rows. Only acceptable with writes blocked (read-only page) until roll-forward |
| B | **Fare-check Lambda only** (back to the M1 parser) | Safe: the fare check writes nothing to subscriptions | **Every fixed-month subscription stops getting alerts** (the M1 parser reads only `route = "ORIG-DEST"`); rolling rows keep working. Silent from the user's point of view | **Not service-safe.** Integrity-safe only. Must be announced or kept short; roll forward to restore |
| C | **Notification Lambda only** (v2 → M1 notification) | Safe: v2 dual-writes the M1 history key `{email}#{route}`, so M1 dedups correctly against what v2 sent; nothing in subscriptions is written | Alerts continue for rolling and fixed rows, but with M1's rules: **no send-time re-check at all** (a row paused or deleted after the fare check can still trigger that one email — as in M1 today), no pinned target, and dedup **per route, not per month**: an alert for one month suppresses alerts for the route's other months for 24 h unless the price drops ≥ 20 % / NT$2,000 | **Degraded, not service-safe**: no data damage and no duplicate within 24 h, but some month alerts are suppressed and the pause/delete guarantee is lost. Short-term only |
| D | **Complete M1.4 stack** (API + fare check + notification + page back to M1) | Safe for the stored data (no migration to undo; PITR is the backstop, D11). `subscription_quota` is left orphaned (harmless, unread by M1) | **All fixed-month subscriptions lose alerts and disappear from the page** (the M1 list Lambda only knows rolling rows); M1 rolling rows work exactly as before | **Not service-safe** for users with fixed-month rows. Integrity-safe. Before rolling back: count fixed-month rows; if > 0, notify those users or keep alerts running |

Front end only (Phase 3A mock) is preview-only and harmless. No rollback can make a key change
half-done: every key change is one transaction (s18, s22–s24).

### B3 — coordinated release and rollback strategy (recommendation; not implemented)

1. **Release order (forward):** notification v2 (accepts v1 and v2 messages) → fare check
   (emits v2) → subscriptions API (creates the first fixed-month rows) → page. Each step is
   backward compatible with the previous one, and **no fixed-month row exists until the last
   two steps**, so steps 1–2 can be rolled back with no availability loss.
2. **Gate before the API step:** B4 Stage C re-run PASS (24 scenarios, 2 runs); EventBridge still
   DISABLED; Resend testing mode; one canary user.
3. **Point of no clean return:** the first fixed-month row. From then on, B and D lose alerts for
   those rows and A risks integrity. So after the API step, **rollback = roll forward** (fix and
   redeploy) by default; a real rollback must be the **whole set together** (D) with the
   fixed-month users informed, never the fare check or API alone.
4. **Kill switch instead of rollback:** keep `RECHECK_SUBSCRIPTION` on and add a
   create-fixed-month feature flag in the API (refuse new fixed-month creates with a clear
   message) — this stops the growth of the at-risk set without touching existing rows.
5. **Before any rollback:** snapshot counts (fixed-month rows, users affected), record Lambda
   `CodeSha256` and alias versions so each function is rolled back by alias, not by redeploy.
6. **Production deployment is not part of this PR.**

## 7. B4 — updated requirements and real-DynamoDB test plan

**Not executed against AWS** (needs the owner's separate approval). Offline evidence in this PR:
- the 24 scenarios pass on moto's DynamoDB-compatible server
  (`aws/tests/test_m14_ddb_scenarios.py`);
- the subscriptions API suite covers multi-month CRUD, key-change transactions and 2 extra
  50/60-request storms.

**Scenarios.**
- s01–s15 are updated to the new keys with their original checks. Two were reviewed in detail
  (final review, 2026-11-12):
  - **s09** (edits, pauses and creates at 10) is **back to its original strict form**: in-place
    edits (target, and the unchanged month) race pauses and creates; only `200`/`409` are
    accepted, never `404`; additionally every row must stay at its key, the quota version stays
    10 and no edit or pause uses a transaction. An earlier revision of this PR had moved those
    edits to another month and accepted `404` for all 40 requests — a month edit now moves the
    row to a new key, so a later request on the old ID legitimately gets `404`, but accepting it
    blanket also hid a pause that 404s on a row that never moved. That racing case now has its
    own scenario, **s22**, where a `404` is accepted only for a request whose row was actually
    moved.
  - **s15** (same-row storm) still checks I3 exactly as before: quota version = baseline +
    committed **count-changing** transactions. Before R-MM-1 every committed transaction in s15
    was count-changing (creates, deletes, legacy creates), so "all commits" and "count-changing
    commits" were the same number. A month edit is now a key-change transaction that must **not**
    move the version, so counting it would make a correct implementation fail. The scenario now
    checks both halves separately and more strictly than before: key-change commits = successful
    month moves; rows = 6 + count-changing commits − 2 × deletes (exact, previously a range);
    the rolling row moved at most once and its new row carries `previous_route`; the fixed
    month created at most once.
- New:

| ID | What | Pass criteria |
|---|---|---|
| s16 | 60 creates of one route across all 12 months (5 per month), from empty | each month at most once; ≤ 10 rows; rows = 201 responses; version = creates; then exactly 10 |
| s17 | 60 creates of one route/month beside two existing months | exactly one 201; siblings untouched; version 3 |
| s18 | 60 month changes (5 rows × 12) onto two target months | 5 rows; no two rows share a month; moved rows = 200s; quota record unchanged |
| s19 | deletes, edits, moves onto a just-deleted month, and creates of sibling months at 10 | ≤ 1 delete and ≤ 1 move succeed; creates ≤ freed slots; edited sibling survives; version = 10 + deletes + creates |
| s20 | M1 user: creates of the rolling row's month and the next, legacy upserts, moves of the rolling row onto that month | fixed month at most once; rolling row moved at most once and never merged into an existing month; other M1 row unchanged; version = count-changing commits |
| s21 | 60 mixed creates (two routes × months), deletes, month changes and route changes | version = 4 + count-changing commits; rows = 4 − deletes + creates; no row moved twice |
| s22 | at 10: 20 pauses + 20 month moves (each row to two different months) + 20 creates | each route exactly once at old or one new month; moves = 200s per row; `404` only on a moved row; provenance kept; version 10 |
| s23 | 30 moves and 30 deletes of the same row beside 4 sibling months | ≤ 1 move, ≤ 1 delete; never at both keys; rows = 5 − deletes; version = 5 + deletes |
| s24 | key-change transactions cancelled (injected and real: move onto an occupied month; stale `updated_at`) | `409`, nothing written, concurrent pause kept, quota unchanged; a later move works and leaves count and version unchanged |

All scenarios also check:
- **I1:** at most 10 rows per user;
- **I2:** the quota count equals the rows;
- **I3:** the quota version equals the committed count-changing transactions;
- **I4:** every row is complete and comes from the seed or a successful response;
- **I5:** another user's rows and quota are byte-identical before and after;
- **I6 (new):** the key agrees with the stored route and month;
- **I7 (new):** no two rows share (origin, destination, departure month) — checked on the stored
  attributes, independently of how keys are built (so also at most one rolling row per route).

Mutation check of the key-change protocol (in-process patches of `Store.change_route`): a
non-atomic move, a move whose Put is unconditional, a move whose Delete skips the `updated_at`
guard, and a move that touches the quota are **each caught deterministically by s24** and also
by s18/s22/s23 under concurrency.
