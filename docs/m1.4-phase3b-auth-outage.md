# M1.4 Phase 3B-E — Supabase outage handling in the subscriptions API

**Before:** `subsapi/auth.py` turned *any* failure to reach Supabase (`except Exception`) into
"no user". A Supabase outage, timeout or rate limit therefore reached signed-in users as
`401 unauthorized`, and the page told them their session had expired.

**Now:** Supabase's answer is classified (full table in
[`docs/api/m1.4-subscriptions-api.md` §2](api/m1.4-subscriptions-api.md#2-authentication)):

- **`401 unauthorized`:** a definitely invalid session (no token, Supabase `400/401/403`, or no
  email).
- **`503 auth_unavailable`:** Supabase could not confirm the session right now (`408/429/5xx`,
  timeout, DNS, TLS, connection failure, unreadable answer, a redirect, or an unexpected
  status), with `Retry-After: 5`.
- **`500 internal_error`:** missing configuration or a programming error. There is no catch-all.

**Redirects are never followed.** urllib's default opener follows `301/302/303/307/308` and
resends the request's headers, which here are the user's bearer token and the publishable key,
to the new destination, even when it is plain HTTP. If that destination answered with another
email, the API would act as that user. The request now uses an opener whose redirect handler
refuses every redirect (`_NoRedirect` in `subsapi/auth.py`); the 3xx becomes `503` (reason
`redirect`). The HTTPS handler is the standard one, so certificate and hostname verification are
unchanged.

In every non-success case the function makes **no DynamoDB call** and never falls back to a
test or request-body identity. Logs carry only a fixed reason label, never the token, the email
or Supabase's response text.

**Unchanged:**
- the identity model (the email from Supabase);
- the direct test-invocation safeguards;
- cross-user isolation and transaction logic;
- CORS ownership (API Gateway; the function sets no CORS headers);
- the front end;
- the production M1 Lambdas (`flight-save-subscription`, `flight-list-subscriptions`).

## How the page behaves
The front end already maps every `503` to `service_unavailable`:
- **Loading the list:** shows "訂閱服務暫時無法使用，請稍後重新整理頁面確認最新狀態後再試。"
  with a retry button, not "登入已過期".
- **Writes:** show the cautious "may or may not have been saved" message and reload the list
  once, even though an `auth_unavailable` write is known not to have run. A clearer message
  would need a front-end change, which is out of scope here.

## Email confirmation: UNVERIFIED (prerequisite before production notifications)
- **The setting couldn't be read in Phase 3B-E.** The read-only database query was refused,
  and the Supabase auth settings endpoint isn't reachable from the build environment. The
  README says confirmation "can be disabled for simplicity in this v1".
- **The API does not check `email_confirmed_at`.** This phase deliberately doesn't add that
  check.
- **Why it matters:** if confirmation is off, anyone can sign up with someone else's address and
  create subscriptions under it. Once notifications are on, fare emails would then go to that
  address.
- **Before production notifications (EventBridge/Resend) are enabled:** the owner checks
  Supabase → Authentication → Email → "Confirm email" and decides whether to enforce it. A
  backend check on `email_confirmed_at` only helps when confirmation is on, because when it is
  off Supabase marks every address as confirmed at sign-up.
