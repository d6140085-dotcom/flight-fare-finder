# M1.4 — Same route, several departure months: audit and integration requirement

- **Status:** audit only (2026-11-11). **Nothing changed** in the API, the DynamoDB schema or any
  deployed resource. Needs an owner decision before Phase 3B.
- **Question:** can one user hold `KHH-TYO 2027-01`, `KHH-TYO 2027-02` and `KHH-TYO 2027-03` as
  three independent subscriptions, each counting toward the limit of 10?
- **Answer today: no.** It is a deliberate decision in the current design, not a front-end
  limitation, so it can't be fixed in PR #19 alone.

## 1. Findings

| Item | Current design | Where |
|---|---|---|
| Primary key | `subscriptions`: partition `email`, sort **`route`** (`"ORIG-DEST"`). The sort-key attribute is itself named `route` | ADR 0001 D1; `aws/lambdas/flight-subscriptions-api/subsapi/store.py` |
| Route uniqueness | **One subscription per user per route pair, whatever the month.** Creating the same route with another month → `409 duplicate_subscription` (a `Put` with `attribute_not_exists`) | ADR D1 ("a different month is not a second subscription"); API contract §3.2, §4.2 step 7 |
| PATCH/DELETE identity | `PATCH /subscriptions/{route}` and `DELETE /subscriptions/{route}`, `{route}` = `^[A-Z]{3}-[A-Z]{3}$` | API contract §4.3, §4.4 |
| Month changes | An `UpdateItem` on the same key. A route change is a transaction: `Delete` old + `Put` new | ADR D5 |
| Route/month composite identity | **Not supported.** Considered and **rejected** in ADR 0001 ("Departure month in the sort key … changes the dedup key and needs a migration. Rejected; one month per route pair") | ADR 0001, Alternatives |
| Legacy rolling rows | M1 rows (`TPE-TYO`, `TPE-SEL`) have no `departure_month` and stay rolling. Because the key is the route, a rolling row and a fixed row for the same route can't coexist | API contract §3.2, §8.1 |
| Mock client (PR #19) | Enforces one route per user, **matching the real contract**. Changing it alone would make the preview promise something the API refuses | `src/lib/m14/mock-client.ts` |

### Who else depends on `route` being the plain pair

| Component | Dependency | Effect of a composite sort key |
|---|---|---|
| **Deployed M1 parser** (`flight-parser`) | `Scan` with `route = "ORIG-DEST"` | Rows with a composite key are never matched. This is safe (M1 can't honour months), but those subscriptions get **no alerts on rollback to M1** |
| **Deployed M1 list Lambda** (`flight-list-subscriptions`) | Returns `route` as-is | `/app` maps rows by `route` to the two M1 plans, so extra rows are ignored. Harmless but untidy |
| **Deployed M1 save Lambda** (`flight-save-subscription`) | Upserts `{email, route}` for the two plans | Unaffected while plan rows keep the plain key |
| Phase 2A fare check (`farecheck/effects.py`, `matching.py`) | `rows_for_route` scans `route = :r`, then matches on effective month | Must match on `origin` + `destination` (or a `route_pair` attribute) instead of the sort key |
| Phase 2B-1 notification v2 (`notify2/service.py` `recheck`) | `GetItem(Key={email, route})`, then checks the month (`month_changed`) | Needs the subscription's own key in the SQS message |
| Phase 2B-1 dedup | Streams `v2#{subscriber}#{route}#{month}` | **Already month-aware: no change.** Each month is its own stream. Two rows resolving to the same (route, month) share one stream, so they never send twice |
| M1 history rows `{email}#{route}` | Read as "covers every month of the route" for up to 24 h | Unchanged |
| Quota (`subscription_quota`) | Counts rows; create/delete transactions on `{email, route}` | Count semantics unchanged (each month is one record). The duplicate condition and the transaction keys change |
| **B4 atomic tests** (`aws/integration/m14_scenarios.py`, s01–s15) | Validated on the current key shape | s04 (same route) changes meaning; s07/s08 (route edits) and s15 (same-row storm) involve the key. **B4 must be re-run** (moto, DynamoDB Local, Stage C) for any key change. Today's PASS doesn't carry over |

## 2. Options

| | A. Keep one month per route (current) | B. Composite sort key in the same table (recommended if the feature is wanted) | C. New table with a subscription id |
|---|---|---|---|
| Identity | `route` | Fixed rows: `route = "ORIG-DEST#YYYY-MM"`. Legacy rolling rows keep `"ORIG-DEST"` | `sub_id` (opaque), plus `origin`, `destination`, `departure_month` |
| Migration | None | **None for existing data**: only M1 rows exist and they keep their keys; Phase 1B rows have never been written (not deployed) | Copy every row; dual-read/write during the switch |
| Readers to change | — | Fare check (match on attributes), notification v2 recheck (message carries the key), API, front end | Every reader and writer, including the M1 Lambdas' replacements |
| Rollback to M1 | Clean | M1 ignores fixed rows: no alerts for them until roll-forward; M1 rows unaffected | M1 table frozen at the switch; new subscriptions invisible to M1 |
| Risk | Lowest | Moderate (contained, testable) | Highest |

## 3. Recommendation

1. **Ship PR #19 with the current rule** (one departure month per route). The mock matches the
   contract, and the page now says so: 「每條航線目前只能追蹤一個出發月份；想改月份，請編輯既有的訂閱。」
2. **If several months per route is wanted, choose option B as one explicit change** before the
   Phase 3B cutover, while no Phase 1B row exists yet. That avoids any data migration.
   - The owner should amend ADR 0001 D1 first (it currently rejects this).
3. **Integration requirement R-MM-1** (Phase 1B API + Phase 2A fare check + Phase 2B-1
   notification + Phase 3B front end, one change set):
   - **Identity**
     - Sort key `route`: `"ORIG-DEST"` for legacy rolling rows (unchanged); `"ORIG-DEST#YYYY-MM"`
       for fixed-month rows.
     - New stored attributes on every new row: `origin`, `destination`, `route_pair`
       (`"ORIG-DEST"`).
   - **API**
     - Each subscription gets an `id` (= sort key).
     - `PATCH`/`DELETE /subscriptions/{id}` with `{id}` URL-encoded; accept
       `^[A-Z]{3}-[A-Z]{3}(#\d{4}-\d{2})?$`.
     - Keep `route` in responses as the pair, for display.
   - **Uniqueness**
     - At most one row per (route pair, month), plus at most one rolling row per route pair.
     - A rolling row and a fixed row for the same pair may coexist. When the rolling row's
       effective month equals a fixed month, v2 dedup sends at most one email for that stream.
     - `409 duplicate_subscription` only for the same (pair, month).
   - **Month change**
     - On a fixed row it changes the key: a transaction (`Delete` old + `Put` new, as a route
       change today) with no quota change.
     - A rolling → fixed change likewise.
   - **Quota:** unchanged (every row counts, only delete frees a slot).
   - **Fare check:** select rows by `route_pair` (legacy rows: derive it from the key) and
     effective month.
   - **Notification:** the message carries `subscription_id`; `recheck` reads that key.
     Stream keys are unchanged.
   - **Tests:** re-run B4 Stages A–C with new scenarios: three months of one pair created
     concurrently; a month change onto an existing (pair, month); rolling + fixed on one pair.
     Update the dedup tests and the front-end mock.
   - **Rollback:** document that M1 ignores fixed-month rows; nothing else changes for M1 users.
4. **Don't** reuse the current route-only `PATCH`/`DELETE` paths for composite rows, and **don't**
   change keys in a deployed table without the B4 re-run.
