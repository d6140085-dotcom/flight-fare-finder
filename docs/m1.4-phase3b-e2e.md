# M1.4 Phase 3B-D — Playwright end-to-end tests and automatic CI

```
Chromium ─► Vite dev server (127.0.0.1:5173, local HTTP mode) ─► HttpSubscriptionsClient
        ─► Phase 3B-B harness (127.0.0.1) ─► real Lambda handler ─► DynamoDB Local (CI)
```

## Run locally

```bash
pip install --require-hashes -r aws/requirements-test.lock     # Python 3.12 test deps (hashed)
bun install --frozen-lockfile && bunx playwright install chromium
bun run test:e2e              # 24 browser tests (moto unless DDB_ENDPOINT points at DynamoDB Local)
bun run test:e2e:isolation    # production + preview builds with every HTTP-mode variable set
```

`e2e/global-setup.ts` starts the harness and the dev server with a minimal environment: fake
AWS keys, no proxies, and Supabase and the M1 API pointed at placeholders that never resolve.
Every test then starts from empty test tables and a fixed clock (`2026-11-05T03:00:00Z`). The
suite runs with one worker and **no retries**.

## What is covered

| File | Scenarios |
|---|---|
| `auth-outage.spec.ts` (3B-E) | the backend's session check fails while the browser session is fine: on load the page shows "訂閱服務暫時無法使用" with a retry button, not "登入已過期", and the session stays; an edit (Supabase `503`), a delete (connection reset) and a create (timeout) write nothing, are not replayed, reload once and keep the input; every such request made **no DynamoDB call**. A session Supabase rejects (`401`) is still a sign-in problem, with no automatic retry. |
| `auth.spec.ts` | `/app/subscriptions` through the app's **real** guard (`appLoader` → `supabase.auth.getUser()`): unauthenticated → `/signin`; valid fake session → the page; expired (refresh refused) and revoked (401) sessions → `/signin`. The API sees only the dev token, never the session. |
| `lifecycle.spec.ts` | list → create → price → pause → resume → month move (new ID) → route move (new ID) → delete. Each step is checked in the UI **and** in the stored records; every returned version equals the stored version. |
| `rules.spec.ts` | three months on one route; duplicates refused (by the page, and by the server for one created in another tab); 10 rows max with paused, expired and legacy rolling rows counted and labelled; quota record = rows; the form offers exactly the server's selectable months. |
| `concurrency.spec.ts` | two tabs read version V1; tab A writes; tab B's stale PATCH, then stale DELETE, get `409`. Tab B reloads exactly once and never resends; A's change stays and the unrelated row is untouched. |
| `uncertain.spec.ts` | `503`/`504`, a network cut before the backend, and **response loss after a committed write** (PATCH and create): one reload, input kept, no replay. Also `429` without retry, and double clicks. |
| `cors.spec.ts` | real Chromium CORS from an allowed origin (PATCH and DELETE preflights, readable `401`/`404`/`409`/`503`, origin echoed and never `*`) and a disallowed origin (writes never sent; a simple GET's response is hidden). |
| `isolation.spec.ts` | production builds have no M1.4 page; preview builds show only the mock. Neither sends a request to the harness URL, a dev token or any API call. |

**Post-commit response loss** works like this:
1. Playwright forwards Chromium's own request to the backend (`route.fetch`).
2. It checks the stored records, which show the write committed (the barrier).
3. Only then does it cut the connection (`route.abort`).

The page therefore never sees the success response. The harness request counters confirm that the
write reached the backend exactly once.

**CORS method note:** while Playwright request interception (`route`) is active, Playwright
answers CORS preflights itself. The CORS tests therefore use browser contexts **without
interception**, with both origins served by real local servers (the dev server and a small server
on `127.0.0.1:5199`). The other specs use interception to block every non-local host and to stand
in for Supabase, so they don't assert on CORS.

**Fake authentication** checks that the app handles sessions correctly. It does **not** show that
production Supabase authentication behaves the same way: there the API verifies a real Supabase
session, whereas here it accepts the harness's fixed dev token.

## Automatic CI (`.github/workflows/ci.yml`)

**When it runs:** on pull requests to `main`, on pushes to `main`, and by manual dispatch (for
re-runs on the same commit).

**Locked down:**
- `permissions: contents: read`; no secrets, no `id-token`, no AWS actions and no deploy steps;
  `pull_request` only, never `pull_request_target`;
- checkout without persisted credentials;
- AWS keys are the fake value `testing`.

**Pinned inputs:**
- actions pinned to commit SHAs;
- DynamoDB Local pinned by image digest;
- `bun install --frozen-lockfile`;
- Python test dependencies pinned with hashes (`aws/requirements-test.lock`, generated for Python
  3.12 / Linux with `uv pip compile --generate-hashes`);
- Playwright pinned in `bun.lock`.

| Job | What |
|---|---|
| A | the full Python suite (moto) |
| B | `tsc` (app and e2e), Vitest, and the ESLint regression check |
| C | API, B4 scenarios, shared contract and harness tests on **DynamoDB Local**, plus the real-HTTP client tests |
| D | Playwright end-to-end tests on **DynamoDB Local** |
| E | bundle scans, plus production and preview builds checked in Chromium |

**ESLint regression check** (`scripts/eslint-regression.mjs`):
- It compares findings one by one against `scripts/eslint-baseline.json`, which was generated from
  `main` at 103 errors / 7 warnings.
- Each finding is fingerprinted by file, rule, severity, source line and message, and duplicates
  are counted. A new finding therefore fails the check even if old ones disappear at the same time.
- Refresh the baseline with `--update`, only in a reviewed PR.
