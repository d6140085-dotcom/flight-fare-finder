## 6. Remaining concurrency risks

1. **Liveness under extreme contention:** with ≤ 3 attempts, many simultaneous requests from one
   user end in `409 conflict` (nothing written). Safe, but the UI should retry or ask the user
   to retry. Not expected from real users; measured in s02/s05/s12.
2. **Query isolation:** DynamoDB documents `Query` as read-committed with respect to
   transactions. The protocol relies on the quota `GetItem` (serialisable) being read first;
   s02/s03/s12 on real DynamoDB are the evidence that the count is never stale at commit.
3. **Idempotency window:** `ClientRequestToken` is honoured for 10 minutes; each application
   attempt uses a fresh token, so a replay can only come from the SDK's own retry of the same call.
4. **Clock skew between Lambda instances:** `updated_at` is always made strictly greater than the
   stored value, so skew can't make a stale token match; it only affects displayed times.
5. **Hot quota item per user:** all count-changing writes for one user serialise on one item —
   by design; far below per-item throughput limits at realistic request rates.
6. **Pre-cutover legacy writer:** the deployed M1.1 `POST /subscribe` Lambda does not use the
   quota. Safe only while no new route is reachable; the cutover must switch both together (B3).
7. **Emulator gaps:** moto and DynamoDB Local don't reproduce DynamoDB's internal transaction
   conflicts or idempotency replay exactly — the reason stage C exists.
