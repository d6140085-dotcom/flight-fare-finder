### What PR #12 changed

- `Store.update` now maps `TransactionConflictException` to a `WriteConflict` error instead of
  letting it escape as a 500. Raised `TransactionConflictException` on a transaction is treated
  like a cancelled transaction; `TransactionInProgressException` becomes a non-retryable
  `WriteConflict` (the earlier attempt may still commit).
- Legacy `POST /subscribe` re-reads and retries within the same ≤ 3 attempts and bounded
  jittered backoff, then answers `409 conflict`. Its update is conditioned on the `updated_at`
  it read, so a retry never overwrites a change it hasn't seen.
- `PATCH` answers `409 conflict` without retrying (the client reloads).
- Any other unexpected error is still a 500, now logged with the exception type and AWS error
  code.
- Test harness: an unexpected exception is recorded as a 500 response so the scenario still
  checks integrity and fails visibly; new scenario **s15** (same-row write storm); offline
  regression tests inject `TransactionConflictException` every third `UpdateItem`.

## 6. Remaining concurrency risks

1. **Liveness under extreme contention:** with ≤ 3 attempts, many simultaneous requests from one
   user end in `409 conflict` (nothing written). Safe, but the UI should retry or ask the user
   to retry. Not expected from real users; measured in s02/s05/s12.
2. **Query isolation:** DynamoDB documents `Query` as read-committed with respect to
   transactions. The protocol relies on the quota `GetItem` (serialisable) being read first;
   s02/s03/s12 on real DynamoDB are the evidence that the count is never stale at commit.
3. **Idempotency window:** `ClientRequestToken` is honoured for 10 minutes; each application
   attempt uses a fresh token, so a replay can only come from the SDK's own retry of the same call.
4. **Clock skew between Lambda instances:** `updated_at` is always made strictly greater than the
   stored value, so skew can't make a stale token match; it only affects displayed times.
5. **Hot quota item per user:** all count-changing writes for one user serialise on one item —
   by design; far below per-item throughput limits at realistic request rates.
6. **Pre-cutover legacy writer:** the deployed M1.1 `POST /subscribe` Lambda does not use the
   quota. Safe only while no new route is reachable; the cutover must switch both together (B3).
7. **Emulator gaps:** moto and DynamoDB Local don't reproduce DynamoDB's internal transaction
   conflicts or idempotency replay exactly — the reason stage C exists.

### 7.9 Stage B 2026-11-13 — s19 failure and the DELETE ID-reuse fix

- Stage B on `main` `c6b4b47` (run 43352824588): 131/132 tests, 23/24 scenarios; **s19 failed**
  (two `204` for deletes of `KHH-TYO_2027-01`).
- Cause: s19's deletes carried no `if_updated_at`, and a version-less DELETE re-read "whatever is
  at the ID" on every internal retry. After A was deleted and B moved into A's ID, a request that
  had been aimed at A could delete B (ABA). Invariants I1–I7 still held — the data stayed
  consistent — but the wrong subscription was removed.
- First fix (superseded the same day, before merge): bind every DELETE to one `updated_at`.
  Rejected: timestamps cannot identify a subscription (two writes can share a millisecond; the
  timestamp-only version deletes B when A and B have identical `updated_at`).
- **Final fix (PR #22): random row versions.** Every row carries `version_token` (128 random
  bits, new on every change); PATCH and DELETE require `if_version`, checked atomically in the
  conditional write; no version-less or re-read fallback. Legacy M1 rows use an all-attribute
  guard and a `legacy-` version (API contract §4.5, with the one documented limitation and the
  B3 migration that closes it). s19 sends A's version; the `RowVersionAba` tests (11) run on moto
  and DynamoDB Local. The CloudFormation template is unchanged; the runner ZIP changes.
