# M1.4 B5 — live Travelpayouts v1/v3 comparison plan (read-only)

- **Status:** plan only, 2026-11-09. **No live call has been made.** Running it needs the
  owner's separate approval.
- **Closes:** release blocker B5 (Travelpayouts API compatibility,
  [plan](m1.4-plan.md#m14-release-blockers)), together with the offline evidence in PR #15
  (`aws/lambdas/flight-fare-check/`, `aws/tests/test_m14_fare_check.py`).
- **Question to answer:** with the Phase 2A validation applied, does v3
  `/aviasales/v3/prices_for_dates` find valid round-trip TWD fares at least as often as v1
  `/v1/prices/cheap`, at comparable prices, and what do real responses contain (currency, dates,
  airports, missing data)?

## 1. Safety boundaries

| Must not | How the plan guarantees it |
|---|---|
| Deploy anything to AWS, update a production Lambda, change EventBridge | Runs as a local command-line tool on the owner's computer; touches no AWS API at all |
| Write DynamoDB, read subscriber data | Uses a fixed route list (§3), not the `subscriptions` table; no AWS credentials needed |
| Send SQS messages or emails | The tool has no matching step and no SQS/SES code; it only calls Travelpayouts and writes local files |
| Expose secrets | The token is read from a local environment variable (`TP_TOKEN`) set by the owner, sent only in the `X-Access-Token` header, never printed, logged or saved; output files are scanned for the token before the run ends. Claude never retrieves the token from SSM |
| Overload the API | Hard cap on total requests, one request at a time, a fixed minimum interval (§4); far below the 600 requests per minute Travelpayouts allows for v3 |

## 2. Tool (to be written after approval, in its own PR)

`aws/tools/b5_compare.py`, built only from code already reviewed in PR #15:

- `farecheck.travelpayouts.Client` for both APIs (same request URLs, headers and validation as
  production), with a recording transport that saves each raw response.
- `farecheck.compat.compare` / `summarize` for the scoring.
- Options: `--plan routes.json`, `--max-requests` (default 200, refuses more than 300),
  `--interval-seconds` (default 2, minimum 1), `--out <dir>`, `--usd` (off by default).
- Output (local, not committed): one JSON line per request (time, API, route, month, HTTP
  status, top-level `currency`, offer count, every offer's price, item currency, departure and
  return strings, `origin`/`destination`, airports, `transfers`, v1 `expires_at`, v3 `link`), the
  validated result with rejection counts, and a summary. A short sanitized summary (no raw
  responses) is committed afterwards as the B5 evidence.

## 3. Sample (representative, small)

Run date T; months M1 = next month, M4 = T + 4 months, M10 = T + 10 months (all Asia/Taipei).

| Origin | Destinations | Why |
|---|---|---|
| TPE | TYO, OSA, SEL, OKA, HKG, BKK, SIN, VCE, LON, NYC, SYD, KMJ | Multi-airport cities (TYO, OSA, SEL, BKK, LON, NYC); single airports (OKA, HKG, SIN, SYD); an airport with a known alternate (VCE/TSF); a thin route (KMJ) for missing data; short and long haul |
| KHH | TYO, OKA, HKG, BKK | Second origin, popular routes |
| RMQ | TYO, OKA, HKG, SEL | Third origin, fewer flights (missing-data behaviour) |

20 routes. TPE routes at M1, M4 and M10; KHH and RMQ routes at M1 and M4 → 36 work items. Each
round makes 36 v1 + 36 v3 TWD requests = **72 requests** (about 3 minutes at 2-second spacing).
**Three rounds about 24 hours apart** (following Travelpayouts' cache-refresh guidance) gives
216 requests in total. One optional USD request per v3 TWD success on the first round only, as a
currency sanity check (§5.1), adds at most 36.

## 4. Procedure

1. The owner approves this plan and the tool's PR is merged (offline tests only).
2. On the owner's computer: `export TP_TOKEN=…` (from their Travelpayouts account; not from
   SSM through Claude), then
   `python3 aws/tools/b5_compare.py --plan aws/tools/b5_routes.json --out b5-round1/`.
3. The tool prints only counts and the summary; the owner checks that no output file contains
   the token (the tool also checks).
4. Repeat for rounds 2 and 3, about 24 hours apart.
5. Claude analyses the output files (shared by the owner) and writes the B5 report; the owner
   decides whether B5 passes.

Stop immediately on HTTP 401/403 (token problem) or repeated 429 (rate limit); never retry in
a loop.

## 5. What is compared

### 5.1 Currency
- Is a top-level `currency` present in v1 and v3 responses, and is it `twd`? Is there an item
  currency?
- **Sanity check that `currency=twd` is honoured:** for the same v3 offer, TWD price ÷ USD price
  should be close to the TWD/USD exchange rate. A ratio near 1 would mean currency is ignored —
  a false-positive risk the validation can't catch when no currency field is returned.

### 5.2 Dates
- Formats and offsets of `departure_at`/`return_at` (local offset, `Z`, or date only).
- Share of offers rejected as `wrong_month`, `departed`, `return_before_departure`,
  `return_too_far`, `expired` (v1).
- Whether v3 with `one_way=false` still returns offers without `return_at` (`one_way`
  rejections).

### 5.3 Airports and codes
- v3 `origin`/`destination`: echoed request codes or city codes? (Important for airport-type
  destinations: if v3 returned a city code that differs from the requested airport, every offer
  would be rejected as `destination_mismatch`.)
- v3 `origin_airport` for `TPE`: how often `TPE` vs `TSA` (T2).
- Every `destination_airport_unexpected` / `origin_airport_unexpected` rejection, with the
  airport code, to find catalog gaps (§6).

### 5.4 Fares and missing data
- Per work item: v1 kind, v3 kind, both cheapest valid prices, difference %, and whether the
  dates are the same itinerary.
- Missing data: items where only one API has a valid fare; items where both are `no_data`;
  errors by HTTP status.
- Stability across rounds: how often the cheapest fare changes within about 24 hours.

### 5.5 Pass criteria (proposed; owner confirms)
B5 passes for switching to v3 if, over the three rounds:
1. v3 has a valid fare in at least as many work items as v1 (`summarize().switch_ok`);
2. where both have one, prices agree within 10 % in at least 90 % of items, and every larger
   gap is explained (different dates or airports);
3. currency is confirmed honoured (§5.1) and no one-way or wrong-month offer would have
   alerted after validation;
4. any airport rejections of real fares are understood, with a decision on the catalog (§6).

If v3 fails, production stays on `FARE_API=v1` (the default), which Phase 2A already supports.

## 6. False-positive and false-negative risks

**False positives (an alert that shouldn't happen):**

| Risk | Current mitigation | What the run checks |
|---|---|---|
| One-way fare shown as round trip | `return_at` required | `one_way` rejection counts |
| Wrong currency (e.g. USD numbers treated as TWD) | Response and item currency checked **when present** | §5.1 ratio check when fields are absent |
| Fare in another month | Departure month checked on the local date | `wrong_month` counts |
| Stale cache (fare no longer bookable) | Past departures and expired v1 offers rejected; fare labelled reference/approximate | Price changes across rounds |
| Different airport than the user expects (e.g. TSA for TPE) | Allowed by design (city code); airport recorded | `TPE` vs `TSA` share |

**False negatives (a real cheap fare missed):**

| Risk | Current behaviour | What the run checks |
|---|---|---|
| **Catalog airport gaps.** An airport-type destination's metro has another airport not in `airports.json` (e.g. VCE↔TSF Treviso, OSL↔TRF Torp, KUL↔SZB Subang, NGO↔NKM Komaki); the offer is rejected as `destination_airport_unexpected` | Confirmed offline 2026-11-09: such offers are rejected | Count and codes of these rejections; VCE is in the sample deliberately |
| v3 returns a city code for an airport request | Would reject all offers (`destination_mismatch`) | §5.3 |
| v3 `limit=30` with `sorting=price`: if the 30 cheapest are all invalid (e.g. one-way), a valid fare beyond them is missed | `no_data (all_rejected)` | Items with 30 offers and none valid |
| Unexpected date or price format | Rejected (`bad_departure`, `bad_price`) | Rejection reasons |
| Thin routes with no cached data | `no_data` (same as M1) | v1 vs v3 coverage on KMJ/RMQ routes |
