# M1.4 B5 — live Travelpayouts v1/v3 comparison plan (read-only)

- **Status:** plan and tool ready, 2026-11-09 (tool: `aws/tools/b5_compare.py`, offline-tested).
  **No live call has been made.** Running it needs the owner's separate approval.
- **Closes:** release blocker B5 (Travelpayouts API compatibility,
  [plan](m1.4-plan.md#m14-release-blockers)), together with the offline evidence in PR #15
  (`aws/lambdas/flight-fare-check/`, `aws/tests/test_m14_fare_check.py`).
- **Question to answer:** with the Phase 2A validation applied, does v3
  `/aviasales/v3/prices_for_dates` find valid round-trip TWD fares at least as often as v1
  `/v1/prices/cheap`, at comparable prices, and what do real responses contain (currency, dates,
  airports, missing data)?

## 1. Safety boundaries

| Must not | How the plan guarantees it |
|---|---|
| Deploy anything to AWS, update a production Lambda, change EventBridge | Runs as a local command-line tool on the owner's computer; touches no AWS API at all |
| Write DynamoDB, read subscriber data | Uses a fixed route list (§3), not the `subscriptions` table; no AWS credentials needed |
| Send SQS messages or emails | The tool has no matching step and no SQS/SES code; it only calls Travelpayouts and writes local files |
| Expose secrets | The token is read from a local environment variable (`TP_TOKEN`) set by the owner, sent only in the `X-Access-Token` header, never printed, logged or saved; output files are scanned for the token before the run ends. Claude never retrieves the token from SSM |
| Overload the API | Hard cap on total requests, one request at a time, a fixed minimum interval (§4); far below the 600 requests per minute Travelpayouts allows for v3 |

## 2. Tool (built 2026-11-09; offline-tested; never run live)

`aws/tools/b5_compare.py` with the sample in `aws/tools/b5_routes.json`. Step-by-step Windows
PowerShell instructions: [B5 tool guide](m1.4-b5-tool-guide.md).

- **Same code as production:** `farecheck.travelpayouts.Client` for both APIs (identical request
  URLs, headers and validation), `farecheck.compat` for scoring. The market check adds only
  `market=tw` to three v3 requests.
- **No AWS:** standard library only; it doesn't import `boto3` and needs no AWS credentials.
  Subscriptions are never read; the route list is a fixed file.
- **Commands:** `preview` (zero network), `live --round N --confirm-live` (also needs
  `B5_LIVE_APPROVED=yes` and the token in `TP_TOKEN`), `check-output DIR`, `summarize DIR...`.
- **Limits:** sequential requests; at least 1 s apart (default 2 s); per-run cap default 200,
  absolute 300, checked before the first request and again on every request.
- **Stops** on HTTP 401/403 (token problem), the **first** 429 (no retry), or 3 consecutive
  errors. Ctrl+C stops at once; nothing is retried automatically.
- **Output** (local, `b5-results/` is git-ignored): `requests.jsonl` (one line per request:
  API, item, URL without token, HTTP status, elapsed time, rate-limit response headers only,
  response currency, result kind and reason, every offer with its validation verdict, risk
  signals), `comparisons.json`, `summary.json`, `summary.md`, `run.json` (settings and an 8-character
  token fingerprint, never the token). Request headers are never written; every string is passed
  through token redaction; the run ends with an automatic secret scan.

## 3. Sample (representative, small)

Months are counted from the run's current month in Asia/Taipei (M1 = next month).

| Origin | Destinations | Months | Work items |
|---|---|---|---|
| TPE | TYO, OSA, SEL, OKA, HKG, BKK, SIN, VCE, LON, NYC, SYD, KMJ | M1, M4 | 24 |
| TPE | TYO, BKK, LON, SYD | M10 | 4 |
| KHH | TYO, OKA, HKG, BKK | M1 | 4 |
| RMQ | TYO, OKA, HKG, SEL | M4 | 4 |

Why these: multi-airport cities (TYO, OSA, SEL, BKK, LON, NYC); single airports (OKA, HKG, SIN,
SYD); an airport with a known alternate (VCE/TSF); a thin route (KMJ) for missing data; short
and long haul; all three origins; near, middle and far months.

**Correction (2026-11-09):** the first version of this table listed TPE at M1/M4/M10 and
KHH/RMQ at M1/M4, which is 52 work items, not the 36 stated. The sample above keeps the stated
36 work items and request budget.

Per round: 36 v1 + 36 v3 TWD requests + 3 v3 market checks = **75 requests** (about 3 minutes
at 2-second spacing). Optional `--usd` in round 1 adds 36 v3 USD requests (111). **Three rounds
about 24 hours apart** (Travelpayouts' cache-refresh guidance): **225 requests**, or 261 with the
USD check. Peak rate 30 requests per minute, 5 % of the 600 per minute Travelpayouts allows for v3.

**Cost:** no AWS cost (no AWS is used). Travelpayouts' written reply set a rate limit, not a
price; no per-request charge for the Data API is known to the project. Only the owner's
computer and internet connection are used.

## 4. Procedure

1. The owner reviews and merges the tool's PR (offline tests only).
2. On the owner's computer, in Windows PowerShell, follow the [tool guide](m1.4-b5-tool-guide.md):
   self-test, `preview`, set the token for that window only, then — **only after approving the
   live test** — `live --round 1 --confirm-live`.
3. The tool checks its own output; the owner can rerun `check-output` at any time.
4. Rounds 2 and 3 about 24 hours apart, each in a new folder.
5. `summarize` the three folders; the owner shares the summary files (never the token) and
   Claude writes the B5 report; the owner decides whether B5 passes.

## 5. What is compared

### 5.1 Currency and market
- Is a top-level `currency` present in v1 and v3 responses, and is it `twd`? Is there an item
  currency?
- Market: the fare check sends no `market` parameter (v3 default). Record any market field the
  responses carry, and for a small subset (TPE–TYO, TPE–OSA, KHH–OKA at M1) repeat the v3 request
  once with the documented `market` parameter set to the Taiwan market, to see whether results,
  prices or coverage change. Observation only; the production request stays unchanged unless the
  owner decides otherwise. (Adds at most 3 requests per round.)
- **Sanity check that `currency=twd` is honoured:** for the same v3 offer, TWD price ÷ USD price
  should be close to the TWD/USD exchange rate. A ratio near 1 would mean currency is ignored —
  a false-positive risk the validation can't catch when no currency field is returned.

### 5.2 Dates
- Formats and offsets of `departure_at`/`return_at` (local offset, `Z`, or date only).
- Share of offers rejected as `wrong_month`, `departed`, `return_before_departure`,
  `return_too_far`, `expired` (v1).
- Whether v3 with `one_way=false` still returns offers without `return_at` (`one_way`
  rejections).

### 5.3 Airports and codes
- v3 `origin`/`destination`: echoed request codes or city codes? (Important for airport-type
  destinations: if v3 returned a city code that differs from the requested airport, every offer
  would be rejected as `destination_mismatch`.)
- v3 `origin_airport` for `TPE`: how often `TPE` vs `TSA` (T2).
- Every `destination_airport_unexpected` / `origin_airport_unexpected` rejection, with the
  airport code, to find catalog gaps (§6a).

### 5.4 Round trips
- With `one_way=false`, every v3 offer counted as valid must have `return_at`, a return on or
  after the departure, and `transfers`/`return_transfers` consistent with a two-way trip.
- Count v1 offers without `return_at` (M1 would have alerted on them; Phase 2A rejects them).

### 5.5 Fares and missing data
- Per work item: v1 kind, v3 kind, both cheapest valid prices, difference %, and whether the
  dates are the same itinerary.
- Missing data: items where only one API has a valid fare; items where both are `no_data`;
  errors by HTTP status.
- Stability across rounds: how often the cheapest fare changes within about 24 hours.

### 5.6 Rate limits and hygiene
- Record the rate-limit headers on every response, the lowest remaining quota seen, and any 429.
- After each round, scan all output files for the token, `@`, and the owner's account
  identifiers; any hit invalidates the round (files deleted, round repeated after a fix).

### 5.7 Acceptance criteria: two separate conclusions (revised 2026-11-09)

B5 reports **A. technical compatibility** and **B. business suitability** separately.
`summarize` computes both from the round folders; the owner makes the final decision.

v1 and v3 are cached results of different queries with different cache coverage. **Neither
lower v3 coverage nor a v1/v3 price difference makes the integration technically wrong**, and
relative prices never choose the production API on their own.

**A. Technical compatibility — PASS / FAIL.** PASS only if every check passes (a check that
lacks evidence is `not_verified` and counts as not passed):

| Check | Passes when |
|---|---|
| API parsing | Every HTTP 200 response parses, and no offer is rejected for an unexpected field format (`bad_price`, `bad_departure`, `bad_return`, `not_object`) |
| Round trip | Every accepted offer has a return date on or after departure; every v3 request sent `one_way=false` |
| Departure and return dates | No accepted offer has already departed (same rule as production) |
| Currency | No TWD request got a non-TWD response or fare; evidence exists (response `currency` fields, or the round-1 `--usd` check with a plausible TWD/USD ratio of 10–60) |
| Wrong-month rejection | No accepted offer departs outside the requested month |
| Malformed response handling | Every error has a known, classified reason (no crash, no unexplained state) |
| API error handling | Every non-200 status maps to an `http_<code>` error, and no round stopped early (repeat aborted rounds) |
| Token safety | The secret scan of every round folder is clean |
| No production side effects | By construction: the tool has no AWS, database, Lambda, SQS or email code (offline tests verify) |

**B. Business suitability — PASS / CONDITIONAL / FAIL** (proposed thresholds; owner confirms).

- Measured per round and route/month:
  - valid-fare coverage of each endpoint;
  - route/months covered by **both**, **only v1**, **only v3** and **neither**;
  - missing-data rates (`no_data` + `error`) per endpoint;
  - false-negative risks: cheaper offers rejected for airport mapping (§6a), and route/months
    where every offer was rejected.
- **PASS:** v3 covers every route/month that v1 covers, with no airport-mapping losses → v3
  alone is sufficient.
- **CONDITIONAL:** v3 covers at least half of all covered route/months, but some are covered
  only by v1 (→ keep v1 as a fallback), or cheaper fares were lost to airport mapping (→ §6a
  review), or more than 25 % of route/months have no data from either API (→ review).
- **FAIL:** no valid fare from either API, or v3 covers less than half of the route/months
  that have any valid fare.
- The report states **whether v3 alone is sufficient** and **whether a v1 fallback is
  advisable**.

**Price differences (review only, never a failure).** Every overlapping route/month whose
cheapest v1 and v3 fares differ by more than 10 % is listed with:
- both prices and which is lower;
- departure and return dates of each, and whether they are the same;
- v3's actual airports;
- round-trip and TWD checks;
- cached-fare freshness (v1 `expires_at` hours left; v3 provides no freshness field).

A lower valid v3 fare is not an error.

**Also required:** each round's secret check is clean, and aborted rounds are repeated, not
counted.

If technical compatibility fails, production stays on `FARE_API=v1` (the default). If business
suitability is CONDITIONAL, the owner decides between v3 with v1 fallback, staying on v1, or
fixing the listed conditions first; that would be a separate code change.

## 6. False-positive and false-negative risks

**False positives (an alert that shouldn't happen):**

| Risk | Current mitigation | What the run checks |
|---|---|---|
| One-way fare shown as round trip | `return_at` required | `one_way` rejection counts |
| Wrong currency (e.g. USD numbers treated as TWD) | Response and item currency checked **when present** | §5.1 ratio check when fields are absent |
| Fare in another month | Departure month checked on the local date | `wrong_month` counts |
| Stale cache (fare no longer bookable) | Past departures and expired v1 offers rejected; fare labelled reference/approximate | Price changes across rounds |
| Different airport than the user expects (e.g. TSA for TPE) | Allowed by design (city code); airport recorded | `TPE` vs `TSA` share |

**False negatives (a real cheap fare missed):**

| Risk | Current behaviour | What the run checks |
|---|---|---|
| **Catalog airport gaps.** An airport-type destination's metro has another airport not in `airports.json` (e.g. VCE↔TSF Treviso, OSL↔TRF Torp, KUL↔SZB Subang, NGO↔NKM Komaki); the offer is rejected as `destination_airport_unexpected` | Confirmed offline 2026-11-09: such offers are rejected | Count and codes of these rejections; VCE is in the sample deliberately |
| v3 returns a city code for an airport request | Would reject all offers (`destination_mismatch`) | §5.3 |
| v3 `limit=30` with `sorting=price`: if the 30 cheapest are all invalid (e.g. one-way), a valid fare beyond them is missed | `no_data (all_rejected)` | Items with 30 offers and none valid |
| Unexpected date or price format | Rejected (`bad_departure`, `bad_price`) | Rejection reasons |
| Thin routes with no cached data | `no_data` (same as M1) | v1 vs v3 coverage on KMJ/RMQ routes |

## 6a. Airport-mapping review criteria (B5)

Phase 2A keeps strict airport validation. Confirmed offline (2026-11-09) cases where a real fare
to an alternate airport of the same city is rejected: **Venice VCE / Treviso TSF**, **Oslo OSL /
Torp TRF**, **Kuala Lumpur KUL / Subang SZB**, **Nagoya NGO / Komaki NKM**. The run measures, for
every `*_airport_unexpected` rejection: the requested code, the returned `origin`/`destination`,
the returned airport, the price, and whether it would have been the cheapest valid offer (a
missed or more expensive alert).

An airport may be added to a destination's accepted airports in `airports.json` **only if all**
of these hold, each decided by the owner in a separate PR with tests:

1. **Same requested code:** Travelpayouts returned the requested code itself in `destination`
   (or `origin`) for that offer — the API treats the airport as part of the requested
   destination, not a different one.
2. **Same city in an independent reference:** OpenTravelData (already used by
   `aws/tools/verify_airports.py`) lists the airport under the same IATA city code as the
   destination; a marketing name ("Venice Treviso") alone is not enough.
3. **Plausible for travellers:** reasonable ground access to the destination city (the review
   records distance and transfer options); an airport that serves a different city is never
   added, however cheap.
4. **Observed, not hypothetical:** at least one rejected real offer in the B5 run, or an
   explicit owner decision.
5. **No loosening by pattern:** no wildcard, "any airport in the same country" or "trust
   whatever the API returns" rule. Each addition is an explicit code → airport entry, and the
   catalog verifier keeps passing.

Offers to an airport that fails any criterion stay rejected: the subscriber may miss that fare
(false negative) but never gets an alert for a different destination (false positive).
