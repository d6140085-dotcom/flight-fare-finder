## API (new Lambda `flight-subscriptions-api`, role `flight-subscriptions-api-role`)

Full contract: [M1.4 subscriptions API](api/m1.4-subscriptions-api.md). Summary:

| Method & path | Body | Behaviour |
|---|---|---|
| `GET /subscriptions` | — | Rows with `departure_month`, `month_mode`, `effective_month`, `status`; `limits {max, used}` |
| `POST /subscriptions` | `origin`, `destination`, `departure_month`, `target_price` | Allowlist, month window, target 1–1,000,000 TWD, no duplicate route, quota-checked create |
| `PATCH /subscriptions/{route}` | any of `target_price`, `departure_month`, `alerts_paused`, `origin`+`destination`, `if_updated_at` | `UpdateItem` or atomic route change; never touches the quota |
| `DELETE /subscriptions/{route}` | — | Quota-checked delete; the only way to free a slot |
| `POST /subscribe` (legacy) | `plan_name`, `target_price` | After cutover: same handler and quota path (existing route → update; new route → quota-checked rolling create). Production routing unchanged until then |

The API never reads or writes `notification_history` (ADR D6).

## Fare check (wrapper + parser)

- **Only subscribed route-months are queried — never the catalog.** The number of catalog
  destinations has no effect on Travelpayouts usage; a destination nobody subscribes to is never
  looked up.
- **Work items from data, deduplicated by `(origin, destination, effective_month)`.** The
  wrapper scans `subscriptions` (projection without `email`: `route`, `origin`, `destination`,
  `departure_month`, `alerts_paused`), computes each row's effective month (`departure_month`,
  or next month in Asia/Taipei for rolling rows), drops paused and expired rows, and invokes
  the parser once per **distinct** `(origin, destination, effective_month)`. Each month gets an
  independent result; two users on the same route and month share one lookup. The static
  `flight-routes.json` is retired.
- **Parser matches only its group:** rows of that route whose effective month equals the
  invocation's month, not paused, not expired (re-checked in the parser, in case a row changed
  after the wrapper's scan). The SQS message format is unchanged.
- **Expired rows** (fixed month < current month) are skipped by both; nothing is written to them.
- **Concurrency cap** on the parser (about 5) to stay well under Travelpayouts' per-minute limits.
- **`DRY_RUN=1`** setting: compute and log matches, send nothing to SQS. All Phase 2 testing
  uses it, so no test can email anyone.
- **`route-index` GSI** (sparse, active rows) when subscriptions reach roughly 1,000, so the
  parser queries one route instead of scanning the table per route.

### Travelpayouts v3 migration (gated)

Target request:
`/aviasales/v3/prices_for_dates?origin=…&destination=…&departure_at=<effective month YYYY-MM>&one_way=false&currency=twd&sorting=price`
(token in the `X-Access-Token` header, as today).

| Check | Why |
|---|---|
| `one_way=false` sent explicitly | v3 defaults to one-way; today's v1 results are round trips (every live message had a `return_at`) |
| Every accepted offer has `return_at`, `departure_at` falls in the requested month, and `return_at` ≥ `departure_at` | Keeps the "round trip departing in the chosen month, any return" meaning; drop offers that don't |
| Response is `success: true` with a `data` **array** (v1 was an object keyed by destination) | New parser path; empty/`success: false`/429 → "no fare", exactly as v1 handling |
| `currency` in the response (if present) equals the requested one, case-insensitively | Never compare a non-TWD price with a TWD target |
| `market` left unset, as v1 today (default `ru`) | Changing the data source market is a separate, explicit decision |
| Cheapest = minimum `price` across valid offers | Same rule as v1 |

Rollout: `FARE_API=v1|v3` setting, default `v1`. Run both in `DRY_RUN` for the same routes over
several schedules; switch only if v3 returns a valid round-trip fare at least as often as v1 and
the cheapest prices agree within an agreed tolerance. v1 stays available as a fallback.

### Origin TPE is a city code (Taoyuan + Songshan)

`airports.json` defines the origin `TPE` as `type: "city"` with `airports: ["TPE", "TSA"]`:
the IATA metropolitan code for Taipei covers **TPE** (Taoyuan International) and **TSA**
(Songshan). The IATA code `TPE` is *also* the code of the Taoyuan airport itself, so the same
three letters can mean "Taipei, any airport" or "Taoyuan only" depending on the API.
OpenTravelData lists both airports under city `TPE` (checked 2026-11-05). M1 already sends
`origin=TPE` to v1 `/prices/cheap`, whose `origin` is documented as a city code, and its
responses don't say which airport was used; M1 behaviour is therefore unchanged by this PR.
`TSA` is not offered separately (it would duplicate fares), and KHH and RMQ are single airports.

Phase 2 must confirm how Travelpayouts treats `TPE`, in `DRY_RUN`, before the cutover:

| # | Check | Pass condition |
|---|---|---|
| T1 | Travelpayouts' own static data (`/data/en/cities.json`, `/data/en/airports.json`; no price quota) | `TPE` is a city with flightable airports `TPE` and `TSA` (`TSA.city_code = TPE`) |
| T2 | v3 `prices_for_dates` returns `origin_airport` for each offer; log its distribution for every `TPE-*` work item | Values are only `TPE` or `TSA`; anything else is rejected and logged |
| T3 | Routes served from Songshan (`TPE-TYO` via HND, `TPE-SEL` via GMP, `TPE-SHA`) | `TSA` offers appear (city semantics); if they never do, v3 is treating `TPE` as the Taoyuan airport only — record it, and the UI wording changes to 台北（桃園） |
| T4 | v1 vs v3 for the two M1 routes over several runs | Same airport semantics and cheapest price within the agreed tolerance (v3 migration table above) |
| T5 | Departure airport shown to users | Decide whether to show 「桃園」/「松山」 from `origin_airport`; the email shows it only after an approved notification change, so until then the UI says 台北 (桃園／松山) consistently |

Outcome recorded in the plan before the cutover; if T1–T3 contradict city semantics, the
catalog entry is corrected (for example `type: "airport"` with no `airports`) in its own reviewed
change.

### USD lookup

Each route costs two requests (TWD + USD). The USD value only feeds the optional 「約 US$」 line.
Dropping it halves Travelpayouts usage and needs no notification code change (the line is
skipped when absent), but the email changes visibly. Decide after the M1 email test; an
alternative is one currency-rate request per run instead of one USD request per route.

## Deployment gate (before any new route is publicly reachable)

The deployed parser checks next month for every row and ignores pause and month (ADR D14), so the
cutover needs all of these, verified in `DRY_RUN`:

1. Wrapper builds work from data and deduplicates by `(origin, destination, effective_month)`.
2. Parser matches only rows of its month; rolling rows resolve to next month, as today.
3. Paused rows and expired fixed-month rows produce no SQS message.
4. `subscription_quota` exists; `POST /subscriptions`, `DELETE` and legacy `POST /subscribe` use
   the quota path (read version first, then count; ≤ 3 attempts).
5. The SQS message the notification Lambda receives is byte-for-byte the M1 shape; the
   notification Lambda's hash is unchanged.
6. The two existing M1 rows produce the same work items and matches as before the change.

If Phase 1B ships before Phase 2, its routes stay unattached (direct IAM invocation only) until
this gate passes; otherwise 1B, 2 and the cutover ship together.

## Impact

At 100 users × 3 subscriptions (~40 distinct routes), checking every 30 minutes:
~3,840 Travelpayouts calls/day (~1,920 without USD), peak ~80 per run (limits 300–600/min).
Fixed months add work items: in the worst case (every subscription on a distinct month) one per
subscription — at most 10 per user, so 100 users × 3 = ≤ 300 lookups per run before USD,
still under the per-minute limit with the concurrency cap, but schedule frequency may need to
drop if users spread across many months;
~2,000 Lambda invocations/day; AWS cost under US$1/month; PITR ≈ US$0.00. The binding limits
are Travelpayouts' per-minute rate and Resend's sending plan (and the demo-sender restriction
until M3).
