# M1.4 specification — Multi-Platform Flight Search Links

- **Status:** specification only, proposed 2026-11-06. Nothing here is implemented or deployed.
  The links are built in **Phase 2B** (email) and **Phase 3** (subscription page), each after
  its own approval. They ship only once the compliance items in §8.4 are resolved.
- **Related:** [M1.4 plan](m1.4-plan.md) (phases, blocker B6) ·
  [API contract §3.4](api/m1.4-subscriptions-api.md#34-fare-check-status-phase-2a) (fare data
  for the page) · [ADR 0001 D15](adr/0001-m1-4-dynamic-routes.md) · notification email:
  `aws/README.md`.
- **Unchanged by this feature:**
  - Travelpayouts **Data API** stays the only fare source.
  - The wrapper, parser and fare-detection rules, the SQS message, `subscriptions`,
    `subscription_quota` and `notification_history` (keys and schemas) all stay the same.
  - The existing Aviasales search link stays.

## 1. Goal

When the system detects a fare, the user can search **the same itinerary** on the platform
they prefer. The links favour the Taiwan market, Traditional Chinese and TWD.

The links are a convenience only. They never claim that the fare Travelpayouts detected can be
booked on another platform.

## 2. User experience

### 2.1 Email notification (Phase 2B)

```
✈️ 台北 → 東京 參考票價 NT$8,062（已低於你的目標價）

參考票價（Travelpayouts 偵測）：NT$8,062
你的目標價：NT$9,000
去程 2026-12-11  回程 2026-12-18（來回）
航空公司：…

[ 在 Skyscanner 搜尋此行程 ]      ← primary button
[ 在 Trip.com 搜尋此行程 ]        ← secondary button
在 Aviasales 搜尋此行程（英文介面，票價來源網站）   ← text link
在 Google 航班自行搜尋（需手動輸入航線與日期）       ← text link, optional

票價為系統偵測到的參考價格，可能已變動。各平台的價格與可訂位情況不同，
實際價格以訂購網站為準。
```

- **Wording replaces today's 「立即訂購」**, which suggests the fare is guaranteed to be
  bookable. The headline changes from 「降價通知！NT$X 已達標」 to a "reference fare" wording.
  Both are part of the Phase 2B notification change and need approval like any email change.
- English equivalents, used in docs and tests: "Reference fare detected: NT$8,062" and
  "Search this itinerary on Skyscanner".
- The plain-text part of the email carries the same links, one per line, with the same labels.

### 2.2 Subscription page (Phase 3)

- Buttons appear **only** when the subscription's `fare_check.kind` is `ok` and it carries both
  dates (API contract §3.4).
- No buttons appear for 尚未查詢, 沒有近期票價資料, 查詢失敗, 已暫停 or 已過期.
- Layout under the fare line:
  - 「參考票價（Travelpayouts 偵測）：NT$8,062・去程 12/11 回程 12/18」;
  - then one primary button (Skyscanner), one secondary button (Trip.com) and a 「更多搜尋方式」
    disclosure holding Aviasales and Google Flights;
  - then the short disclaimer (§5).
- Every link opens in a new tab with `rel="noopener noreferrer"` and is announced as external
  (icon plus visually hidden 「（另開新視窗）」).

### 2.3 Platform priority

| Order | Platform | Role | Itinerary preserved? (§4) |
|---|---|---|---|
| 1 | Skyscanner Taiwan (`www.skyscanner.com.tw`) | Primary recommendation | Yes, for verified codes |
| 2 | Trip.com Taiwan (`tw.trip.com`) | Secondary recommendation | Yes, for verified codes |
| 3 | Aviasales (`www.aviasales.com`) | Original fare-search source; always kept | Yes (English UI) |
| 4 | Google Flights | Optional fallback | **No**: opens Google Flights in Traditional Chinese; the user enters the route and dates |

The order and on/off state live in configuration (§3.1), not in code. A broken platform can be
switched off without changing the notification or fare-check logic.

## 3. Architecture

### 3.1 Placement: links are presentation, not detection

```
Travelpayouts Data API ─▶ wrapper/parser ─▶ SQS message (unchanged: route, cheapest{price,
                          (fare detection,                depart_date, return_date, …})
                           no links)                            │
                                                                ▼
                         search-links module ◀── search-platforms.json (order, enabled,
                         (pure functions)          URL templates, verified codes, affiliate: off)
                           │            │
             notification email     subscription page (from fare_check: route + dates)
```

- **Pure function:**
  `build_search_links(origin, destination, depart_date, return_date, today) → [{platform,
  label, url, kind: "itinerary" | "fallback", notice}]`.
  - It makes no network calls and reads no user data.
  - It takes no email address, user ID or token as input.
- **One configuration file**, `aws/config/search-platforms.json`, holds for each platform:
  - the URL template and the allowed host;
  - `enabled` and `order`;
  - the codes verified for itinerary links, and code overrides;
  - an `affiliate` block, empty and disabled.

  Python (email) and TypeScript (page) read the same file, and a shared set of test vectors
  keeps the two in step.
- **Never** in the wrapper or parser. Never stored in `subscriptions` or
  `notification_history`, and never sent in the SQS message: the message already carries
  everything needed (`route`, `cheapest.depart_date`, `cheapest.return_date`).
- **Page data:**
  - The proposed `fare_check` record (API contract §3.4, a new table not yet approved) is
    extended with `depart_date` and `return_date` beside `cheapest_twd`. These are non-key
    attributes of that proposed table; no existing table or key changes.
  - Without them the page shows no buttons.
  - The browser builds the URLs; the API returns no URLs.
- **Email size:** the notification Lambda's inline code is at the 4,096-byte CloudFormation
  limit. Phase 2B therefore depends on moving it to packaged deployment (ADR D10), which is
  already planned.

### 3.2 Why not the Skyscanner referral endpoint

Skyscanner documents an Affiliates Link API (`/g/referrals/v1/flights/day-view`) whose
parameters are listed in its developer docs. The endpoint is meant for partners identified by
an impact.com `mediaPartnerId`.

On 2026-11-06, a request **without** a partner ID redirected (301) to the public results page.
The redirect added tracking parameters this project was never issued:

- an `irclickid`;
- `associateid`;
- `campaign_id`;
- `utm_source=…-Unmonitised Partner Tracker`.

To avoid attributing clicks to a tracker that isn't ours, v1 links straight to the **public
page that the redirect lands on**. It uses only the parameters the redirect itself produced,
whose names match the documented ones (`adultsv2`, `cabinclass`, `market`, `locale`,
`currency`). The referral endpoint becomes the route for affiliate links later (§9), once a
`mediaPartnerId` is issued.

## 4. URL generation rules

### 4.1 Inputs and validation (all platforms)

| Input | Rule | On failure |
|---|---|---|
| `origin` | One of the catalog origins `TPE`, `KHH`, `RMQ` (`airports.json`) | No links at all (log the error without personal data) |
| `destination` | One of the 95 catalog destinations | No links at all |
| `depart_date` | Valid `YYYY-MM-DD`; not before today (Asia/Taipei); not after today + 13 months | Itinerary links are replaced by fallbacks (§6) |
| `return_date` | Valid `YYYY-MM-DD`, **required**, ≥ `depart_date`, not after today + 13 months | Fallbacks; **never** a one-way link |
| Passengers / cabin | Fixed: 1 adult, economy (the fare data has the same meaning) | — |

- Codes are upper-case in the catalog. Each platform template converts the case itself.
- Inputs are validated before any string building.
- URL components are percent-encoded, even though validated codes and dates never need it.

### 4.2 Per-platform templates

Each "Verified 2026-11-06" result below was checked by opening the generated URL in a real
browser. "Documented" means the vendor's public documentation describes it.

**Skyscanner Taiwan (itinerary)**

```
https://www.skyscanner.com.tw/transport/flights/{o}/{d}/{yymmdd(depart)}/{yymmdd(return)}/
  ?adultsv2=1&cabinclass=economy&market=TW&locale=zh-TW&currency=TWD
```

- Codes are lower-case.
- Parameter names and meanings are documented
  ([Flights Parameters](https://developers.skyscanner.net/docs/referrals/flights-parameters):
  `adultsv2`, `cabinclass`, `market`, `locale`, `currency`). The path form is the page that
  Skyscanner's own referral service redirects to; it isn't separately documented.
- Verified for `TPE-TYO`:
  - the page reads 台北 (TPE) → 東京（任何）;
  - 出發 12月11日, 回程 12月18日;
  - Traditional Chinese.
- Verified for `RMQ-OKA`: 台中 (RMQ) → 沖繩 (OKA), round trip, and results loading.
- The referral redirect itself added `market=tw&locale=zh-tw&currency=twd`.
- **Not verified:**
  - **TWD prices.** The automated browser met Skyscanner's bot check before prices rendered.
    After the bot check, Skyscanner returns the user to the same itinerary path.
  - **Origin `TPE` semantics.** Skyscanner showed 「台北 (TPE)」, which may mean Taoyuan only.
    Songshan (`TSA`) fares may then be missing on Skyscanner.
  - **City codes other than `TYO`.** Skyscanner uses its own entity codes for some cities. For
    example, the referral service mapped `tyo` → `tyoa`. Only codes in the verified list get an
    itinerary link (§4.3).

**Trip.com Taiwan (itinerary)**

```
https://tw.trip.com/flights/showfarefirst?dcity={o}&acity={d}&ddate={depart}&rdate={return}
  &triptype=rt&class=y&quantity=1&locale=zh-TW&curr=TWD
```

- Codes are lower-case and dates are `YYYY-MM-DD`.
- **Not documented publicly.** Trip.com's site uses this entry URL itself. It redirects to
  `/m/flights/{o}-to-{d}/tickets-{o}-{d}/?dcitycode=…&ddate=…&adate=…&triptype=1&…&locale=zh-TW&curr=TWD`
  (the mobile view, in the test browser),
  and the redirect keeps every value.
- Verified for `TPE-TYO`: 台北 → 東京, TWD prices, Traditional Chinese, round-trip flow (去程航班
  first). Also verified for `RMQ-OKA` (台中 → 沖繩) and `KHH-OKA`.
- **Silent failures observed:**
  - An unknown destination code (`zzq`) is accepted and shown as "zzq".
  - A past date is moved silently to today.

  Hence the strict validation in §4.1 and the verified-codes rule in §4.3.

**Aviasales (itinerary; existing format, unchanged)**

```
https://www.aviasales.com/search/{O}{DDMM(depart)}{D}{DDMM(return)}1
```

- Verified for `TPE-TYO`: Taipei ⇄ Tokyo, Fri Dec 11 — Fri Dec 18, 1 pax, economy.
- The UI is English. No documented language or currency parameter exists, so none is added,
  and the label says 英文介面.
- The Data API's `prices_for_dates` returns a `link` for each offer, documented as "add the code
  to `https://www.aviasales.com/`". When Phase 2A moves to v3, that `link` may replace the hand-built
  path, but only after its own verification.
- The DDMM format has no year. The validation window (§4.1) keeps dates within 13 months, so
  the year can't be ambiguous within the window.

**Google Flights (fallback only)**

```
https://www.google.com/travel/flights?hl=zh-TW
```

- Opens Google Flights in Traditional Chinese.
- Google publishes no consumer deep-link format for flight searches, so **no route or date is
  added**. `gl` and `curr` were honoured in testing but aren't documented, so they are left out.
- The page pre-fills the origin from the visitor's own location. The button label therefore
  always says 需手動輸入航線與日期.

### 4.3 Verified-codes rule

- An itinerary link is generated only when **both** codes are in that platform's
  `verified_codes` list in `search-platforms.json`. Otherwise that platform gets its fallback
  link (§6).
- The lists start with the codes verified on 2026-11-06:
  - Skyscanner: `TPE`, `RMQ`, `TYO`, `OKA`;
  - Trip.com: `TPE`, `KHH`, `RMQ`, `TYO`, `OKA`;
  - Aviasales: all catalog codes, which come from Aviasales' own data.
- They grow through the manual verification in §7.3.
- City codes need particular care. Of the 95 destinations, 26 are city codes (for example
  `LON`, `PAR`, `NYC`, `SEL`, `OSA`, `BJS`).
- A platform-specific **code override** (for example `TYO → tyoa` on Skyscanner) may be added
  only after it has been verified the same way.

## 5. Localization and price disclaimers

| Item | Rule |
|---|---|
| Language | Traditional Chinese labels everywhere. Platform UI: zh-TW on Skyscanner, Trip.com and Google Flights; English on Aviasales (labelled) |
| Currency | The fare is shown in TWD as detected. Skyscanner and Trip.com links request TWD. Any other currency is the platform's own choice |
| Price wording | Always 「參考票價（Travelpayouts 偵測）：NT$X」. Never 「立即訂購」, 「保證」, 「此價格可在 … 購買」 or a platform name next to the price |
| Button wording | 「在 {平台} 搜尋此行程」. For a fallback: 「前往 {平台}（需自行確認航線與日期）」 |
| Disclaimer (email and page) | 票價為系統偵測到的參考價格（資料來源：Travelpayouts），可能已變動。各平台顯示的價格與可訂位情況可能不同，實際價格以訂購網站為準。 |
| Date display | 去程 YYYY-MM-DD 回程 YYYY-MM-DD（來回）. Both dates are always shown next to the buttons, so the user can check them on the platform |

## 6. Failure and fallback behaviour

| Situation | Behaviour |
|---|---|
| Origin or destination not in the catalog | No search links; the email still sends (it never depends on links); error logged without personal data |
| Missing, invalid, past or out-of-window date, or `return_date` < `depart_date` | Every platform gets its fallback, never a one-way link; notice 「請自行確認航線與日期」 |
| Codes not in a platform's `verified_codes` | That platform gets its fallback: Skyscanner `https://www.skyscanner.com.tw/`, Trip.com `https://tw.trip.com/flights/`, Google Flights as §4.2. Aviasales keeps its itinerary link |
| Platform URL breaks or changes (detected by the periodic check, §7.3) | Set `enabled: false` or mark its codes unverified in configuration; no code change and no change to fare detection or notifications |
| All itinerary links unavailable | The email and page still show the reference fare, dates and disclaimer, plus the fallback links |
| Generator throws | Caught. The email is sent without the links section rather than failing; a counted, data-free log line is written |

### 7.3 Manual provider verification (owner, before each enablement, then monthly)

Automated browsing meets bot checks on Skyscanner, and scraping provider sites is out of scope.
A person therefore opens a checklist of generated links. For each one they confirm the route,
both dates, round trip, Traditional Chinese, TWD, and a correct city/airport name.

- Results are recorded in the config's `verified_codes` with a date. A code fails if any field is
  wrong.
- Minimum set before go-live:
  - the M1 routes;
  - every origin × the 10 most-subscribed destinations;
  - every city code that is enabled for itinerary links.

## 8. Security and compliance

### 8.1 Security

- URLs are built from catalog codes and validated dates only. They never contain user
  identifiers, email addresses, tokens or subscription IDs.
- Links go **directly** to the platform. There is no redirect through our domain (no open
  redirect), no click-tracking service and no tracking pixel.
- Host allowlist per platform; `https` only; HTML escaping; `rel="noopener noreferrer"` so the
  platform receives no `window.opener` and no referrer from the app.
- Link generation adds no new AWS permission, secret or network call. The Travelpayouts token
  never appears in links (already a rule in `aws/README.md`).

### 8.2 Data API vs Search API

| | Travelpayouts **Data API** (used) | Travelpayouts **Search API** (not used) |
|---|---|---|
| What | Cached prices from Aviasales users' searches (kept about 2–7 days) | Real-time search across agencies |
| Access | "Allowed without restrictions", with a token | Restricted: application, project review, conversion thresholds |
| Rules | Use per the partner agreement; cache about 24 h; don't use expired prices | Every search user-initiated; full results with a Book button; **may not be combined with other metasearch APIs**; no scraping; server-side only |

This project uses **only the Data API** and must not start using the Search API. The Search
API's ban on combining with other metasearch APIs does not apply to the Data API, and the
links in this spec call no other provider's API.

### 8.4 Unresolved — must be closed before the links ship (release blocker B6)

1. **Combining Travelpayouts-derived fares with links to other platforms.**
   - Neither the Data API pages nor the Affiliate Agreement forbids it. Nor do they expressly
     allow showing an Aviasales-derived price next to Skyscanner, Trip.com or Google Flights
     links.
   - The Data API's purpose is to inform users and build content, and its prices come from
     Aviasales searches.
   - **Action:** ask Travelpayouts support in writing and record the answer here. Until then,
     the email and page name Travelpayouts as the fare source and keep Aviasales in the link
     set.
2. **Using Skyscanner's public results URL without a partner relationship.**
   - It is an ordinary hyperlink to a public page; we do no scraping and no framing.
   - Skyscanner's general website terms have not been reviewed for this.
   - **Action:** owner review of Skyscanner's site terms, or join its affiliate programme and use
     the referral endpoint (§9).
3. **Trip.com and Google Flights URL stability.** Neither format is documented. This is managed
   operationally (§6, §7.3), but it is a standing risk.
4. **Origin `TPE` on Skyscanner** may mean Taoyuan only (§4.2). Record the result of the manual
   verification; if it is confirmed, add a note next to the Skyscanner button.

None of these blocks Phase 2A, which doesn't touch links.

## 9. Future affiliate integration

- Each platform has an `affiliate` block in `search-platforms.json`:
  `{"enabled": false, "params": {}, "via": null}`.
  - Enabling it adds only the issued, documented parameters to that platform's links, or swaps
    the template for the platform's documented affiliate form.
  - It changes nothing in the SQS message, wrapper, parser, `notification_history`, any table
    schema or the email structure.
- Expected routes (none issued today):

  | Platform | Route | Parameters |
  |---|---|---|
  | Aviasales | Travelpayouts `marker` (`?marker=<id>`, already described in `aws/README.md`) | Partner ID, not a secret |
  | Trip.com | Travelpayouts Trip.com programme link tool | Converted link from Travelpayouts; no hand-made `Allianceid`/`SID` |
  | Skyscanner | impact.com membership | Referral endpoint (`/g/referrals/v1/flights/day-view`) with the issued `mediaPartnerId` |

- Prerequisites for enabling any affiliate link:
  - an issued ID recorded in the config by the owner;
  - an affiliate disclosure on the page and in the email (「本服務可能因你透過連結訂購而獲得佣金」);
  - an L09 update;
  - a re-run of §7.3.
- Test L12 rejects an enabled affiliate block without an issued ID.

## 10. Acceptance criteria

1. Email (Phase 2B) and page (Phase 3) show the reference fare with the §5 wording and the
   disclaimer. 「立即訂購」 is removed.
2. Platform order is Skyscanner, Trip.com, Aviasales, Google Flights, driven by configuration.
   Aviasales is always present.
3. For verified codes and valid dates, Skyscanner and Trip.com links open the same round trip
   (route, both dates) in Traditional Chinese, with TWD requested. Confirmed by §7.3 for the
   minimum set.
4. No link is ever one-way. Every invalid or missing date or unverified code produces the
   documented fallback and notice.
5. L01–L12 pass in both Python and TypeScript from the shared vectors. L08 and L09 show no
   personal data, tokens or affiliate parameters.
6. Links are generated outside the fare-detection path. The SQS message, the parser output and
   all table schemas are unchanged, verified by the existing M1 message-shape tests.
7. The §8.4 items are closed with written evidence, and the owner approves enabling each
   platform.
