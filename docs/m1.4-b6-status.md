### 1.0 Provider eligibility (B6-2B)

Eligibility is about **authorization for our intended use** (links in opt-in alert emails and the
signed-in subscription page of a commercial service), not about whether a URL works. A provider is
never "approved" because its links open correctly. No new configuration field exists for this; the
states map onto the existing `enabled` and `verified_codes` settings and this document.

| State | Meaning | How the config expresses it |
|---|---|---|
| **Approved for intended use** | Written terms or an affiliate agreement cover this use | `enabled: true`, itinerary codes as verified |
| **Pending authorization** | Use depends on an authorization not yet confirmed | `enabled: true` only while not deployed; must be resolved before B3 activation |
| **Restricted** | Allowed only in a limited form (for example general search page only) | `verified_codes.codes: []` |

### 1.2 Email-first MVP (decided 2026-11-25)

- **Scope:** opt-in alert emails first. Subscription-page fare display and affiliate links wait for

  Skyscanner and Trip.com disabled, their code kept.
- **Travelpayouts Support, ticket #257588 (2026-11-23):** travel platforms and online services are
  accepted (no blog required); the project is currently ineligible for some programs, including
  Trip.com; three consecutive months of stable traffic are recommended before another review;
  **affiliate links are permitted in opt-in flight-price alert emails and registered users'
  dashboards**; once Trip.com is available, official link tools or the Partner Links API may convert
  supported Trip.com URLs; the API converts existing URLs and doesn't build searches. This is not a
  Trip.com approval and doesn't validate our hand-built Aviasales links.
- **Official Aviasales link evidence (owner, dashboard):** the Link Generator produced a partner
  link for `https://www.aviasales.com/search/TPE1412TYO21121` (SubID `b6-3proof`). Its long form
  is `https://tp.media/r?campaign_id=…&marker=…&p=…&sub_id=…&trs=…&u=<encoded destination>`, and `u`
  decodes to exactly our builder's URL. **Our direct `www.aviasales.com/search/…?marker=` format is
  a different format and remains unverified**: not verified are the final redirect, airports and
  dates after it, click and conversion attribution, and whether direct or automatically built links
  are authorized. The options are direct links (only with written confirmation), the Partner Links
  API, or building the `tp.media/r` form ourselves (only with written confirmation).
- **Legacy M1 template blocked:** `EMAIL_TEMPLATE=m1` makes every v2 email `blocked:legacy_m1_template_disabled`
  (no Resend call, no history, no subscription change, no SQS retry). The M1 email showed Data API
  fares with an unmarked 「立即訂購」 link and no source label, which conditions 3 and 4 (§8.5 of the
  spec) don't allow. The legacy renderer is kept, unused.
- **M1 page:** the hard-coded 「近期最低價約 NT$9,325 / NT$5,989」 hints (unsourced, stale) were
  replaced with neutral wording; no amounts remain.
- **Open before any subscription-page activation:** the M1.4 subscriptions API returns
  `fare_check.cheapest_twd` to the signed-in browser even while the page hides it; that needs its
  own review (omit until B6-4, or confirm compliant). The page's link presentation (Aviasales stays

  Partner Links API for affiliate links rather than appending the marker to Aviasales search URLs,
  and says tracking and attribution can't be guaranteed for manually built direct-marker URLs.
- **Decision:** the official Partner Links API is the preferred production integration; direct
  marker URLs are not relied on for production attribution. This is not authorization to deploy or
  enable the integration.
- **B6-3A (offline, this change):** notification-side foundation only. `AFFILIATE_LINK_MODE`
  (`disabled` | `direct` | `partner_api`; the deployed handler treats unset as `disabled`), the
  optional message field `aviasales_partner_url`, a layered validator (`notify2/partnerlinks.py`)

  link lifetime and reuse, determinism, redirect behaviour and attribution.

### 1.4 B6-3B: Partner Links API producer (offline, not enabled)

- **Where:** the fare-check parser (`farecheck/partnerapi.py`, called from `runner.run_parser`).
  After matching, and only if at least one subscription matched, it creates ONE partner link per
  fare offer and attaches it to every recipient's message as `aviasales_partner_url`, then
  enqueues. Any failure enqueues nothing for that offer (no partial queue, no direct-marker
  fallback); the next scheduled fare check tries again. Dry run never calls the API.
- **Destination:** built by `farecheck/searchlinks.py` exactly as the notification builds it
  (route, fare dates, `as_of`, month check), marker removed. `farecheck/searchlinks.py` and
  `farecheck/partnerlinks.py` are byte-identical mirrors of the notify2 modules (the existing
  `subkeys.py` approach); tests check the copies, the 85-case link matrix on both sides, the
  expected destination on both sides and a producer -> notification round trip. A fare outside
  the message month gets no link. `partner_api` requires `NOTIFY_MESSAGE_VERSION=2` (the
  destination depends on `as_of` and `month`).
- **Request:** `POST https://api.travelpayouts.com/links/v1/create` with
  `{trs, marker, shorten: false, links: [{url, sub_id}]}`; `trs` and `marker` as JSON numbers, as
  in the documentation's examples (values with a leading zero are refused); fixed Sub ID
  `fff-alert-v1` (`PARTNER_SUB_ID`, no personal data).
- **Response:** Layer A (HTTP status, JSON, top-level `code`, echoed marker/trs, echoed input URL
  matched by value not position, per-link `code`, `partner_url` type), then Layers B/C (the same
  approved-format check the notification applies). `APPROVED_FORMATS` stays empty, so nothing is
  enqueued in `partner_api` mode until B6-3C.
- **Retry:** at most one retry (fixed 1 s, 5 s per attempt) for timeout/network errors, 429 and
  5xx, and only with ≥ 15 s of Lambda time left. Never for 400/401/403, a per-link failure or an
  invalid response.
- **Settings (fare check):** `AFFILIATE_LINK_MODE` (default `disabled`; only `partner_api` changes
  anything), `TP_MARKER` and `TP_TRS` (required and validated in `partner_api`; never logged or
  printed), `PARTNER_SUB_ID`. The existing SSM token handling is reused; no IAM change.
- **API authorization gaps (B6-3C):** the documentation says an API token is required but does
  not say how it is sent (no header, parameter or example). `CONFIRMED_AUTH_HEADER` is `None`, so
  the client refuses to call (`auth_method_unconfirmed`); it is set only from a written
  confirmation or a controlled dry run. Also undocumented: whether string ids are accepted, the
  429 body, link lifetime/expiry, whether identical input returns an identical link, and whether a
  link may be cached and reused across recipients and runs (we reuse one link per offer per run
  only; the notification pins one link per fare event).
- **Global rate limit — B6-3C/B3 activation blocker.** The documented limit is 100 requests per
  minute per marker. One run fans out up to `MAX_WORK_ITEMS=500` asynchronous parser invocations
  at once; each matched offer makes one request plus at most one retry (≤ 1,000), and Lambda's
  asynchronous retries of a failed invocation can repeat that; any future consumer of the marker
  (e.g. B6-4) shares the same budget. One request per invocation does not bound the rate, and
  Reserved Concurrency alone doesn't either (it caps simultaneity, not requests per minute).
  Today a burst fails closed (429 -> nothing enqueued for that offer, retried next run), which is
  safe but can delay or miss alerts. The smallest enforceable global limit is a shared per-minute
  counter (a conditional DynamoDB `UpdateItem` that refuses past the limit) consulted before every
  request; the fare check is read-only on DynamoDB by design, so this needs an IAM and design
  change outside B6-3B. Until such a limit exists, `partner_api` must not be activated.

### 1.1 Route verification classes

Two codes being listed in a platform's `verified_codes` does **not** mean that combination was
opened in a browser. Each platform-route pair is in exactly one class:

| Class | Meaning | Routes today |
|---|---|---|
| **BROWSER_VERIFIED_ROUTE** | This exact route was opened in a browser (2026-11-06) | Skyscanner: **TPE → TYO**, **RMQ → OKA** (TWD prices not confirmed: bot check). Trip.com: **TPE → TYO**, **RMQ → OKA**, **KHH → OKA**. Aviasales: **TPE → TYO** (link format only) |
| **VERIFIED_CODES_ONLY** | Both codes are in the platform's `verified_codes` (or, for Aviasales, its own catalog), so the app builds an itinerary link, but this combination was never opened | Every other pair of Skyscanner codes TPE, RMQ, TYO, OKA (for example TPE → OKA, RMQ → TYO); every other pair of Trip.com codes TPE, KHH, RMQ, TYO, OKA (for example KHH → TYO, TPE → OKA); every other Aviasales route |
| **UNVERIFIED** | A code is not in `verified_codes`; the app shows that platform's general search page | Everything else (for example any KHH route on Skyscanner, any LON route on Skyscanner or Trip.com) |

Google Flights has no route links (a general page by design). **Affiliate attribution stays NOT
VERIFIED** for every route, including the browser-verified Aviasales one (§4).

## 2. B6-1 (this change): offline only

| Item | What changed |
|---|---|
| Departure-month defence | `searchlinks.build(..., month=None)` (Python, keyword-only) and `buildSearchLinks(..., { month })` (TypeScript). When a month is given, a fare whose departure date isn't in that month (year **and** month compared) gets general search pages only, reason `fare_outside_subscribed_month`; a malformed month gives `invalid_subscribed_month`. The labelled Aviasales affiliate link stays (as its general page), so the email/page remains compliant. Both default to no check, so earlier callers are unchanged |
| Where the month comes from | No new month logic. Email: the message's `month` field, the scheduler's resolved effective month (the same field `keys.resolve_month` reads; M1-shape messages have none, and their month would be derived from the departure date itself, so there is nothing independent to compare). Page: the API's `effective_month` (subscriptions API, shared month rules: fixed month, or next month in Asia/Taipei for a legacy rolling row) |
| Why it's defence in depth | The fare check already rejects offers outside the requested month (`farecheck/travelpayouts.py`, `wrong_month`). B6-1 makes the link layer refuse an itinerary link even if a mismatched fare reaches it (bug, stale record, or a legacy row viewed after the month rolled over) |
| Notification month guard | The v2 notification no longer relies on the producer alone. `keys.resolve_month` (called first in `service.process`) rejects a message that names a `month` but whose fare departs in another year-month, or whose departure date is missing or malformed: `InvalidMessage`, so the SQS handler drops it (no retry) before any history read or write, rendering or Resend call, and subscriptions are untouched. The date is parsed with the link builder's `parse_day`. M1-shape messages (no month) are unchanged. Tests: `aws/tests/test_m14_notify_month_guard.py` |
| Shared test matrix | `aws/tests/vectors/search-links-matrix.json` (85 deterministic cases), run by `aws/tests/test_b6_link_matrix.py` and `src/lib/m14/search-links.matrix.test.ts`. Expectations were written from the spec rules, independently of the builders |
| Manual checklist generator | `aws/tools/b6_link_checklist.py`: offline Markdown checklist for §3 below |
| B5 record | [m1.4-b5-results.md](m1.4-b5-results.md): owner-reported, not independently verified |

## 3. Manual browser verification (B6-2, not started)

Generate the list locally (no network, no marker, nothing opened):

```
python3 aws/tools/b6_link_checklist.py --today 2026-11-23 --out b6-checklist.md
```

- Defaults: TPE, KHH, RMQ × TYO, OSA, SEL, OKA, HKG, BKK, SIN, LON, NYC, SYD × month offsets
  1, 6 and 12. Override with `--origins`, `--destinations`, `--months`.
- Each platform-route pair is labelled with its §1.1 class: **BROWSER_VERIFIED_ROUTE** (only the
  exact routes listed there, kept in the tool's `BROWSER_VERIFIED_ROUTES`), **VERIFIED_CODES_ONLY**
  (codes verified, combination never opened: still to check by hand) or **UNVERIFIED** (the app
  shows the general page; a candidate itinerary URL is printed for checking only). The class is
  never inferred from `verified_codes` alone. Google is a general page by design.
- Aviasales URLs are printed **without** a marker, so opening one credits nobody; every Aviasales
  row states that affiliate attribution is NOT VERIFIED.
- Priority for the manual pass: anything that could send a user to the **wrong airport** (Skyscanner
  `TPE` = Taoyuan only?, Skyscanner city entity codes such as `tyoa`), the **wrong month**
  (Trip.com silently moves past dates; far months 11–12 on every platform) or an **untracked
  affiliate URL** (B6-3).
- Results go into `search-platforms.json` `verified_codes` with a date, and newly opened routes
  into the tool's `BROWSER_VERIFIED_ROUTES` with their evidence, in a later PR (B6-2).

   verified against the current requirements, roll back by suspending delivery (disable the SQS
   Event Source Mapping): [m1.4-b3-suspension-rollback.md](m1.4-b3-suspension-rollback.md).

    links aren't relied on for production attribution. `partner_api` stays blocked until a link
    format is approved from a controlled API dry run, the authentication method is confirmed and
    an enforceable global rate limit exists (§1.4). The producer side exists offline (B6-3B).
11. **Information minimisation (before B6-4 production activation).** `aws/config/search-platforms.json`
    is embedded in the Production JavaScript bundle (inert data; the M1.4 code is excluded). Before
    B6-4 enables links in Production, the Production bundle must carry only required public values:
    no credentials, no internal compliance or review notes, no browser-verification metadata
