- **Status:** code and offline tests, 2026-11-11. **Not deployed.** The M1 notification Lambda
  (`aws/lambdas/flight-fare-notification/index.py`) is unchanged and is what runs in production.
- **Closes in code:** release blocker B1 (month-aware deduplication). B1 stays **OPEN** until
  the owner approves and deploys it ([plan](m1.4-plan.md#m14-release-blockers)).
- **Code:** `aws/lambdas/flight-fare-notification-v2/` (`handler.py`, package `notify2/`),

## 1. Current M1 behaviour (verified 2026-11-11)

Verified from the deployed source, the stack builder and read-only `DescribeTable` /
`GetQueueAttributes` calls (no items read):

| Item | M1 today |
|---|---|
| Dedup key | `notification_history.pk = "{email}#{route}"`, sort key `sent_at` (ISO-8601 with offset, ms). One stream per **user and route**; departure month plays no part |
| Rule (`should_send`) | Send if there is no earlier row, or the newest row is at least `NOTIFY_FLOOR_HOURS` old (deployed: **24**), or the fare is at least `REALERT_PCT` (**20 %**) below the last alerted price, or at least `REALERT_ABS_TWD` (**NT$2,000**) below it |
| Order of operations | Query newest row → decide → POST to Resend → `put_item` the history row only after a 2xx. Not atomic |
| Failures | Resend 429/5xx or an exception → message retried (partial-batch failure); other 4xx → dropped |
| Table | `pk` (S, hash) + `sent_at` (S, range), on-demand, **no TTL**, no index; each row stores the raw `email`, `route`, `price` |
| Trigger | `flight-fare-queue`, batch 5, `ReportBatchItemFailures`; Lambda timeout 30 s; queue visibility 180 s; **no dead-letter queue** (retention 4 days) |

Gaps this phase fixes:
- **No month in the key.** A January alert suppresses February and March for 24 hours (B1).
- **Race.** Two concurrent invocations for one user and route can both read "no recent
  alert" and both send.
- **Crash window.** If the Lambda dies after Resend accepts the email but before `put_item`,
  the redelivered message sends a second email.
- **Email as the key.**
- **Poison messages.** A malformed message raises and is retried until it expires (4 days).

## 2. Architecture

```
parser (Phase 2A) --SQS--> notification v2
  message: M1 shape [+ "month", "as_of" with NOTIFY_MESSAGE_VERSION=2]
                              |
                              |- validate (malformed -> dropped, never retried forever)
                              |- stream = (subscriber_id, route, month)
                              |- read v2 state (consistent) [+ genuine M1 rows in the 24 h window]
                              |- M1 rule within the stream -> skip?
                              |- claim the stream (conditional write)
                              |- re-check the subscription row (paused/expired/edited/deleted -> skip)
                              |- Resend POST with Idempotency-Key = event id
                              '- commit (transaction: state + log [+ M1-shape copy]) or release
```

Rendering is the M1 email, byte for byte; a parity test compares it with the M1 Lambda. The
wording and search links are Phase 2B-2.

## 3. Deduplication key design

| Part | Value |
|---|---|
| `subscriber_id` | `"s1_" + HMAC-SHA256(pepper, lower(trim(email)))[:32 hex]`. Pepper: SSM SecureString `/flight/dedup-pepper` (at least 32 characters) |
| Stream key | `pk = "v2#{subscriber_id}#{ORIGIN}-{DEST}#{YYYY-MM}"` |
| State item | `(pk, sent_at = "STATE")`: `last_sent_at`, `last_price`, `last_event_id`, `version`, `sends`, `route`, `month`, `subscriber_id`, and while a send is in progress `claim_event`, `claim_expires` (epoch s) |
| Log item | `(pk, sent_at = "<ISO UTC ms>")`: `route`, `month`, `price`, `event_id`, `subscriber_id`; **no email** |
| Effective month | The `month` field (scheduler-resolved, v2 messages); otherwise the fare's departure month `cheapest.depart_date[:7]`, which Phase 2A validation guarantees equals the work item's month |
| Event id | `sha256({pk, price, depart, return, airline, as_of or SQS messageId})[:40]`. With `as_of`, a re-run of one schedule is one event; without it, a redelivered SQS message is one event |
| Resend key | `Idempotency-Key: flight-fare/{event id}` (Resend keeps keys 24 h) |

**Why HMAC of the address and not a "user ID".** No subscription row has a user-id attribute
today:
- M1 and Phase 1B rows are keyed `(email, route)`, and the Phase 1B API identifies users by
  their verified Supabase email.
- A Supabase user UUID would need a new attribute on every row plus a backfill. M1 rows can't be
  backfilled without Supabase admin access, which the project rules forbid.
- Changing identity mid-stream would reset deduplication.

The HMAC is stable for every existing row, isn't the address, and can't be reversed or
dictionary-matched without the pepper. Different addresses give different streams, so users
can't suppress each other. **Owner decision:** keep the HMAC, or plan a later migration to
Supabase user IDs.

## 4. Behaviour

- **Within a stream (same user, route, month):** exactly the M1 rule (24 h floor; 20 % or
  NT$2,000 re-alert). A parity test runs both implementations on the same cases.
- **Different months:** independent streams (KHH→TYO 2027-01, 2027-02 and 2027-03 each alert on
  their own).
- **Different users:** independent streams.
- **Legacy rolling rows:** the scheduler resolves their month (next month, Asia/Taipei, at
  `as_of`). An M1-shape message is placed by its departure month.
- **Month end:** the subscription re-check uses the message's `as_of` (the scheduler's single
  Asia/Taipei instant), not the Lambda's clock.
  - A message from a 23:59:59 run processed at 00:00:01 still goes to its month's stream.
  - The first run after midnight starts the next month's stream for rolling rows.
  - An M1-shape message without `as_of`, processed after midnight, is skipped as
    `month_changed` rather than sent for a month the rolling row no longer means.
- **Re-check before sending** (`RECHECK_SUBSCRIPTION`, default on). Consistent `GetItem` of the
  subscription. It skips when the row is gone, expired at `as_of`, paused, now means another
  month, or now has a target below the fare. This is stricter than M1, never looser.
- **No data:** the fare check sends no message, so nothing reaches this Lambda (tested end to
  end with the Phase 2A parser).
- **Malformed message:** dropped and logged (M1 retried it until expiry).

## 5. Concurrency and idempotency

| Threat | Protection |
|---|---|
| Two invocations, same stream | `claim` is a conditional `UpdateItem`: no state yet, or same `version` and no live claim. The loser gets `ClaimConflict` → message retried → on redelivery it sees the committed send and the M1 rule decides (usually skipped). Tested with 12 parallel threads: exactly one email |
| Decision on a stale read | The claim's `version = :v` condition fails if anyone committed or claimed since the read |
| Duplicate SQS delivery | Same messageId (or same `as_of`) → same event id → `last_event_id` match → skipped |
| Crash after Resend, before commit | The claim stays until it expires (120 s), which is before SQS redelivers (visibility 180 s). The redelivery uses the same Resend Idempotency-Key, so Resend replays the original result without sending again; then the commit happens. Tested: one email, two requests, same key |
| Claim expired while a worker was stalled | The commit's condition fails → a monotonic state update (never moves `last_sent_at` backwards) and the log rows are still written (`sent:claim_lost`) |
| Resend 429 / 5xx / 409 concurrent / network | Claim released, message retried (M1 semantics) |
| Resend 409 `invalid_idempotent_request` | Treated as already sent (that key was used), then committed |
| Resend other 4xx | Claim released, dropped, no history row (M1 semantics) |
| Other users | The key includes `subscriber_id`; nothing is shared across users |

Timing invariant (checked by `Settings`): Lambda timeout (30 s) < `CLAIM_SECONDS` (120) < queue
visibility (180 s).

## 6. Backward compatibility and migration

- **Existing M1 history is honoured.** Before deciding, v2 reads the newest *genuine* M1 row
  for `{email}#{route}` within the last `NOTIFY_FLOOR_HOURS`. If that M1 alert was about this
  stream's month, it counts as the previous alert. "About this month" means next month at send
  time by the UTC calendar (M1's parser) or by Asia/Taipei, at send time and one hour before.
  Older rows can't suppress anything under the M1 rule. So switching to v2 doesn't resend
  within 24 hours, and an M1 alert about December doesn't suppress January.
- **Rollback safety (`LEGACY_DUAL_WRITE`, default on).**
  - Every v2 send also writes an M1-shape row (`pk = "{email}#{route}"`, `sent_at`, `email`,
    `route`, `price`, plus `source = "v2"` and `month`).
  - If the M1 Lambda is restored, it finds that row and keeps its 24-hour suppression. A test
    shows that without this the M1 Lambda would resend.
  - v2 ignores rows marked `source = "v2"` when reading M1 history, so its own copies never
    suppress another month (a bug found and fixed during testing).
- **Roll-forward after a rollback:** M1 rows written during the rollback are newer than the v2
  state and are honoured (tested).
- **Existing rows are never modified or deleted.** Existing subscription rows, keys and the
  Phase 1B API are untouched.
- **Messages:** v2 accepts the M1 shape (current parser) and the v2 shape. The M1 Lambda
  ignores the two extra v2 fields, so the parser can switch to `NOTIFY_MESSAGE_VERSION=2` at any
  time after Phase 2A is deployed.

## 7. Deployment changes needed later (none made; each needs approval)

1. **SSM parameter** `/flight/dedup-pepper` (SecureString, at least 32 random characters,
   generated by the owner; never in the repository). The role already reads `/flight/*`. If it
   is missing, the Lambda fails closed: every message is retried and none is sent.
2. **Package-deploy** `flight-fare-notification` from `package_notification_v2.py`: handler
   `handler.handler`, the same role, trigger, timeout and `CITIES`/`AIRLINES` variables. This is
   a template change to `flight-m1-email-on-target`; the code no longer fits inline.
3. **Environment:** keep `NOTIFY_FLOOR_HOURS`/`REALERT_PCT`/`REALERT_ABS_TWD`/`RESEND_PARAM`;
   add `DEDUP_PEPPER_PARAM`, and optionally `CLAIM_SECONDS=120`, `LEGACY_HISTORY_READ=1`,
   `LEGACY_DUAL_WRITE=1`, `RECHECK_SUBSCRIPTION=1`.
4. **IAM:** none expected. `flight-lambda-role` already allows `GetItem`, `Query`, `PutItem` and
   `UpdateItem` on `notification_history` and `GetItem` on `subscriptions` (checked read-only
   2026-11-06); `TransactWriteItems` is authorised by those item-level actions. Re-verify with
   the IAM policy simulator before deploying.
5. **No table change:** same keys and attribute types; new items only. Optional and
   recommended:
   - a TTL attribute for log items (the table has no TTL today and grows forever);
   - a **dead-letter queue** for `flight-fare-queue` (`maxReceiveCount` about 5).
6. **Order:**
   1. pepper;
   2. deploy v2 while the parser still sends M1-shape messages;
   3. watch the logs;
   4. later, after the Phase 2A parser is deployed, set `NOTIFY_MESSAGE_VERSION=2`.

   Keep `LEGACY_DUAL_WRITE` on for at least the rollback window plus 24 hours.

## 8. Rollback

Redeploy the M1 inline code (the unchanged `index.py`, same stack). Nothing needs undoing in
data:
- M1 reads `{email}#{route}`, where v2's copies keep suppression working;
- M1 ignores `v2#…` items;
- extra message fields are ignored.

Roll-forward later honours anything M1 sent in between. The only lost property during a
rollback is month-awareness itself, which is M1's existing behaviour.

## 9. Known risks and open questions

1. **Identity choice:** HMAC of the address (above) instead of a Supabase user id. Owner to
   confirm. Rotating the pepper resets every stream (one possible extra alert per stream), so
   it is never rotated casually.
2. **M1-shape messages at month end:** they may be skipped as `month_changed` in the first
   minutes after midnight on the 1st. That means one missed alert, never a wrong one. It
   disappears with `NOTIFY_MESSAGE_VERSION=2`.
3. **Resend key window is 24 h.** A message stuck longer than that between send and commit
   could send twice. That would need the claim to expire, SQS redelivery to keep failing for 24
   hours and the commit to fail every time. Very unlikely; a DLQ (item 5 above) would bound it.
4. **Existing M1 rows contain addresses** in `pk` and `email`, and v2's rollback copies do too.
   Removing them needs a later privacy clean-up after the rollback window (not in this phase).
5. **No TTL / no DLQ** today (recommended above).
6. **Re-check reads `subscriptions`** with a consistent `GetItem` per send attempt. That is
   cheap, but it is a new read on the send path.
7. B1 stays OPEN until approval and deployment.
