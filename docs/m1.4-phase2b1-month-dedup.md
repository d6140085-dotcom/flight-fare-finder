## 1. Current M1 behaviour (verified 2026-11-11)

Verified from the deployed source, the stack builder and read-only `DescribeTable` /
`GetQueueAttributes` calls (no items read):

| Item | M1 today |
|---|---|
| Dedup key | `notification_history.pk = "{email}#{route}"`, sort key `sent_at`. One stream per **user and route**; the departure month plays no part |
| History row | Exactly `pk`, `sent_at` (`datetime.isoformat(timespec="milliseconds")` in UTC, e.g. `2026-11-20T04:00:00.000+00:00`), `email`, `route`, `price` (TWD). **No departure month, no fare dates, no target** |
| Rule (`should_send`) | Send if there is no earlier row, or the newest row is at least `NOTIFY_FLOOR_HOURS` old (deployed: **24**), or the fare is at least `REALERT_PCT` (**20 %**) below the last alerted price, or at least `REALERT_ABS_TWD` (**NT$2,000**) below it |
| Order of operations | Query newest row → decide → POST to Resend (10 s client timeout) → `put_item` the row only after a 2xx. Not atomic |
| Failures | Resend 429/5xx or an exception → message retried (partial-batch failure); other 4xx → dropped |
| Table | `pk` (S, hash) + `sent_at` (S, range), on-demand, **no TTL**, no index |
| Trigger and queue | `flight-fare-queue`, batch 5, `ReportBatchItemFailures` on; Lambda timeout 30 s; visibility 180 s (= 6 × timeout); retention 4 days; **no dead-letter queue** |

Gaps this phase fixes:
- **No month in the key** (B1).
- **Read-then-write race:** two invocations for one user and route can both send.
- **Crash window:** a crash between Resend accepting the email and `put_item` means the
  redelivered message sends again.
- **Email as the key.**
- **Poison messages:** malformed messages are retried until they expire.

## 2. Architecture

```
parser (Phase 2A) --SQS--> notification v2 (per message, inside a time budget)
  message: M1 shape [+ "month", "as_of" with NOTIFY_MESSAGE_VERSION=2]
     |- validate (malformed -> dropped, never retried forever)
     |- stream = (subscriber_id, route, month); event id
     |- duplicate event? -> skip      stale (> 20 h)? -> skip, or record its own earlier attempt
     |- read v2 state [+ genuine M1 rows of the route, last 24 h]
     |- M1 rule within the stream -> skip?
     |- claim the stream (conditional write; re-entrant for the same event)
     |- re-check the subscription row (paused/expired/edited/deleted -> skip)
     |- Resend POST with Idempotency-Key = event id
     '- commit (transaction: state + log [+ M1-shape copy]) | release | keep claim if outcome unknown
```

Rendering is the M1 email, byte for byte (parity test). The wording and search links are Phase
2B-2.

## 3. Identity: HMAC of the address vs the Supabase user id (reviewed)

**What the integration exposes today.** Both endpoints that write subscriptions call
Supabase's `GET /auth/v1/user` with the caller's access token and keep only `email`:
- M1 `flight-save-subscription/index.py`, function `user_email`;
- Phase 1B `subsapi/auth.py`, function `resolve_email`.

That endpoint validates the token server-side, and its response also contains the user's
`id`, the same value as the JWT `sub` claim, which Supabase documents as "The user ID (UUID)".
So the **verified user id is available without the Admin API**: one more field to read from a
response we already fetch. (The first version of this document wrongly implied otherwise.) The
frontend already keys its own cache by `user.id`. No subscription row stores it today:
`subscriptions` is keyed `(email, route)`, and the production table has 2 rows, both M1.

| | A. HMAC of the normalised address (current code) | B. Verified Supabase user id |
|---|---|---|
| Available to the notification path today | Yes: the message carries the recipient address | **No**: neither rows nor messages carry it; needs the API to store `user_id` and the parser to forward it |
| Existing subscription keys | Unchanged | Unchanged (a non-key attribute), but rows need a backfill |
| Backfill of existing rows | None needed | Lazy: set on the user's next authenticated request (no Admin API). Rows of users who never return keep no id, so a fallback is still needed |
| Authentication / authorisation | Unaffected; the address comes from the verified session | Stronger long-term anchor: the immutable id from the same verified call |
| Email-address change | New address → new stream (one possible extra alert). But today the whole subscription is keyed by address, so after a change the user can't see their old rows either: a **subscription-keying** problem, not only a dedup one | Stream survives the change, once rows carry the id; the subscription key problem remains until rows are re-keyed |
| Existing M1 history | Read through the M1 key either way (§6) | Same |
| Migration complexity now | None | API + parser + message change, mixed rows, dual-key dedup reads to avoid a reset |
| Privacy | Pseudonymous, but derived from the address; needs a secret pepper (leak → dictionary-matchable; rotation resets all streams) | Random UUID, no secret, not derived from contact data; still personal data (links to `auth.users`) |
| Long-term maintainability | Secret to manage; identity tied to the address | Matches auth; fewer moving parts once migrated |

**Recommendation for M1.4: A (HMAC) as a temporary, versioned choice; B as the target.**
A is the only option that works for every existing row without touching authentication, the
subscription schema or the API, which this phase must not change, and it introduces no
transition reset. Its weaknesses (secret management, address-derived) are bounded:
- the pepper lives in SSM and is never rotated casually;
- the key is versioned (`s1_`), so a later scheme can coexist.

**Future migration path to B** (separate phase, owner approval):
1. Phase 1B API stores `user_id` (from the `/auth/v1/user` response it already reads) on every
   create and update. That is a new non-key attribute with no key change. Existing rows get it on
   the user's next authenticated write; optionally a read-only "touch" on login.
2. The parser forwards `user_id` in v2 messages when the row has it.
3. Notification v2 computes the primary key `u1_{user_id}` when present and **also reads the
   `s1_` stream** of the same message (dual-read, newest wins). It writes only to `u1_`. No
   alert resets at the transition.
4. After every active row has `user_id` and one `NOTIFY_FLOOR_HOURS` has passed, stop reading
   `s1_`; then retire the pepper.
5. Separately, plan re-keying `subscriptions` by `user_id` so an address change doesn't strand a
   user's subscriptions. That is a larger API and data migration of its own.

## 4. Deduplication key design

| Part | Value |
|---|---|
| `subscriber_id` | `"s1_" + HMAC-SHA256(pepper, lower(trim(email)))[:32 hex]`; pepper: SSM SecureString `/flight/dedup-pepper`, at least 32 characters |
| Stream key | `pk = "v2#{subscriber_id}#{ORIGIN}-{DEST}#{YYYY-MM}"` |
| State item | `(pk, sent_at = "STATE")`: `last_sent_at`, `last_price`, `last_event_id`, `version`, `sends`, `route`, `month`, `subscriber_id`, and during a send `claim_event`, `claim_expires` (epoch s) |
| Log item | `(pk, sent_at = "<ISO UTC ms>")`: `route`, `month`, `price`, `event_id`, `subscriber_id`; no address |
| Effective month | The `month` field (scheduler-resolved, v2 messages); otherwise the fare's departure month `cheapest.depart_date[:7]`, which Phase 2A validation guarantees equals the work item's month |
| Event id | `sha256(JSON{pk, price, depart, return, airline, as_of, delivery})[:40]`, where `delivery` is the SQS messageId only when there is no `as_of`. Deterministic: same message → same id; with `as_of`, a re-run of one schedule → same id; a different fare → a different id |
| Resend key | `Idempotency-Key: flight-fare/{event id}` (46 characters; Resend allows up to 256) |

## 5. Behaviour

- **Within a stream:** exactly the M1 rule (parity test).
- **Different months:** independent streams. **Different users:** independent streams.
- **Legacy rolling rows:** the month is resolved by the scheduler (next month, Asia/Taipei, at
  `as_of`). M1-shape messages use the departure month.
- **Month end:** the subscription re-check uses the message's `as_of`. An M1-shape message (no
  `as_of`) processed after midnight on the 1st is skipped as `month_changed` instead of being
  sent for a month the rolling row no longer means.
- **Re-check before sending** (default on): skips when the row is gone, expired, paused, now
  means another month, or now has a target below the fare.
- **No data:** no message, so nothing reaches this Lambda (end-to-end test).
- **Malformed message:** dropped and logged.

## 6. M1 history: how old rows are interpreted (reviewed)

**What the schema allows.** An M1 row is exactly `{pk: "{email}#{route}", sent_at, email,
route, price}` (§1; a test runs the real M1 code and checks the row). There is **no departure
month and no fare date**, so the month an M1 alert was about cannot be established from the
data. The first version inferred it ("next month at send time"). That inference is dropped:
M1's parser never checked that the fare it used departed in the requested month, so the
inference could have been wrong, and a wrong inference could resend within 24 hours.

**Rule now:** the newest *genuine* M1 row for the user and route sent within the last
`NOTIFY_FLOOR_HOURS` is treated as the previous alert of **every** month stream of that route.

| Case | Behaviour |
|---|---|
| Recent M1 row (< 24 h) | Every month of that route is suppressed by the M1 rule; only a 20 % or NT$2,000 drop re-alerts (as M1 would) |
| M1 row ≥ 24 h old | Ignored (M1 itself would send again) |
| Row without a usable price | The 24 h floor still applies; no price-drop re-alert against an unknown price |
| Row whose `sent_at` isn't an ISO timestamp with an offset | Ignored: M1 can't write such a row (test) |
| v2's own rollback copies (`source = "v2"`) | Ignored (v2 state covers them); a genuine M1 row behind a newer copy is still found |
| Another user's or another route's rows | Never consulted |

- **Can switching to v2 resend within 24 h?** **No.** It is tested for M1 rows 0.01 to 23.9 h
  old, several months and prices. The cost is that, during the one-time switch-over, the
  first alert of a *different* month of the same route can be delayed by up to 24 hours after
  the last M1 alert.
- **Rollback with several months.** v2 may have sent December and January for one route within
  24 hours; each send also wrote an M1-shape copy.
  - The restored M1 Lambda sees the newest copy and suppresses the route for 24 hours (its own
    route-level behaviour).
  - Once M1 sends again, a roll-forward treats that genuine M1 row as covering every month of the
    route for 24 hours.

  Both are tested end to end with the real M1 code.

## 7. Delivery guarantees (Resend idempotency reviewed)

Resend's documented behaviour:
- `Idempotency-Key` header, 1–256 characters, "kept in the system for 24 hours";
- same key and payload → "the same response, without actually sending the email again";
- same key with a different payload → `409 invalid_idempotent_request`;
- a request still in progress → `409 concurrent_idempotent_requests`, safe to retry later.

The documentation does not say whether a *failed* first request (429/5xx) consumes the key.

| Case | Handling | Result |
|---|---|---|
| Duplicate SQS delivery (same messageId) | Same event id; `last_event_id` match | Skipped |
| Parser re-run of one schedule (v2 message, same `as_of`) | Same event id | Skipped |
| Crash after Resend accepted, before the commit | Claim kept. The redelivery of the same event re-enters it (re-entrant claim) and sends with the same key; Resend replays; commit | **One email** (test: two requests, identical payload and key) |
| Response lost / timeout / 5xx / `409 concurrent` | Outcome **unknown**: claim kept, message retried. Other events for the stream wait (Retry) while the claim is live | One email if the same message resolves it first |
| `409 invalid_idempotent_request` | Treated as already sent; committed without a new email | No duplicate. If the earlier request with that key actually failed, this is one missed alert (Resend doesn't document whether failed requests keep the key) |
| 429 | Rejected before processing: claim released, retried | No duplicate |
| Other 4xx | Claim released, dropped, nothing recorded (M1) | No email |
| Retry after more than 24 h | Messages older than `MAX_MESSAGE_AGE_HOURS` (**20**, must be < 24) are never sent: from `as_of`, else the SQS `SentTimestamp`. If the stale message is its own earlier attempt, it is **recorded as a possible send** without sending | Every real send attempt for an event happens within 20 h of its creation, inside Resend's window. A message that kept failing past 20 h costs at most one missed alert |
| Payload stability | The email depends only on the message, `CITIES`/`AIRLINES` and the `from` address | Stable across retries unless configuration changes between attempts; then Resend answers `409 invalid` (handled above) |

**Guarantee, stated precisely: at most one email per fare event**, and the M1 rule within each
stream. This holds under duplicate deliveries, concurrent invocations and crashes, as long as
retries happen within Resend's 24-hour window (enforced by the 20-hour age limit).

**Not exactly-once.** Remaining edges:
1. An event can be **missed** (never duplicated) when:
   - its message expires or goes to a DLQ;
   - it is older than 20 h;
   - Resend answers `409 invalid_idempotent_request` after a failed first attempt.
2. **Two different events of one stream can both send** when all of these happen: an attempt
   ends with an unknown outcome **and actually sent**; its claim expires (`CLAIM_SECONDS`)
   before the same message is redelivered; and a *different* event for the same stream arrives
   in that gap.

   The window is the gap between claim expiry and redelivery. Keeping the claim on unknown
   outcomes and making it re-entrant narrows it, but it is not zero. The result would be at most
   one extra alert within the floor.
3. **A stalled worker can still send after losing its claim.** If a worker stalls longer than
   `CLAIM_SECONDS`, its commit finds the claim gone; the send is recorded anyway
   (`claim_lost`). A second worker could have sent a different event meanwhile, which is the
   same edge as item 2.

## 8. SQS reliability (reviewed)

| Setting | Today | Assessment | Required for deployment |
|---|---|---|---|
| Lambda timeout | 30 s | A batch of 5 with up to 10 s per Resend call (plus DynamoDB) can exceed 30 s; a timed-out batch returns entirely. Safe for correctness (redeliveries are skipped or re-enter their claims) but noisy | **60 s**; the handler also stops starting messages with < 15 s left and reports them as failures (implemented) |
| Visibility timeout | 180 s | AWS: at least 6 × function timeout | **360 s** with a 60 s timeout |
| Claim expiry | 120 s (code default) | Must be > Lambda timeout and < visibility, so a dead worker's claim frees before the redelivery (checked by `Settings`) | **`CLAIM_SECONDS=180`**, `LAMBDA_TIMEOUT_SECONDS=60`, `QUEUE_VISIBILITY_SECONDS=360` |
| Batch size | 5 | Fine with the time budget | Keep 5 (or 1–2 for the first days) |
| Partial batch responses | `ReportBatchItemFailures` on | Without it, one failure would retry the whole batch | **Mandatory** (keep) |
| Retry handling | Retry on 429/5xx/unknown/claim conflict; drop malformed and other 4xx | Correct | — |
| Dead-letter queue | **None**: a failing message cycles for 4 days | Needed to bound retries (and therefore the stale-message window) and to surface failures | **Mandatory**: DLQ with `maxReceiveCount` **≥ 5** (AWS recommends at least 5; 10 suggested, ≈ 1 h at 360 s) and a CloudWatch alarm on DLQ depth. A DLQ'd message is a missed alert, never a duplicate |
| Message retention | 4 days | Longer than the 20 h age limit; anything older is skipped anyway | Keep; DLQ retention 14 days |

## 9. Deployment blockers (none done; each needs approval)

1. **Pepper:** SSM SecureString `/flight/dedup-pepper` (owner-generated, at least 32 random
   characters; never in the repository). The role already reads `/flight/*`. Without it the
   Lambda fails closed (every message retried, nothing sent).
2. **DLQ + alarm** on `flight-fare-queue` (§8): mandatory.
3. **Timeouts:** Lambda timeout 60 s, queue visibility 360 s, and the environment `CLAIM_SECONDS=180`,
   `LAMBDA_TIMEOUT_SECONDS=60`, `QUEUE_VISIBILITY_SECONDS=360`.
4. **Package-deploy** `flight-fare-notification` from `package_notification_v2.py`
   (`handler.handler`; the same role, trigger with `ReportBatchItemFailures`, `CITIES`/`AIRLINES`).
   This is a template change to `flight-m1-email-on-target`.
5. **IAM:** none expected (the role allows `GetItem`, `Query`, `PutItem` and `UpdateItem` on
   `notification_history` and `GetItem` on `subscriptions`). Re-verify with the policy simulator,
   including `TransactWriteItems`.
6. **Identity decision** (§3): accept HMAC for M1.4 or schedule the user-id migration first.
7. **Order:** pepper → DLQ and timeouts → v2 with M1-shape messages → after the Phase 2A deploy,
   `NOTIFY_MESSAGE_VERSION=2`. Keep `LEGACY_DUAL_WRITE` on for at least the rollback window plus
   24 hours.

Recommended, not blocking: a TTL attribute for v2 log items (the table has no TTL and grows
forever).

## 10. Rollback

Redeploy the unchanged M1 inline code (same stack). Nothing needs undoing in data:
- M1 reads `{email}#{route}`, where v2's copies keep suppression working;
- M1 ignores `v2#…` items;
- the extra message fields are ignored.

Roll-forward honours anything M1 sent in between (§6). During a rollback the system has M1's
behaviour: no month-awareness, and the M1 race and crash windows.

## 11. Remaining risks and open questions

1. Identity (§3): the owner's decision; the pepper is never rotated casually.
2. The delivery edges in §7 (bounded; at most one extra alert or one missed alert per edge).
3. During the switch-over, another month's first alert can be delayed by up to 24 h (§6).
4. M1-shape messages around midnight on the 1st may skip one alert (gone with v2 messages).
5. Existing M1 rows and v2's rollback copies contain addresses. Plan a privacy clean-up after
   the rollback window.
6. The re-check adds one consistent `GetItem` on `subscriptions` per send attempt.
7. B1 stays OPEN until approval and deployment.
