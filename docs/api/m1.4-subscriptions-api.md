# M1.4 subscriptions API — contract

- **Status:** specification for review (Phase 1A, revised 2026-11-05). Not deployed; no AWS
  resources exist for it yet.
- **Implements:** [ADR 0001](../adr/0001-m1-4-dynamic-routes.md) decisions D1–D6, D9, D11–D14.
- **Prototype:** `src/lib/m14/subscriptions.ts` and `src/lib/m14/months.ts` follow these shapes,
  rules and error codes, so the Phase 1B client can replace the prototype's in-memory reducer
  without UI changes.
- **Executable reference for §5:** `aws/reference/subscriptions_quota.py`, tested under every
  interleaving of concurrent requests by `aws/tests/test_m14_quota_model.py`.

## 1. Overview

| | |
|---|---|
| Base URL | The existing HTTP API `flight-api` (`VITE_FLIGHT_API_URL`), region `ap-southeast-2` |
| Handler | New Lambda `flight-subscriptions-api`, role `flight-subscriptions-api-role` (`subscriptions` + `subscription_quota` tables only) |
| Format | JSON, UTF-8. Prices are whole TWD integers. Times are ISO-8601 UTC strings. Months are `YYYY-MM` |
| Existing endpoints | `POST /subscribe` and `GET /subscriptions` (M1.1). **Production routing is not changed by this contract yet**; the cutover is one reviewed change set (§8.3) |

| Method & path | Purpose | Success |
|---|---|---|
| `GET /subscriptions` | List the caller's subscriptions | `200` |
| `POST /subscriptions` | Create a subscription | `201` |
| `PATCH /subscriptions/{route}` | Change target, departure month, pause/resume, and/or origin and destination | `200` |
| `DELETE /subscriptions/{route}` | Delete a subscription | `204` |
| `POST /subscribe` (legacy, M1) | Upsert one of the two fixed plans | `200` — after cutover, served by the same handler and quota path (§8.2) |

`GET /subscriptions` moves to the new handler at cutover; its response is a superset of today's,
so the current `/app` page keeps working.

## 2. Authentication

- Every request needs `Authorization: Bearer <Supabase access token>` from the signed-in session.
- The Lambda resolves the user by calling Supabase `GET /auth/v1/user` with the project's
  publishable key, exactly as M1.1 does. The **email from Supabase** (trimmed, lower-cased) is
  the user key. Any `email` field in a request body or query is **ignored**.
- Missing, malformed, expired or rejected tokens → `401 unauthorized`. Nothing is read or written.
- Direct IAM-authorized invocations (no API Gateway context) may pass `test_email` for testing,
  as in M1.1. API Gateway requests always carry a request context, so this path can't be reached
  from the internet.
- CORS: existing origins and headers; `AllowMethods` gains `PATCH` and `DELETE`.

## 3. Resources

### 3.1 Subscription

```json
{
  "route": "TPE-TYO",
  "origin": "TPE",
  "destination": "TYO",
  "origin_name": { "zh": "台北", "en": "Taipei" },
  "destination_name": { "zh": "東京", "en": "Tokyo" },
  "departure_month": "2027-03",
  "month_mode": "fixed",
  "effective_month": "2027-03",
  "status": "active",
  "target_price": 9000,
  "currency": "TWD",
  "alerts_paused": false,
  "plan_name": null,
  "created_at": "2026-11-05T03:00:00Z",
  "updated_at": "2026-11-05T03:00:00Z"
}
```

| Field | Type | Notes |
|---|---|---|
| `route` | string | `ORIGIN-DESTINATION`; the DynamoDB sort key; **one per user per route pair** |
| `origin`, `destination` | string | IATA city or airport code from `aws/config/airports.json` |
| `origin_name`, `destination_name` | object | From the allowlist; `null` if a stored code is no longer listed |
| `departure_month` | string \| null | Stored. `YYYY-MM` for fixed-month rows; **absent/null = legacy M1 rolling row** |
| `month_mode` | `"fixed"` \| `"rolling"` | Derived: `rolling` exactly when `departure_month` is absent |
| `effective_month` | string | Derived: the month fares are checked for — `departure_month`, or next month (Asia/Taipei) for rolling rows |
| `status` | `"active"` \| `"paused"` \| `"expired"` | Derived at read time (§3.3); never stored |
| `target_price` | integer | TWD, `min`–`max` from `aws/config/subscription-policy.json` (1–1,000,000) |
| `currency` | string | Always `"TWD"` |
| `alerts_paused` | boolean | Stored only when `true`; an absent attribute means not paused |
| `plan_name` | string \| null | Present only on M1 fixed-plan rows (`tokyo`, `seoul`); `null` otherwise |
| `created_at`, `updated_at` | string | `updated_at` is also the optimistic-concurrency token (§4.3) |

### 3.2 Departure month rules

Policy (`subscription-policy.json` → `departure_month`): format `YYYY-MM`, time zone
`Asia/Taipei`, first selectable month = **next month**, window = **12 calendar months**.
On 2026-11-05 the selectable months are `2026-12` … `2027-11`; the UI defaults to `2026-12`.

- `POST /subscriptions` **requires** `departure_month` within the window → else
  `400 invalid_departure_month` (missing included). New rows are therefore always fixed-month.
- `PATCH` with `departure_month` must be within the window, **or equal to the stored value**
  (so a client can resend an unchanged expired month). `null` is accepted only when the stored
  row is already rolling (no change) → else `400 invalid_departure_month`. A fixed row can never
  return to rolling.
- **Legacy → fixed transition:** a rolling row becomes fixed only when the user picks a month
  (`PATCH departure_month`). It is never converted automatically. From that write on, the row
  follows fixed-month rules (it can expire). The route key, `created_at`, `plan_name` and pause
  state are unchanged by a month-only edit.
- One subscription per route pair: a different month for an existing route is **not** a new
  subscription → `409 duplicate_subscription`.

### 3.3 Status

Evaluated with the current month in Asia/Taipei, in this order:

1. `expired` — fixed row whose `departure_month` < current month. Fare checks and notifications
   stop for it; it is shown as 「已過期」 and **still counts** toward the limit. Reactivate it by
   `PATCH departure_month` to a month in the window (pause state is kept as stored).
2. `paused` — `alerts_paused = true`.
3. `active` — otherwise. Rolling rows never expire.

Expiry is derived, not written: no background job updates rows, so nothing races with users.

### 3.4 Error

```json
{ "error": "duplicate_subscription", "message": "你已經訂閱過「台北 → 東京」這條航線（每條航線只能訂閱一個月份）。", "details": { "route": "TPE-TYO" } }
```

`error` is a stable machine code (same field the M1 client already reads); `message` is
Traditional Chinese for display; `details` is optional.

## 4. Endpoints

### 4.1 `GET /subscriptions`

Response `200`:

```json
{
  "subscriptions": [ /* Subscription objects, sorted by created_at */ ],
  "limits": { "max": 10, "used": 3 },
  "months": { "current": "2026-11", "selectable": ["2026-12", "…", "2027-11"] }
}
```

`Query` on `email` (strongly consistent). `used` counts **every** row (active, paused, expired).
Legacy rows are normalised (§8.1). The UI shows 「我的航線訂閱：{used} / {max}」.

### 4.2 `POST /subscriptions`

Request:

```json
{ "origin": "KHH", "destination": "OKA", "departure_month": "2027-01", "target_price": 4500 }
```

Response `201` with the new Subscription (`alerts_paused: false`, `plan_name: null`,
`month_mode: "fixed"`).

Validation order (all failures are `400` unless noted; first failure wins):

1. Body is a JSON object → `invalid_json`
2. `origin` is an allowlisted origin → `unsupported_origin` (missing → `origin_required`)
3. `destination` is an allowlisted destination → `unsupported_destination` (missing → `destination_required`)
4. `origin != destination` → `same_origin_destination`
5. `departure_month` in the window (§3.2) → `invalid_departure_month`
6. `target_price` is an integer (not a boolean, not a string) within policy → `invalid_target_price`
7. Route not already subscribed by this user, any month → `409 duplicate_subscription`
8. Total records < limit → `409 limit_reached`

Write: the quota-checked create of §5.

### 4.3 `PATCH /subscriptions/{route}`

`{route}` must match `^[A-Z]{3}-[A-Z]{3}$` → else `400 invalid_route`. Request (all fields
optional, at least one of the first five required → else `400 empty_patch`):

```json
{
  "target_price": 8000,
  "departure_month": "2027-02",
  "alerts_paused": true,
  "origin": "RMQ",
  "destination": "SEL",
  "if_updated_at": "2026-11-05T03:00:00Z"
}
```

- `origin` and `destination` must be sent **together** → else `400 route_change_incomplete`.
- `if_updated_at` (recommended): if present and different from the stored `updated_at`
  → `409 conflict` (someone else changed it; reload).
- Validation as in §4.2 for any field present. Unknown fields → `400 unknown_field`.
- **None of these changes the number of records**, so none touches the quota record or can
  return `limit_reached`. Pause and resume never consume or release quota.

| Case | DynamoDB operation | Errors |
|---|---|---|
| Target, month and/or pause | `UpdateItem` with `attribute_exists(email)` [+ `updated_at = :if`] | `404 not_found`, `409 conflict` |
| Route change (± other fields) | **Atomic route change** (§6) | `404 not_found`, `409 duplicate_subscription`, `409 conflict` |
| Values equal to the stored ones | No write; returns the current row | — |

Response `200` with the resulting Subscription (its `route` is the new one after a route change).
The client must use the returned `route` for later calls.

### 4.4 `DELETE /subscriptions/{route}`

Response `204`, empty body. The quota-checked delete of §5 (optionally with
`updated_at = :if` when `?if_updated_at=` is given). Deleting is the **only** way to release a
slot, whatever the row's status. Errors: `400 invalid_route`, `404 not_found`, `409 conflict`.

## 5. Strict total limit (10 records per user)

**Rule:** a user may hold at most `max` subscription records. Active, paused and expired rows all
count; existing M1 rows count. Pause doesn't release, resume doesn't consume, expiry doesn't
release, delete releases one. Concurrent requests must never take a user past `max`.

A counting `Query` alone can be raced by two simultaneous requests, and DynamoDB conditions can't
compare against a count of other items. The limit is therefore enforced with a per-user quota
record whose **version** serialises every write that changes the number of records.

### 5.1 Quota record

Table `subscription_quota` (new, Phase 1B, pay-per-request, PITR on): partition key `email`;
attributes `count` (number) and `version` (number). It is separate from `subscriptions`, so the
deployed M1 list Lambda, the parser and the wrapper never see these records.

### 5.2 Writes that change the count: create and delete

Create (`POST /subscriptions`, and a legacy `POST /subscribe` for a route the user doesn't
have yet):

1. **Read the quota record first** (`GetItem`, `ConsistentRead`) → version `v`, or *absent*.
2. **Then** read the user's rows (`Query`, `ConsistentRead`) → true count `n`, existing routes.
3. Route exists → `409 duplicate_subscription`. `n >= max` → `409 limit_reached`. Nothing written.
4. `TransactWriteItems`:
   - `Put` subscription, condition `attribute_not_exists(email)`;
   - `Update` quota: `SET count = :n_plus_1, version = :v_plus_1`, condition `version = :v`
     — or, when the record was absent, condition `attribute_not_exists(email)` (this creates it).
5. `TransactionCanceledException`, reasons in item order:
   - item 0 `ConditionalCheckFailed` → `409 duplicate_subscription` (a concurrent create won);
   - item 1 `ConditionalCheckFailed`, or `TransactionConflict` → another create/delete committed;
     **retry from step 1** after a bounded backoff.

Delete: the same steps with `Delete` (condition `attribute_exists(email)`) and
`count = :n_minus_1`; item 0 failing → `404 not_found`.

Why this order is safe: every committed create or delete bumps `version`. If one commits after
step 1, our transaction's `version = :v` condition fails and we re-read. If it committed before
step 1, step 2 (strongly consistent, read after step 1) already includes it. So `n` is never
stale at commit time. Reading the count **before** the version leaves a gap in which another
create can commit unseen — `test_reading_count_before_quota_version_allows_a_bypass` shows the
11th row that order allows.

### 5.3 Retries and outcomes

- At most **3 attempts** per request; full-jitter exponential backoff between attempts
  (`random(0, min(200 ms, 25 ms × 2^attempt))`), so the worst case adds well under a second.
- Retries exhausted → `409 conflict` ("please try again"); nothing was written.
- The loser of a race at `max − 1` normally gets `409 limit_reached` on its re-read.
- Throttling (`ProvisionedThroughputExceeded`/`ThrottlingException`) uses the SDK's own retry;
  if it persists → `500 internal_error`, nothing partially written.

### 5.4 Writes that don't change the count

Target, departure month, pause/resume and route changes keep the number of records, so they
**don't read or write the quota record** and never conflict with creates or deletes. Their own
races are settled by item conditions: `attribute_exists` (row deleted meanwhile → `404`),
`attribute_not_exists` on the new route (route taken meanwhile → `409 duplicate_subscription`),
and optional `updated_at = :if` (→ `409 conflict`).

### 5.5 Users without a quota record (all M1 users today)

No bootstrap job is required: the first create or delete reads *absent*, counts the true rows
(e.g. 2 M1 rows → `n = 2`) and creates the record with `attribute_not_exists(email)`. Two
concurrent first writes can't both succeed: one creates the record, the other's condition fails
and it retries against version 1. A user who never creates or deletes never gets a record and
needs none (the count is always taken from `Query`).

### 5.6 Concurrency matrix (all covered by `aws/tests/test_m14_quota_model.py`)

| Concurrent requests | Guaranteed outcome |
|---|---|
| Two creates at 9 records | Exactly one `201`; the other `409 limit_reached` (or `conflict`) |
| Three creates at 8, no quota record | At most two `201` |
| Two creates of the same route | One `201`, one `409 duplicate_subscription` |
| Create + delete at 10 | Delete `204`; create succeeds only if it sees the freed slot |
| Route edit A→B + create of B | Exactly one succeeds |
| Route edit at 10 + create | Route edit `200` (needs no slot); create `409 limit_reached` |
| Pause + create + delete | All succeed independently; count stays exact |
| Pause + delete of the same row | Delete `204`; pause `200` or `404` |
| Legacy `POST /subscribe` (new route) + `POST /subscriptions` at 9 | Exactly one succeeds |
| Two legacy `POST /subscribe` for the same new plan | One creates, the other updates it (M1 upsert semantics) |

After every interleaving the tests also check that `count` equals the true number of rows.

### 5.7 Configuration

`max` comes from `subscription-policy.json` → `max_subscriptions_per_user`, passed as the
`MAX_SUBSCRIPTIONS` environment variable. The month window comes from the same file.

## 6. Atomic route change

Changing origin/destination changes the sort key, so it can't be an in-place update.

```
TransactWriteItems([
  Delete  subscriptions {email, route: OLD}
          condition: attribute_exists(email) [AND updated_at = :if_updated_at],
  Put     subscriptions {email, route: NEW, origin, destination, target_price, currency: "TWD",
                         departure_month (as sent, or carried over), alerts_paused (carried over
                         unless changed), previous_route: OLD, created_at: now, updated_at: now}
          condition: attribute_not_exists(email)
])
```

- All or nothing: the user never ends up with both routes or neither, and the count is unchanged.
- Duplicate target route → the `Put` condition fails → `409 duplicate_subscription`, nothing changes.
- `plan_name` is **not** carried over (it only describes the M1 fixed routes).
- A rolling row keeps rolling unless a month is sent; a new route chosen in the UI always sends one.
- `created_at` is reset (it's a new route); `previous_route` records where it came from.

## 7. Notification history behaviour

`notification_history` (key `pk = "{email}#{route}"`, sort `sent_at`) is **never read or
written by this API**; its role has no access to that table. The notification Lambda and its
dedup rule are unchanged: send if there is no previous alert for the key, or ≥ 24 h have passed,
or the price is ≥ 20 % or ≥ NT$2,000 below the last alerted price.

| User action | Alert behaviour |
|---|---|
| Create a new route | No history for that key → the first qualifying fare alerts immediately |
| Change target price | Same key: the 24 h floor and re-alert rules continue from the last alert |
| **Change departure month** | **Same key** (the month isn't part of it). Within 24 h of the last alert, a fare for the new month alerts only if it is ≥ 20 % / ≥ NT$2,000 below the last alerted (old-month) price; otherwise the first alert for the new month waits until the 24 h floor has passed. At most a 24 h delay; never a duplicate burst |
| Expire | Parser skips the row; history kept |
| Reactivate (expired → new month) | Same key; usually > 24 h since the last alert, so the first qualifying fare alerts |
| Pause | Parser skips the row; history kept |
| Resume | Same key: no instant repeat within 24 h of the last alert |
| Delete | History kept |
| Delete, then re-create the same route (any month) | Same key → dedup applies (prevents delete/re-create alert spam) |
| Change route A → B | B is a new key and may alert immediately; A's history is kept |
| Change back B → A within 24 h | A's history applies |

Making the month part of the dedup key would change `flight-fare-notification` and is out of
scope; it needs its own approval after the M1 email test. The alert email already shows the
actual departure and return dates of the fare, so a month change is visible to the user.

## 8. Backward compatibility with M1

### 8.1 Existing rows (rolling)

- **No data migration and no automatic conversion.** Existing rows (`TPE-TYO`, `TPE-SEL`) have
  no `departure_month`; they stay **rolling** (fares checked for next month, as today) until the
  user picks a month (§3.2).
- Normalisation on read: missing `alerts_paused` → `false`; missing `plan_name` → `null`;
  missing `departure_month` → `null` + `month_mode: "rolling"`; missing `origin`/`destination`
  → derived from `route`.
- Existing rows count toward the 10-record limit.

### 8.2 `POST /subscribe` (legacy) — one quota path

After cutover `POST /subscribe` is served by `flight-subscriptions-api` through the **same code
path** as `POST /subscriptions`, so the legacy endpoint can't bypass the limit:

| Request | Handling |
|---|---|
| `plan_name` not `tokyo`/`seoul` | `400 invalid_plan` (as today) |
| Plan's route already exists | `UpdateItem` (`attribute_exists`): `target_price`, `plan_name`, `currency`, `updated_at`; keeps `created_at`, pause state and `departure_month`. No quota change → `200` |
| Plan's route doesn't exist | Quota-checked create (§5.2) of a **rolling** row (no `departure_month`, as M1 writes today) → `200`, or `409 limit_reached` |
| Row appears or vanishes mid-request | The transaction fails; re-read decides update vs create (within the 3 attempts) |

The response body stays the M1 shape (`route`, `plan_name`, `target_price`, `currency`,
`updated_at`), so the current `/app` page needs no change. New error codes it doesn't know
(`limit_reached`) fall back to its generic error message.

### 8.3 Cutover and routing

- **This contract changes no production routing.** Today `POST /subscribe` and
  `GET /subscriptions` stay on the M1.1 Lambdas.
- Before cutover only the M1.1 Lambda writes rows, and it can only write the two plan routes, so
  no user can exceed the limit. A quota-unaware legacy writer **alongside** the new API could
  (`test_unaware_legacy_lambda_alongside_new_api_allows_a_bypass`), therefore:
- **Cutover is one reviewed change set** that, together, points `POST /subscribe`,
  `GET /subscriptions` and the four new routes at `flight-subscriptions-api`. The new routes are
  never reachable while the old writer still serves `POST /subscribe`.
- The cutover may only happen after the fare check supports everything the API can write
  (§8.4 and the plan's deployment gate).
- `POST /subscribe` is retired later in its own reviewed change.

### 8.4 Fare check compatibility

The deployed parser checks **next month** for every row of a route and ignores `alerts_paused`
and `departure_month`. If rows with a fixed month, pauses or new routes existed before the fare
check changed, users would get alerts for the wrong month, alerts while paused, or no checks.
Hence the gate in §8.3. The SQS message format to `flight-fare-notification` stays unchanged
(the fare's `depart_date`/`return_date` already travel in `cheapest`); the notification Lambda
needs no change.

## 9. Error codes

| HTTP | `error` | When |
|---|---|---|
| 400 | `invalid_json` | Body isn't a JSON object |
| 400 | `origin_required` / `destination_required` | Field missing on create |
| 400 | `unsupported_origin` / `unsupported_destination` | Code not in the allowlist |
| 400 | `same_origin_destination` | Origin equals destination |
| 400 | `invalid_departure_month` | Missing on create, malformed, outside the 12-month window, or `null` for a fixed row |
| 400 | `invalid_target_price` | Not an integer within policy |
| 400 | `invalid_route` | `{route}` path parameter malformed |
| 400 | `route_change_incomplete` | Only one of `origin` / `destination` sent |
| 400 | `empty_patch` / `unknown_field` | PATCH with nothing to change / unexpected field |
| 400 | `invalid_plan` | Legacy `POST /subscribe` with an unknown plan |
| 401 | `unauthorized` | No or invalid Supabase session |
| 404 | `not_found` | The caller has no subscription with that route |
| 409 | `duplicate_subscription` | The route already exists for this user (any month) |
| 409 | `limit_reached` | Would exceed 10 total records |
| 409 | `conflict` | `if_updated_at` mismatch, or concurrent changes after 3 attempts |
| 429 | `too_many_requests` | API Gateway throttling (10 req/s, burst 20) |
| 500 | `internal_error` | Unexpected failure; nothing partially written (transactions) |

## 10. Security and limits

- Least privilege (`aws/iam/subscriptions-api-role-policy.json`): `GetItem`, `Query`,
  `PutItem`, `UpdateItem`, `DeleteItem`, `ConditionCheckItem` on `subscriptions`; `GetItem`,
  `UpdateItem`, `ConditionCheckItem` on `subscription_quota`. No SSM, KMS, SQS, Lambda or
  `notification_history` access; the Travelpayouts and Resend keys stay unreachable.
- Logs never contain email addresses or tokens; subscribers appear as a short hash.
- Request bodies over 4 KB → `400 invalid_json`.
