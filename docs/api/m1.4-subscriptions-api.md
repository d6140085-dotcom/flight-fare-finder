# M1.4 subscriptions API — contract

- **Status:** specification for review (Phase 1A). Not deployed; no AWS resources exist for it yet.
- **Implements:** [ADR 0001](../adr/0001-m1-4-dynamic-routes.md) decisions D1–D6, D9, D11.
- **Prototype:** `src/lib/m14/subscriptions.ts` follows these shapes and error codes, so the
  Phase 1B client can replace the prototype's in-memory reducer without UI changes.

## 1. Overview

| | |
|---|---|
| Base URL | The existing HTTP API `flight-api` (`VITE_FLIGHT_API_URL`), region `ap-southeast-2` |
| Handler | New Lambda `flight-subscriptions-api`, role `flight-subscriptions-api-role` (`subscriptions` + `subscription_quota` tables only) |
| Format | JSON, UTF-8. Prices are whole TWD integers. Times are ISO-8601 UTC strings |
| Existing endpoints | `POST /subscribe` and `GET /subscriptions` (M1.1) keep working unchanged until Phase 3; see §8 |

| Method & path | Purpose | Success |
|---|---|---|
| `GET /subscriptions` | List the caller's subscriptions | `200` |
| `POST /subscriptions` | Create a subscription | `201` |
| `PATCH /subscriptions/{route}` | Change target price, pause/resume, and/or change origin and destination | `200` |
| `DELETE /subscriptions/{route}` | Delete a subscription | `204` |

`GET /subscriptions` replaces the M1.1 handler on the same route (Phase 1B, reviewed change set);
its response is a superset of today's, so the current `/app` page keeps working.

## 2. Authentication

- Every request needs `Authorization: Bearer <Supabase access token>` from the signed-in session.
- The Lambda resolves the user by calling Supabase `GET /auth/v1/user` with the project's
  publishable key, exactly as M1.1 does. The **email from Supabase** (trimmed, lower-cased) is
  the user key. Any `email` field in a request body or query is **ignored**.
- Missing, malformed, expired or rejected tokens → `401 unauthorized`. Nothing is read or written.
- Direct IAM-authorized invocations (no API Gateway context) may pass `test_email` for testing,
  as in M1.1. API Gateway requests always carry a request context, so this path can't be reached
  from the internet.
- CORS: existing origins and headers; `AllowMethods` gains `PATCH` and `DELETE`.

## 3. Resources

### 3.1 Subscription

```json
{
  "route": "TPE-TYO",
  "origin": "TPE",
  "destination": "TYO",
  "origin_name": { "zh": "台北", "en": "Taipei" },
  "destination_name": { "zh": "東京", "en": "Tokyo" },
  "target_price": 9000,
  "currency": "TWD",
  "alerts_paused": false,
  "plan_name": "tokyo",
  "created_at": "2026-11-04T07:17:23Z",
  "updated_at": "2026-11-04T07:17:29Z"
}
```

| Field | Type | Notes |
|---|---|---|
| `route` | string | `ORIGIN-DESTINATION`; the DynamoDB sort key; unique per user |
| `origin`, `destination` | string | IATA city or airport code from `aws/config/airports.json` |
| `origin_name`, `destination_name` | object | From the allowlist; `null` if a stored code is no longer listed |
| `target_price` | integer | TWD, `min`–`max` from `aws/config/subscription-policy.json` (1–1,000,000) |
| `currency` | string | Always `"TWD"` |
| `alerts_paused` | boolean | Stored only when `true`; an absent attribute means active |
| `plan_name` | string \| null | Present only on M1 fixed-plan rows (`tokyo`, `seoul`); `null` otherwise |
| `created_at`, `updated_at` | string | `updated_at` is also the optimistic-concurrency token (§4.3) |

### 3.2 Error

```json
{ "error": "duplicate_subscription", "message": "你已經訂閱過「台北 → 東京」這條航線。", "details": { "route": "TPE-TYO" } }
```

`error` is a stable machine code (same field the M1 client already reads); `message` is
Traditional Chinese for display; `details` is optional.

## 4. Endpoints

### 4.1 `GET /subscriptions`

Response `200`:

```json
{
  "subscriptions": [ /* Subscription objects, sorted by created_at */ ],
  "limits": { "max_active": 10, "active": 1, "total": 2 }
}
```

`Query` on `email` (strongly consistent). Legacy rows are normalised (§8).

### 4.2 `POST /subscriptions`

Request:

```json
{ "origin": "KHH", "destination": "OKA", "target_price": 4500 }
```

Response `201` with the new Subscription (`alerts_paused: false`, `plan_name: null`).

Validation order (all failures are `400` unless noted; first failure wins):

1. Body is a JSON object → `invalid_json`
2. `origin` is an allowlisted origin → `unsupported_origin` (missing → `origin_required`)
3. `destination` is an allowlisted destination → `unsupported_destination` (missing → `destination_required`)
4. `origin != destination` → `same_origin_destination`
5. `target_price` is an integer (not a boolean, not a string) within policy → `invalid_target_price`
6. Route not already subscribed by this user → `409 duplicate_subscription`
7. Active count < limit → `409 limit_reached`

Write: one `TransactWriteItems` (§5): `Put` subscription with `attribute_not_exists(email)` +
quota update. A cancelled transaction maps to `409 duplicate_subscription` or
`409 limit_reached` according to which condition failed (`CancellationReasons`).

### 4.3 `PATCH /subscriptions/{route}`

`{route}` must match `^[A-Z]{3}-[A-Z]{3}$` → else `400 invalid_route`. Request (all fields
optional, at least one of the first four required → else `400 empty_patch`):

```json
{
  "target_price": 8000,
  "alerts_paused": true,
  "origin": "RMQ",
  "destination": "SEL",
  "if_updated_at": "2026-11-04T07:17:29Z"
}
```

- `origin` and `destination` must be sent **together** → else `400 route_change_incomplete`.
- `if_updated_at` (recommended): if present and different from the stored `updated_at`
  → `409 conflict` (someone else changed it; reload).
- Validation as in §4.2 for any field present. Unknown fields → `400 unknown_field`.

| Case | DynamoDB operation | Errors |
|---|---|---|
| Target and/or pause only | `TransactWriteItems`: `Update` subscription (`attribute_exists(email)` [+ `updated_at = :if`]) + quota update if pause state changes | `404 not_found`, `409 conflict`, `409 limit_reached` (resume at limit) |
| Route change (± target/pause) | **Atomic route change** (§6) | `404 not_found`, `409 duplicate_subscription`, `409 conflict`, `409 limit_reached` |
| Values equal to the stored ones | No write; returns the current row | — |

Response `200` with the resulting Subscription (its `route` is the new one after a route change).
The client must use the returned `route` for later calls.

### 4.4 `DELETE /subscriptions/{route}`

Response `204`, empty body. One `TransactWriteItems`: `Delete` with `attribute_exists(email)`
(optionally `updated_at = :if` when `?if_updated_at=` is given) + quota decrement if the row was
active. Errors: `400 invalid_route`, `404 not_found`, `409 conflict`.

## 5. Strict active-subscription limit (10)

A counting `Query` alone can be raced by two simultaneous requests. The limit is therefore
enforced **inside the write transaction** with a per-user quota record.

- **Table `subscription_quota`** (new, Phase 1B): partition key `email`; attributes
  `active_count` (number) and `version` (number). Separate from `subscriptions`, so the existing
  M1 list Lambda, the parser and the wrapper never see these records.
- **Before writing**, the handler does strongly consistent reads of the user's subscriptions
  (true active count `n`) and quota record (`version` `v`, absent on first use). If the write
  would make the count exceed `max` → `409 limit_reached`, nothing written.
- **Every write that changes the active count** (create, pause, resume, delete of an active row)
  includes an `Update` of the quota record in the same transaction:
  `SET active_count = :new, version = :v_next` where `:new` is `n + 1` or `n − 1`, with condition
  `version = :v` (or `attribute_not_exists(email)` when no record existed).
  (DynamoDB conditions can't do arithmetic, so the limit itself is checked against `n` above;
  the `version` condition is what makes it race-free.)
- **Self-healing and race-free:** the handler always writes the **true** count ± 1, so drift
  (for example from legacy writes) is corrected on the next write. Any concurrent change bumps
  `version`, so the other transaction fails its condition; the handler re-reads and retries
  (max 3), then returns `409 conflict`.
- Route changes and target-only edits don't change the count but include a `ConditionCheck`
  on `version = :v` so they serialise with concurrent pause/resume.
- **Legacy writes** (`POST /subscribe`, which doesn't know about quotas) can add at most the
  two M1 routes; the self-healing read above corrects the count on the next M1.4 write. The
  legacy endpoint is retired in Phase 3.
- Paused subscriptions don't count. Resuming at the limit → `409 limit_reached`.
- `max` comes from `subscription-policy.json` via the `MAX_ACTIVE_SUBSCRIPTIONS` environment
  variable.

## 6. Atomic route change

Changing origin/destination changes the sort key, so it can't be an in-place update.

```
TransactWriteItems([
  Delete  subscriptions {email, route: OLD}
          condition: attribute_exists(email) [AND updated_at = :if_updated_at],
  Put     subscriptions {email, route: NEW, origin, destination, target_price, currency: "TWD",
                         alerts_paused (carried over unless changed), previous_route: OLD,
                         created_at: now, updated_at: now}
          condition: attribute_not_exists(email),
  ConditionCheck / Update  subscription_quota {email}   (§5)
])
```

- All or nothing: the user never ends up with both routes or neither.
- Duplicate target route → the `Put` condition fails → `409 duplicate_subscription`, nothing changes.
- `plan_name` is **not** carried over (it only describes the M1 fixed routes).
- `created_at` is reset (it's a new route); `previous_route` records where it came from.

## 7. Notification history behaviour

`notification_history` (key `pk = "{email}#{route}"`, sort `sent_at`) is **never read or
written by this API**; its role has no access to that table.

| User action | Alert behaviour |
|---|---|
| Create a new route | No history for that key → the first qualifying fare alerts immediately |
| Change target price | Same key: the 24 h floor and the ≥20 % / ≥NT$2,000 re-alert rules continue from the last alert |
| Pause | Parser skips the row; history kept |
| Resume | Same key: no instant repeat within 24 h of the last alert |
| Delete | History kept |
| Delete, then re-create the same route | Same key → dedup applies (prevents delete/re-create alert spam) |
| Change route A → B | B is a new key and may alert immediately; A's history is kept |
| Change back B → A within 24 h | A's history applies |

Deleting a user's history (e.g. account deletion) is out of scope and needs a separate approved
process.

## 8. Backward compatibility with M1 subscriptions

- **No data migration.** Existing rows (`TPE-TYO`, `TPE-SEL`) already store `origin`,
  `destination`, `target_price`, `currency`, `plan_name`, `created_at`, `updated_at`.
- Normalisation on read: missing `alerts_paused` → `false`; missing `plan_name` → `null`;
  missing `origin`/`destination` → derived from `route`.
- The fare pipeline treats a missing `alerts_paused` as active, so existing subscriptions keep
  alerting exactly as today.
- `POST /subscribe` (M1.1) stays unchanged until the new UI is live (Phase 3), then is removed in
  its own reviewed change. Rows it writes are valid M1.4 rows.
- The SQS message format to `flight-fare-notification` is unchanged; the notification Lambda
  needs no change.
- **Quota bootstrap:** before enabling M1.4 writes, create quota records from the current data
  (one per user with rows), or rely on the self-healing first write (§5).

## 9. Error codes

| HTTP | `error` | When |
|---|---|---|
| 400 | `invalid_json` | Body isn't a JSON object |
| 400 | `origin_required` / `destination_required` | Field missing on create |
| 400 | `unsupported_origin` / `unsupported_destination` | Code not in the allowlist |
| 400 | `same_origin_destination` | Origin equals destination |
| 400 | `invalid_target_price` | Not an integer within policy |
| 400 | `invalid_route` | `{route}` path parameter malformed |
| 400 | `route_change_incomplete` | Only one of `origin` / `destination` sent |
| 400 | `empty_patch` / `unknown_field` | PATCH with nothing to change / unexpected field |
| 401 | `unauthorized` | No or invalid Supabase session |
| 404 | `not_found` | The caller has no subscription with that route |
| 409 | `duplicate_subscription` | The route already exists for this user |
| 409 | `limit_reached` | Would exceed the active limit |
| 409 | `conflict` | `if_updated_at` mismatch, or concurrent change after retries |
| 429 | `too_many_requests` | API Gateway throttling (10 req/s, burst 20) |
| 500 | `internal_error` | Unexpected failure; nothing partially written (transactions) |

## 10. Security and limits

- Least privilege: `flight-subscriptions-api-role` gets `GetItem`, `Query`, `PutItem`,
  `UpdateItem`, `DeleteItem`, `ConditionCheckItem` on `subscriptions` and `subscription_quota`
  only. No SSM, KMS, SQS, Lambda or `notification_history` access; the Travelpayouts and Resend
  keys stay unreachable.
- Logs never contain email addresses or tokens; subscribers appear as a short hash.
- Request bodies over 4 KB → `400 invalid_json`.
