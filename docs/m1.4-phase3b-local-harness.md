# M1.4 Phase 3B-B — Local HTTP integration harness

A localhost-only environment that runs the real subscriptions API behind real HTTP, for
development and tests. **Dev/test only:** it is never packaged, deployed or reachable from
outside the machine.

```
HttpSubscriptionsClient / curl / tests
   │  real HTTP, 127.0.0.1:<random port>
   ▼
aws/tools/local_api.py      ── API Gateway HTTP API simulation: routes, payload-2.0 events,
   │                           CORS, gateway 404/413 and injected 429/502/503/504
   ▼
index.handler (unchanged) ─── subsapi.auth.resolve_email (unchanged) ── HTTPS ──► fake Supabase
   │                                                                     127.0.0.1, throwaway CA
   ▼
local DynamoDB: DynamoDB Local (DDB_ENDPOINT) or moto in-process (default)
```

## Run it

```bash
pip install -r aws/requirements-test.txt          # boto3, moto (brings cryptography)
env -i PATH="$PATH" HOME="$HOME" python3 aws/tools/local_api.py serve
# DynamoDB Local instead of moto:
env -i PATH="$PATH" HOME="$HOME" DDB_ENDPOINT=http://127.0.0.1:8000 python3 aws/tools/local_api.py serve
```

- **Startup output:** one JSON line with `api_url`, `engine` (`dynamodb-local` or `moto`), the allowed CORS origins and the test table names.
- **Fake sign-in tokens:**
  - `harness-token-user` → `user@example.com`;
  - `harness-token-other` → `other@example.com`;
  - `harness-token-third` → `third@example.com`;
  - `harness-token-expired` → `401`;
  - anything else → `401`.
- **Why `env -i`:** the harness refuses to start when it finds real-looking credentials or proxies in the environment, and `env -i` starts it with a clean one.

Tests:

```bash
python3 -m unittest -v aws/tests/test_m14_local_harness.py   # Python, real HTTP
npm run test:harness                                          # HttpSubscriptionsClient, real HTTP
```

The manual GitHub workflow **M1.4 DynamoDB Local tests** runs both against the official
DynamoDB Local container. It has no push or PR trigger, no secrets and no AWS access. **Only results with
`engine: dynamodb-local` count as DynamoDB Local results**; moto runs are lightweight checks.

## Isolation (fail closed)

The harness refuses to start (exit 2, nothing printed on stdout) when:
- **AWS:**
  - `DDB_ENDPOINT` is not a localhost URL;
  - an AWS credential is set to anything but the fake `testing` values;
  - an AWS profile, role, web identity, container credentials or a Lambda runtime is configured;
  - `SUBSCRIPTIONS_TABLE` or `QUOTA_TABLE` is a production name or lacks the `test-` prefix;
  - any variable contains an API Gateway URL or an `AKIA…` key.
- **Supabase:**
  - `SUPABASE_URL` is not `https://` on localhost;
  - a real-looking Supabase publishable key, service-role key, secret, JWT secret or access token is set;
  - any variable contains a `*.supabase.co` URL or an `sb_secret_` key.
- **Network:** it is asked to bind anywhere but `127.0.0.1` or `::1`, or to allow the CORS origin `*`.

After the checks pass, the process:
- removes the proxy variables;
- sets fake AWS credentials;
- creates fresh `test-` tables;
- trusts **only** its own throwaway certificate authority (`SSL_CERT_FILE`, plus an empty
  `SSL_CERT_DIR`).

So the unchanged auth code can complete TLS only with the local fake Supabase. Requests are
never forwarded anywhere.

**The control port** (`--control`, tests only) resets and seeds the tables, fixes the clock and
version tokens, reads the stored state and queues one-off 429/502/503/504 faults. It listens on
a second loopback port, and every request needs the random secret printed at startup. The API
port has no control routes.

**Exclusion:** tests check that the Lambda ZIP contains no harness file, that no application
source imports it, and that only the manual workflow runs it.

## Simulated gateway behaviour

| Request | Harness response |
|---|---|
| Unknown route or method (incl. `/subscriptions/` and extra segments) | `404 {"message":"Not Found"}` |
| Body over 1 MiB | `413 {"message":"Request Entity Too Large"}` (the handler's own limit, 4 KiB, gives `400 invalid_json`) |
| Injected fault | `429 Too Many Requests`, `502 Internal Server Error`, `503 Service Unavailable`, `504 Endpoint request timed out`; the function is not reached |
| Preflight with an allowed origin, method and headers | `204` with `Access-Control-Allow-Origin/Methods/Headers/Max-Age` |
| Preflight otherwise | `204` without any `Access-Control-*` header |
| Allowed origin on any other response (including errors) | `Access-Control-Allow-Origin: <origin>`; never `*`, no credentials |
| Disallowed origin | served without CORS headers; the browser blocks it |

The planned B3 CORS settings are in `aws/tools/cors.json` (`b3_allow_origins`) and contract §2.

## Known limitations

- **CORS enforcement:** Node's `fetch` and Python's `urllib` don't enforce CORS. The harness
  tests check CORS as HTTP headers; a real browser check belongs to Phase 3B-D (Playwright).
- **The gateway is simulated,** not API Gateway itself. Exact gateway answers to rejected
  preflights, throttling and timeouts may differ in detail. Those are checked again at B3 on a
  test stage.
- **Faults:** a `504` here never reaches the function. A real 504 can happen after a write
  committed, which is why the client tells users to reload.
- **Concurrency model:** a threaded server shares one function instance, whereas Lambda runs
  separate instances. Concurrency still exercises the real DynamoDB conditions and
  transactions, as in B4.
