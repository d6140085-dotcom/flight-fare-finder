# B3 rollback: suspend notification delivery

Status: planning document (B6-3A, 2026-11-28). Nothing here changes AWS. Every AWS step below
needs its own approval at the time.

## 1. Rule

**A previous Lambda version is not automatically compliant.** Switching the notification
function (or its alias) to an earlier version is a rollback only when that exact version has been
independently verified against the current requirements:

- the labelled Aviasales affiliate link wherever a Data API fare is shown, produced in the
  approved way (AFFILIATE_LINK_MODE; Travelpayouts recommends partner links, ticket #257588,
  2026-11-27), and the Aviasales source label (spec §8.5, conditions 3 and 4);
- the current email content (disclaimer, affiliate disclosure, no 「立即訂購」);
- the current data display (no stale or unsourced amounts);
- Trip.com and Skyscanner disabled; month guards; month-aware deduplication.

The legacy M1 function (`flight-fare-notification`) and `EMAIL_TEMPLATE=m1` fail these checks
(unmarked 「立即訂購」 link, no source label, no disclosure). Neither is a rollback target.

**If no verified compliant version exists, the rollback is suspension:** disable the SQS Event
Source Mapping (the queue trigger) from `flight-fare-queue` to the notification function, and keep
the EventBridge rule `flight-price-check` disabled so nothing new is queued. Restoring a
non-compliant email path is never the fallback.

## 2. What suspension does

| Topic | Behaviour |
|---|---|
| **In-flight messages** | An invocation already running finishes its batch. Messages it had received but not deleted become visible again after the queue's visibility timeout (repository value 180 s, `aws/README.md`) and wait in the queue. A history claim left by an interrupted attempt expires after `CLAIM_SECONDS` (120 s); a redelivery of the same fare event re-enters it later. |
| **Queue retention** | Messages stay until the queue's `MessageRetentionPeriod`, then SQS deletes them unsent. The repository doesn't set it (SQS default: 4 days). **The live value is UNVERIFIED** (§4). |
| **DLQ** | No stack in this repository defines a redrive policy. **Whether the live queue has a DLQ is UNVERIFIED** (§4). While the trigger is disabled nothing is received, so nothing moves to a DLQ. Without a DLQ, a message that keeps failing after resumption cycles until retention ends; the v2 handler drops invalid messages (`keys.InvalidMessage`) instead of retrying them. |
| **Stale notifications** | On resumption, the v2 service skips any fare event older than `MAX_MESSAGE_AGE_HOURS` (20 h, below Resend's 24 h idempotency window) as `skipped:stale`. The one exception: an event this function had already claimed and may have sent is recorded as `recorded:unconfirmed`, never sent again. A suspension longer than 20 h therefore drops the backlog without sending it. Purging the queue instead is an AWS write and needs approval. |
| **Partner links (B6-3A)** | A queued message keeps its `aviasales_partner_url`; a link pinned to a fare event in `notification_history` survives the suspension. On resumption every link is validated again; an unapproved or invalid one blocks the email (nothing sent, nothing recorded). |
| **Producer** | With EventBridge disabled, no new fare checks run. A parser invocation already running can still enqueue; those messages wait in the queue like any other. |

## 3. Before resuming delivery

All of the following, recorded as evidence:

1. The cause is fixed through a reviewed PR and merged by the owner.
2. The deployed function's code hash matches the reviewed build, and its configuration is
   recorded: `EMAIL_TEMPLATE`, `AFFILIATE_LINK_MODE` (never left unset: unset means `disabled`),
   whether `TP_MARKER` and `TP_TRS` are set (never their values).
3. The offline suites pass on that exact commit.
4. Queue depth (visible, in flight, delayed) and DLQ depth are known; a decision on the backlog
   (let `MAX_MESSAGE_AGE_HOURS` expire it, or purge with approval).
5. In `partner_api` mode: an approved link format exists (added through a reviewed change citing a
   controlled API dry run), and the redirect behaviour has been confirmed by Travelpayouts or by
   the owner's manual check.
6. One controlled test message to a test inbox the owner controls, approved beforehand.
7. The legacy M1 trigger stays disabled.

## 4. Live AWS state: not rechecked

On 2026-11-25 a read-only check observed: EventBridge `flight-price-check` DISABLED; the legacy M1
`flight-fare-notification` trigger on `flight-fare-queue` **Enabled**; the queue empty. That is
historical. The AWS connector needed re-authentication when B6-3A was prepared (2026-11-27/28), so
the live state has **not** been independently rechecked, and the retention, DLQ and trigger states
must not be assumed unchanged.

Read-only checks required before B3 (no writes):

1. Caller identity is the read-only connector role.
2. `flight-fare-queue` attributes: `MessageRetentionPeriod`, `VisibilityTimeout`,
   `RedrivePolicy`, `ApproximateNumberOfMessages`, `…NotVisible`, `…Delayed`.
3. If a DLQ exists: its depth and retention.
4. Every Event Source Mapping on the queue: function, state, batch size,
   `ReportBatchItemFailures`.
5. EventBridge `flight-price-check`: state and target.
6. Each notification and fare-check function: last modified, code SHA-256, versions and aliases,
   timeout, reserved concurrency, environment variable **names** only.
7. The parser's asynchronous invoke configuration (retry attempts, maximum event age, destinations).
8. `notification_history` exists; SSM parameters exist (metadata only, never values).
9. Recent invocation and error metrics; CloudTrail write events since 2026-11-25.
