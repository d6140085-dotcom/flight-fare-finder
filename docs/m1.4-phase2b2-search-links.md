### 2.3 The Aviasales marker (Travelpayouts condition 3)

- Source: environment variable **`TP_MARKER`** on the v2 notification Lambda, set at deploy time.
  It is never in the repository; validation rejects any 5+ digit number, `marker=`, token,
  secret or `eyJ` string in `search-platforms.json`. Tests use the obvious fake `000000`.
- Accepted format: 3–12 ASCII digits (Travelpayouts' documented example is numeric). SubIDs
  (`.subid`) are documented by Travelpayouts but unused, so a dot is rejected.
- Appended as exactly one `marker` parameter, on Aviasales links only (L09).
- `TP_MARKER` is the public Travelpayouts partner ID that appears in affiliate URLs. It is **not**
  the API token (`TP_TOKEN`), which is never read by this Lambda and never appears in a link.
- **Fail closed (follow-up commit).** The reference email shows Aviasales Data API fares, so
  Travelpayouts' condition 3 applies to every such email. If a labelled Aviasales affiliate link
  can't be built — `TP_MARKER` missing or malformed, link config missing or invalid, Aviasales or
  its affiliate block disabled, a builder error, or a code outside the catalog — then:
  - the builder returns **no links at all** (never a plain Aviasales link, never third-party links);
  - `render_reference()` refuses (`AffiliateLinkUnavailable`), so **the email isn't sent**;
  - the check runs **before the claim**, so the stream gets no claim, no `STATE` row, no log row
    and no M1 row — nothing can later be mistaken for a successful send;
  - the message ends as `blocked:<reason>` (consumed, not retried: the cause is configuration,
    and the next fare check creates a fresh event once it is fixed);
  - the Lambda logs `… BLOCKED <reason> …` with a data-free reason code
    (`no_valid_aviasales_marker`, `links_config_unavailable`, `link_builder_error:<Type>`,
    `unsupported_code`, `aviasales_affiliate_disabled`), and at start-up
    `links: ERROR TP_MARKER is not set | has an unexpected format`. The value is never logged.
- `search-platforms.json` validation now always requires the Aviasales affiliate block
  (`enabled` and `required`), not only when other platforms are on.
- `EMAIL_TEMPLATE=m1` keeps the M1 email byte-for-byte (backward compatibility). Note that the
  M1 email — what production sends today — links to Aviasales **without** a marker. Using `m1`
  as a rollback for v2 therefore returns to today's non-affiliate behaviour; whether that is
  acceptable under the Travelpayouts conditions is the owner's call (see §5 item 2).

### 2.4 Failure handling (spec §6)

| Situation | Result |
|---|---|
| `TP_MARKER` missing/invalid, link config unavailable, builder raises, Aviasales affiliate disabled | **Blocked**: no email, no history write, `blocked:<reason>` (§2.3) |
| Code not in the catalog, lower-case, `TSA` as origin, empty, 4 letters, injection | No links → **blocked** (`unsupported_code`). Routes come from validated subscriptions, so this shouldn't occur |
| Missing, malformed, past, outside the window, or return before departure | Every platform's general search page with the notice; Aviasales' keeps the marker |
| Codes not verified for a platform | That platform's general search page; others unaffected |
| Platform `enabled: false` | Omitted; others unaffected |
| Bundled config invalid at start-up | Reference emails blocked; the package build already refuses such a file |
| `EMAIL_TEMPLATE=m1` | M1 email, byte-identical to production (parity test) |

### 2.5 Deviations from, and corrections to, the spec

1. **Aviasales year ambiguity (spec §4.2 was wrong).** The spec said the 13-month window keeps
   the year-less DDMM path unambiguous. It doesn't: a return date 12–13 months away reads as a
   date in the past. Aviasales now gets its fallback (home page with marker) when the return date
   is on or after the same day next year; Skyscanner and Trip.com keep their itinerary links.
2. **L12 "no marker" is enforced at run time, not at build time.** The marker is deploy-time
   data, so the build can't see it. The build enforces the configuration half (Aviasales
   affiliate block always enabled and required); the run time blocks the email (§2.3).
3. **Spec §6 "email still sends without links" is superseded** for the reference template: an
   email without the affiliate link is blocked instead (Travelpayouts condition 3).
4. Fallback labels are stricter than spec §5 (「一般搜尋頁」, 「未帶入行程」, 「請自行輸入並確認航線與日期」),
   and Google uses the same pattern instead of 「在 Google 航班自行搜尋」.
5. Missing dates are shown as 「未提供」 instead of an empty string.

### 2.6 Aviasales full-year link format (reviewed, not adopted)

Travelpayouts' article
[Aviasales affiliate links](https://support.travelpayouts.com/hc/en-us/articles/5711895629714-Aviasales-affiliate-links)
(read 2026-11-11) documents a parameterised search link:

| Parameter | Documented meaning |
|---|---|
| `origin_iata`, `destination_iata` | IATA codes; city codes recommended |
| `depart_date`, `return_date` | `Y-m-d` (full year) |
| `oneway` | `1` or `0` (default `0`) |
| `adults`, `children`, `infants` | passenger counts (defaults 1/0/0) |
| `trip_class` | `0` economy, `1` business |
| `currency` | a fixed list (RUB, USD, EUR, UAH, CNY, KZT, AZN, BYN, THB, KGS, UZS) — **no TWD** |
| `marker` | your partner ID |

Paths: `{DomainName}/searches/new` (results) and `{DomainName}/flights/` (pre-filled form).
The domain is left as a placeholder in the article, so the host is **not** documented there.

The same article says links are created in the Travelpayouts dashboard (Aviasales programme →
Tools → Links → Create link), that you check the resulting page for `marker=` with your ID, and
that a partner ID can't simply be added to a short link.

**Conclusion: feasible in principle, not adopted in this PR.**

- In favour: full `YYYY-MM-DD` dates would remove the year ambiguity, so Aviasales could keep an
  itinerary link for the whole 13-month window instead of the general page beyond 12 months.
- Against adopting it now:
  1. the host for `searches/new` isn't stated;
  2. no link in this format has been opened in a browser for this project;
  3. hand-appending `marker` isn't shown to guarantee attribution — the documented process is the
     dashboard link generator.
  The current `/search/{O}{DDMM}{D}{DDMM}1` path is the M1 production format and has been
  browser-verified.
- Candidate (to verify, **not** used in code):
  `https://www.aviasales.com/searches/new?origin_iata=TPE&destination_iata=TYO&depart_date=2026-12-11&return_date=2026-12-18&oneway=0&adults=1&trip_class=0&marker=<marker>`
  (no `currency`, because TWD isn't in the documented list).
- Manual verification needed before switching (owner, in a browser, signed in to Travelpayouts):
  1. In the dashboard, generate an Aviasales flight-search link for one route and compare its
     host, path and parameters with the candidate.
  2. Open the candidate and confirm route, both dates, round trip, 1 adult, economy.
  3. Confirm the landing page keeps `marker=<your ID>` after redirects.
  4. Confirm a test click appears in the Travelpayouts statistics.
  5. Do the same checks for the **current** `/search/…?marker=` link: hand-appended attribution
     is unverified for it too (B6 item 2).

  Switching formats is then a small change to `aviasales_url()` plus golden vectors.
